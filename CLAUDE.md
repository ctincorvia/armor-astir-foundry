# Foundry Module Development Notes

## Concurrent work
- There might be other agents or humans working at the same time as you. Do not panic if you see diffs with changes you did not make in unrelated files. If you and another actor made changes to the same file, then you can investigate.

## Subagent Model Selection

When spawning subagents via the `Agent` tool, set the `model` parameter explicitly rather than relying on inheritance — under `opusplan` or `opus`, a subagent spawned during plan mode inherits Opus, which is overkill and expensive for most exploration.

- **Rote / well-scoped exploration** (known files or symbols, a single targeted lookup, mechanical grep/read work): use `model: "haiku"`.
- **High-complexity exploration** (ambiguous scope, cross-file inference, or output that will directly drive a plan): use `model: "sonnet"`.

Judge each exploration's complexity. When genuinely unsure, prefer `sonnet`.

In practice, a brief that's purely rote (haiku-eligible) is usually also small enough to fall under the "≤3 queries → use Grep/Read directly" guidance and not need a subagent at all — so haiku-tier Explore agents will legitimately be rare. Don't force a haiku call just to exercise the tier; most real briefs mix a verbatim-lookup part with an interpretive part, and bundling both under `sonnet` in one call is correct rather than a sign the dial isn't being used.

## Implementing Plans from Plan Mode

After a plan is approved, prefer delegating the implementation to a subagent with a distilled, self-contained brief rather than continuing inline in the planning session.

- **How**: write the brief to contain only the finalized approach — don't say "implement the plan we discussed," which leans on the polluted history to fill gaps.
- **Exception**: for work that needs tight, iterative back-and-forth or repeated judgment calls, staying inline in the session can be simpler than round-tripping through a subagent.

## Scripts toolbox
Committed, reusable helper scripts live in `.claude/scripts/` (see its own `README.md`) — check there before hand-editing a whitespace-fiddly file or writing a one-off script for a problem that's likely recurred before. This applies just as much when delegating an editing task to a subagent as it does inline: a subagent starts cold on every spawn and has no way to know this directory exists unless the brief says so, so a brief that involves editing existing files should point at it explicitly rather than assume the subagent will find or reinvent it.

- `replace_lines.py` replaces a contiguous line range by number instead of requiring an exact text match, sidestepping the class of `Edit` failures caused by tabs/spaces or trailing whitespace that don't survive a copy out of `Read`'s line-numbered output. It also preserves the file's existing newline convention (`\n` vs `\r\n`) — a hand-rolled one-off replacement script frequently doesn't, and the corruption isn't obvious until a `git add` warning or a diff review surfaces it.
- Invoke everything in `.claude/scripts/` (and any new script you add there) via `py`, not `python`/`python3` — that's the interpreter that actually resolves on this machine.
- When a scripting need recurs rather than being a true one-off, add a new script to `.claude/scripts/` (self-documented via its own docstring/`--help`, listed in its `README.md`) instead of writing a fresh throwaway each time, so the next session — or the next subagent — doesn't have to solve the same problem again.

## Before declaring a task done
- Stage the changes (`git add`) and run the pre-commit checks (`npx lint-staged` and `npm run test:coverage`, as defined in `.husky/pre-commit`) before declaring any task done.
- **When a check fails, assume the code is wrong before assuming the tool is wrong.** If `npm run test:coverage` reports specific uncovered lines, go read those lines and fix them (or add the missing test) before entertaining any theory that the coverage tooling itself is broken — a stale cache, an environment artifact, duplicate report entries, and the like. Only pursue a tooling-bug theory once a clean rerun reproduces the identical anomaly *and* you've confirmed the tool's own config would actually produce whatever artifact you're blaming (e.g. check `vitest.config.js`'s `coverage.reporter` list before analyzing a `coverage-final.json` you haven't confirmed exists). Never report a failing check as "pre-existing" or "unfixable" without pasting the falsifying command output in your report — a bare claim isn't a substitute for a receipt, and this project has already burned a large, unnecessary investigation chasing a coverage "bug" that a single fresh rerun would have disproven in seconds.

## Code organization
Prefer reasonable groupings of classes and functions over large "god files" — each file readable in one sitting and scoped to one clear concern. This is a judgment call, not a line count: split when a file's *responsibilities* multiply. A cohesive file that's long because its subject matter is long (e.g. a catalog of content) is fine.

- `scripts/playbook/playbook-sheet/` is the reference pattern: one file per domain (`astir-mixin.js`, `ardent-mixin.js`, `equipment-mixin.js`, `moves-mixin.js`, `frames-mixin.js`, `progression-mixin.js`, `tracking-mixin.js`), each exporting a plain object of methods merged onto `PlaybookActorSheet.prototype` via `Object.assign` in the orchestrator (`scripts/playbook/playbook-actor-sheet.js`) — not a class-inheritance chain, since the domains never need `super` or to override each other. Every method stays reachable at exactly the `sheet._methodName(...)` path callers and tests already expect.
- A mixin object merged that way is safe for a primitive-default instance field like `_dangerAddOpen = false` (reads fall through the prototype, writes shadow it per-instance) but **not** for an array/object default, which would be shared by reference across every sheet instance. Keep any non-primitive-default field as a real class-field declaration on the orchestrator class itself.
- When consolidating a derived, cross-cutting constant during a split, watch which direction the dependency points — don't drop it into the lowest-level module it happens to reuse pieces of if that would make that module depend upward on higher-level ones. This is why `ALL_MOVES`/`WEAPON_MOVES` got their own `scripts/moves/all-moves.js` rather than living in `moves.js`, which stays free of any dependency on `playbook-moves.js`/`astir.js`/`ardent.js`.
- The same principle applies to test files, not just source. `tests/playbook-actor-sheet.test.js` used to be the largest file in the repo by a wide margin; it's now been split along the same domain lines as the `playbook-sheet/` mixins, plus one file per cross-cutting concern: `tests/playbook-actor-sheet-astir.test.js`, `-ardent.test.js`, `-equipment.test.js`, `-frames.test.js`, `-progression.test.js`, `-tracking.test.js`, `-moves.test.js` (getData shaping, gating, hold, picking), `-move-rolls.test.js` (`_onMoveRoll`/`_onWeaponMoveRoll` and spend variants), `-roll-results.test.js` (every `_rollMove` variant), and `tests/move-chat-listeners.test.js` for `scripts/moves/move-chat-listeners.js`'s own exports. `tests/playbook-actor-sheet.test.js` itself now only covers the orchestrator: class basics, `getData`'s cross-cutting fields, `activateListeners`, `_seedCosmeticDefaults`, `_onPlaybookChange`. `tests/playbook-actor-sheet-commander.test.js` was the original precedent for peeling off one domain's tests into their own file.
- **A domain test file that outgrows one file again splits one level further, by call-site cluster rather than by a second pass over the same domain lines** — `-astir.test.js`/`-equipment.test.js`/`-move-rolls.test.js`/`-roll-results.test.js` each kept only their `getData`/`activateListeners` describes and peeled the rest off into siblings named for what they cover, not for a sub-domain: `-astir-controls.test.js`/`-astir-loadout.test.js`/`-astir-effects.test.js`, `-equipment-add.test.js`/`-equipment-edit.test.js`/`-equipment-weapon-moves.test.js`, `-move-roll-spends.test.js`/`-move-roll-targets.test.js`/`-weapon-rolls.test.js`, `-roll-offers.test.js`/`-roll-guided.test.js`/`-roll-resolved.test.js`. `equipment.test.js` (the pure-data/pure-function file for `scripts/equipment/equipment.js`, unrelated to the sheet) split the same way into `equipment-tags.test.js`/`equipment-editor.test.js`/`equipment-editor-options.test.js`/`equipment-catalog.test.js`. Each split file duplicates whatever slice of the original's `vi.mock`/`beforeEach` scaffolding its own describes actually exercise — vitest hoists `vi.mock` per file, so it can't be shared via import — but catalog-lookup constants that repeat across several of these files (`const EXCHANGE_BLOWS = BASIC_MOVES.find(...)`, etc.) are centralized in `tests/helpers/move-fixtures.js` instead of being redefined in each one, the same sharing `tests/helpers/move-test-helpers.js` already does for the `move-*.test.js` family's roll/dialog fixtures.
- The same domain-per-folder principle applies one level up: `scripts/core/` (cross-cutting catalogs referenced by every domain below — Traits, Approaches), `scripts/moves/`, `scripts/equipment/`, `scripts/frames/` (Astir/Ardent), `scripts/playbook/` (the playbook actor sheet plus its own `playbook-sheet/` mixins), and `scripts/world-actors/` (Carrier/Authority/Cause). `main.js` and `actor-creation.js` stay at `scripts/` root since both are cross-domain bootstrapping code, not owned by one folder.
- **Within a domain folder, a large catalog-plus-logic file splits into one file per catalog plus one (or a few) files for the logic that reads them — never by fragmenting a single catalog literal**, which per the rule above is fine to leave long. `scripts/frames/astir.js` (catalogs: `astir-parts.js`, `astir-moves.js`, `astir-weapons.js`; logic: `astir-power.js`, `astir-pickers.js`), `scripts/moves/moves.js` (catalogs: `basic-moves.js`, `special-moves.js`; logic: `move-results.js`, `move-dialogs.js`, `move-roll.js`), and `scripts/equipment/equipment.js` (catalogs: `equipment-tags.js`, `equipment-catalog.js`; logic: `equipment-helpers.js`, `equipment-dialogs.js`, plus a leaf `equipment-constants.js` for the small values both a catalog and the dialog logic need to reference, which has to live somewhere neither of them owns or the two form an import cycle) are the reference examples. `scripts/equipment/starting-gear.js` split off only its catalog (`starting-gear-pools.js`, ~900 lines) and kept its logic, since that one file had no separate logic-file's-worth of code to split out. In every case the original file stays as a thin barrel — `export { X } from "./sibling.js";` — re-exporting everything it used to define, so no existing importer's path needs to change (see `scripts/moves/move-pools/index.js`/`scripts/moves/playbook-moves.js:24` for the pattern this follows). Route any name two siblings both need through whichever one actually owns it, never back through the barrel — the barrel importing from a sibling that itself imports from the barrel is a real (if usually harmless) circular import, worth avoiding on a fresh split even though `astir.js`'s pre-existing `astir-power.js`/`astir-pickers.js` cycle has been confirmed safe by the full test suite once already.
- **Handlebars partials follow the same principle, and use the same barrel-free approach** — Foundry doesn't need one, since `{{> "modules/armor-astir/templates/<path>.hbs"}}` addresses a partial directly. `templates/playbook-actor-sheet.hbs` split into `templates/playbook-sheet/*.hbs`, one partial per tab (plus `header.hbs`/`status-row.hbs`/`dangers-column.hbs` for the non-tab chrome, and `ardents.hbs` split out from `tab-astir.hbs` since the Ardents section is large enough to be its own concern). Partials must be preloaded via `loadTemplates([...])` — added to the existing `Hooks.once("init", ...)` in `scripts/main.js` — or Foundry throws on first render. When cutting a partial boundary, never split a `{{#each}}`/`{{#if}}`/`{{#with}}` block across the cut: a `{{../foo}}` inside the moved block must still resolve against a frame that opens *within the same partial* (partials inherit the calling context at their `{{>}}` call site, so this holds as long as the `{{>}}` call itself isn't itself nested one level deeper than the original inline markup was).

## Code comments
Default to no comments — well-named identifiers and the diff/PR description carry the "what." Add one only when the WHY is genuinely non-obvious: a hidden constraint, an invariant, a workaround for a specific bug, or behavior that would otherwise surprise a reader. Keep it to one short line; a comment that needs more than that is a sign the reasoning belongs in a doc, not inline.

- **Architectural rationale, cross-file coupling, and design history belong in `docs/domains/*.md`, not in code comments.** Those files exist precisely to hold this kind of explanation — see "Domain conventions" below for the current file-per-area layout. A comment that would otherwise run several lines/sentences (e.g. explaining why a slot-keyed field mirrors another file's key-keyed one, or walking through everything a function's callers assume) should become a doc entry instead, with at most a one-line pointer comment in the code if a reader needs to know where to look (`// see docs/domains/world-actors.md, "Carrier weapons"`).
- Pre-existing multi-paragraph comments in this codebase predate this convention and aren't the pattern to copy for new code — trim opportunistically when touching that code, but don't go out of your way to rewrite comments unrelated to the task at hand.

## Reference environment
- The baseline PBTA Foundry system (`pbta`) and two Masks: New Generation modules are checked out in sibling directories as this module's reference environment. `masks-newgeneration-sheets` is the practical example for implementing and registering custom character/NPC sheets (`ActorSheet` subclasses in `module/masks-character-sheet.mjs` / `module/masks-npc-sheet.mjs`, Handlebars in `templates/`, styling in `styles/`); it has never been updated past core v11, so it is pattern reference only, not something to version-match — and since it imports pbta's own `PbtaActorSheet` rather than hardcoding a Foundry-version-specific base class, it creates no mismatch risk.
- **The sibling `pbta` and `masks-newgeneration-unofficial` repos are pinned (detached HEAD) to the exact versions actually installed** — `pbta` at tag `1.1.15.2`, `masks-newgeneration-unofficial` at tag `1.7.6` — both matching the installed Foundry v12.331.0. This makes their code a reliable reference for what's actually running.
- **If either sibling repo is ever checked out to `main` (or a different tag) again, treat it as running ahead of what's installed** until re-pinned to match. `main` on both tracks newer, unreleased core-version support (e.g. `pbta`'s `main` currently targets core v14 / pbta 1.2.0), and a base-class or namespace reference copied from ahead-of-release source can throw at module-evaluation time — which aborts this module's entire `esmodules` import chain, not just the feature being added (this has happened once already). If in doubt, confirm a reference also appears in the *installed* system bundle (`Data/systems/pbta/module/pbta.js` in the Foundry user data directory) or in Foundry's own unpacked client source (`resources/app/client/...` under the Foundry install directory) — grep both if unsure.
- Foundry does not hot-reload `esmodules` — after editing a script file the client needs a full reload. It *does* hot-reload `css`, `hbs`/`html` and `json` (verified in the installed client's `#handleHotReload`: CSS by cache-busting the `<link>` href, Handlebars by recompiling the partial and re-rendering every open window), so a styling or template tweak can land without one. That reload is pushed by a server-side file watcher, though, and whether it fires through the dev-checkout junctions is unverified — treat a full reload as the reliable fallback whenever an edit doesn't appear. See [docs/windows-dev-setup.md](docs/windows-dev-setup.md) for the junction layout itself.

## Recurring conventions
These hold across every domain below. The domain sections note only genuine exceptions.

- **Manual trackers, not enforcement.** Nothing in this module knows when a Sortie, Downtime or Scene begins, so no tracked resource ever resets itself — the player clears it. This covers moves' `uses` checkboxes, Astir Parts' Expended, equipment's `spent` tags, Potions, Cause Factions' flags, and the Advancement checklist (which grants nothing). It's cheap bookkeeping that saves eyeballing a text block during play, not a rules engine.
- **Catalog in code, keys on the actor.** `MOVE_POOLS`, `EQUIPMENT_TAGS`, `ASTIR_PART_CATALOG`/`ASTIR_MOVE_CATALOG`/`ASTIR_WEAPON_CATALOG` hold the definitions; the actor stores only the keys it picked, so edited rules text reaches existing characters, and a `resolve*` helper drops keys that no longer resolve (`resolvePlaybookMoves`, `resolveEquipmentTags`). `EQUIPMENT_CATALOG` is the one deliberate exception — snapshotted on pick, not referenced (see Equipment).
- **Derive fresh every render, never persist.** `_conflictTier`, `equipmentValue`, a weapon's or Part's Tier, and `advancements.topCount` are all computed in `getData` so they can't drift out of sync with what they derive from.
- **Behaviour that depends on actor state goes in the sheet, not the data.** A move / part / tag definition is static data. When behaviour varies per character, put a declarative flag on the object and evaluate it generically in `PlaybookActorSheet` — `usesWeapon`, `requiresChannelDisabled`, `forcesDesperationAtMaxPerils`, `grantsGuided`, `grantsChannelOnAnyMove`, `regainPowerOnDoubles` and every other Astir Part flag work exactly this way.
- **Templates and CSS are invisible to the test suite.** `renderTemplate` is stubbed globally in `tests/setup.js`, and `lint-staged` only runs ESLint on `.js`. Handlebars syntax errors, wrong `../` scope inside a nested `{{#each}}`, and every styling regression sail past a fully green `npm run test:coverage`. Anything touching `.hbs` or `.css` has to be eyeballed in a real Foundry client. `npx handlebars <file>.hbs -f /dev/null` (the `handlebars` npm package, fetchable via `npx` without adding it as a dependency) will at least catch a syntax error — unbalanced `{{#if}}`/`{{#each}}`, a stray `{{/each}}` — without needing a running client, but it cannot catch a wrong `../` scope or any other data-binding mistake, since it never evaluates against real data. `loadTemplates` is also invisible in the same way: `tests/setup.js` stubs it as a no-op, same as `renderTemplate`, so a call added to `scripts/main.js`'s init hook only proves it *was called*, never that the partial paths it lists actually resolve or render — that part is still client-only.

## Domain conventions
- "Playbooks" are always player-controlled Actors (type `character`), never Items. This differs from the baseline PBTA system, where a playbook is normally an Item of type `playbook` that gets applied to a blank character actor. In this module, dragging a playbook out of a compendium should produce a ready-to-play character actor directly — see `src/packs/basic-playbook-scout/` for the pattern (an Actor document with `system.details.callsign` added so players can also record a callsign alongside the actor's native name/image).

Domain-specific conventions live in `docs/domains/`, one file per area — read the relevant one
before touching that area's code:
