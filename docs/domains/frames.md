# Astir & Ardents

### Astir
- An Astir lives at `system.attributes.astir` on the playbook actor itself (nullable — `null`/absent means "no Astir"), not as its own document. `scripts/frames/astir.js` is the barrel for this domain's whole catalog+logic split — `ASTIR_PART_CATALOG` lives in `astir-parts.js`, `ASTIR_MOVE_CATALOG` in `astir-moves.js`, `ASTIR_WEAPON_CATALOG` in `astir-weapons.js`, the Power-pool math in `astir-power.js`, and the async-dialog pickers in `astir-pickers.js` — but every name below is still reachable from `astir.js` itself, re-exported (see claude.md's "Code organization"). Astir Parts read as moves (same `traits`/`description`/`uses` shape as `BASIC_MOVES`) and fold into the Moves tab's "Astir Moves" group alongside the Astir's one unique Move.
- **A part's or Astir weapon's benefits only apply while the Astir specifically is the mounted frame.** Since Ardents exist, `piloted` is not a single Astir-only boolean: `_mountedFrame()` returns whichever one frame (the Astir, keyed `"astir"`, or one Ardent, keyed by its stored id) currently has `piloted: true`, an invariant enforced by the single write path `_setMountedFrame`. A player isn't always in a frame, so every frame's Piloted checkbox starts unchecked, and every part-derived effect reads `_mountedParts()` (the mounted frame's own installed parts, `[]` when nothing is mounted) rather than checking "is it the Astir" directly. The whole Astir Moves group gets `gated: true` unless the Astir is mounted, as do Astir weapons' quick-roll buttons (a separate `astirWeaponMoves` mapping in `getData`, so ordinary weapons are unaffected). Managing the loadout itself — Parts, the Astir Move, Astir weapons, and the base Tier/Core/Approach/Power/Overheating fields — is **not** gated.
- Every part-specific mechanic is a declarative flag evaluated generically in the sheet (see Recurring conventions). Flags are read off the actor's *installed* parts (`_astirParts()`) for display, but the mounted frame's own (`_mountedParts()`) for any actual effect — the Parts list still needs to show installed-but-inactive parts when nothing is mounted.
- **Spell Routines' Guided grant is scoped to one player-chosen move, not every move.** `grantsGuided: true` stays a flag on the part, but `_rollMove` (`move-roll-mixin.js`) only sets `guided` when the rolled move's key matches `system.attributes.guidedMoveChoices.<partKey>` — a dropdown rendered on the part's own row in both the regular and Extra Parts lists (`astir-mixin.js`'s `_guidedMoveOptions`/`_onGuidedMoveChoiceChange`), offering every move currently rendered anywhere in `moveGroups` that's actually `rollable` — Guided only ever fires inside `_rollMove`, so an activatable/summonable move (or Plan & Prepare's `variableDiceRoll`, its own separate pipeline) is excluded from the list rather than offered as a choice that would silently never trigger. Classical Spellcasting's own "choose a Basic Move" grant (see Moves docs) is the same "declare a choosable field, store the choice keyed by the granting entry's own key, resolve generically" shape, just keyed by move rather than by part.
- **Every Active part gets a manual `uses: [{ key: "expended", label: "Expended" }]` checkbox** — Subsystems' own rules text ("spend 1 Power to re-activate an expended Astir part") already assumes any Active part can become expended, so this reuses the generic `uses` mechanism with no new rendering code. A part with an Activate button (`showsReadTheRoomQuestions`) or a roll-dialog spend auto-checks it when used; every other Active part is toggled by the player. `partType: "Active" | "Passive"` is display-only, a badge in the Parts list — it drives no behavior.
- **`ASTIR_MAX_PARTS` (2) caps the Astir's regular Parts pool**, enforced by `_onAstirPartAdd`'s guard-and-warn and reflected in `getData`'s `partsFull` flag, which hides the Parts section's Add button once reached — the exact `ARDENT_MAX_LOADOUT` shape below, just for the Astir's own Parts. Extra Parts remain uncapped, matching the Extra-pool design documented later in this file (the "uncapped loadout pool" bullet).
- **Artifact is an ordinary `grantsRollModifier` entry**, the same mechanism every other advantage/effect-granting move or part uses (see the Moves docs' Roll Modifiers section) — unscoped (no `moveKeys`, so it's offered on every move's roll dialog, matching its "before or after the roll" rules text) and gated by `costsUse: "expended"`, which reads/writes the same `moveUses.<partKey>.expended` field the Astir Moves group's own manual checkbox toggles, so both entry points land on one shared state. Its `label` ("Advantage from Artifact") is what the dialog's Roll Modifiers section shows; the part's own rich-text `description` stays separate from the entry's own short plain-text `description`, since a compact dialog row can't render multi-paragraph HTML.
  - **A part whose rules text is a manual adjustment must not carry a `grantsRollModifier` entry with none of `effect`/`advantage`/`reminderOnly` set.** Warding has an Expended checkbox like any other Active part but no `grantsRollModifier` entry at all — Artifact itself used to carry a bespoke `spend` field with the same failure mode (an entry offered in every roll dialog whose checkbox did nothing when checked), before that mechanism was retired in favor of `grantsRollModifier`. Warding's Expended checkbox is deliberately not gated on the Astir being piloted, so it stays usable any time.
- **An Astir weapon picked from the catalog (`_onAstirWeaponAdd`) has its Kind/Tier/Range/Tags permanently locked** (`configureEquipment`'s `lockTags` option — see docs/domains/equipment.md's "Equipment" notes for the full budget/lock rule and provenance-flag design); `.astir-weapon-add` (`_onAstirWeaponCustomAdd`) is a separate, catalog-free custom-creation button next to the existing "O" picker, subject instead to the "tags sum to 0 or less" budget rule.
- **An Astir Move or Astir Weapon catalog entry can require an installed Astir Part via `requiresParts: [partKey, ...]`**, enforced by `unmetPartRequirements`/`partRequirementTooltip` (`astir.js`) — the exact `requiresMoves` mechanism above, mirrored for Astir Parts instead of moves. `astirMoveSections`/`chooseAstirMove` and `chooseAstirWeapon` all take an `installedPartKeys` param and gate their picker options the same way (visible but disabled, with a tooltip) rather than filtering them out. The four Familiar Astir weapons (`requiresParts: ["astir-part:familiar-matrix"]`) are the first real content; `ASTIR_MOVE_CATALOG`'s one placeholder entry carries none yet, so the mechanism there is ready but unexercised until real Astir Moves are transcribed.
- **`rollMove` returns `{ message, dice }`, not just the `ChatMessage`** — `_rollMove` needs the dice breakdown to check Flourish Component's regain-Power-on-doubles (`roll-effects.js#rolledDoubles`, true when the two *kept* dice match) without `moves.js` needing to import `astir.js`.
- **Weapon Conduit's "+2 Power towards weapons only" is a second, entirely separate Power pool** (`astir.weaponPower`, max via `astirMaxWeaponPower`), not a restriction on the main one — nothing spends Power on weapons yet, so it's tracked exactly like the main Power meter (manually stepped, clamped to its derived max on every Part/Astir-weapon change, hidden by the template whenever its max is 0).
- **A Drain tag (`drain-1`/`drain-2`/`drain-3`) on a weapon actually mounted on the Astir (`kind: "weapon"`, `astir: true`) lowers Power for real** — `astirWeaponDrainTotal` sums it, and both `astirMaxPower`/`astirMaxWeaponPower` take the actor's equipment array (not just its Parts) to fold it in. Drain is paid out of the Weapon Power pool's capacity first (that pool's whole purpose); only the remainder reduces main Power (see the shared private `splitWeaponDrain`). A mundane (Foot-scale) weapon's or gear's Drain is inert — an `astir: true` entry is only ever managed from the Astir tab, so its presence in the equipment array already *is* "mounted," with no separate equipped/carried state. Unlike Part cost, this reduction is **not** floored at `ASTIR_POWER_MIN`: a heavily-Drained loadout can legitimately push max (and current) Power negative.
- **An Astir with negative Power can't be piloted.** `_astirPowerUpdates` (shared by the Part and Astir-weapon handlers) re-clamps `power`/`weaponPower` to their recomputed max after any change and forces `piloted` off with a `ui.notifications.warn` the moment that clamp goes negative while piloted; `_onAstirPilotedToggle` mirrors the check to block manually re-checking the box. `getData`'s `power.negative` flag drives a persistent on-sheet indicator as the non-toast counterpart.
- **Alchemical Suite's Potions** (`astir.potions.{red,blue,yellow}`) are granted — 1 of each color, all three at once — by the Controls tab's Refresh Sortie button (`_onRefreshSortie`, gated on `grantsPotionsOnRefreshSortie`), not by rolling any particular move. Each color is a spent boolean, not a count (max 1 by design, matching the rules text's "take 1 of each"), toggled via a freely reversible checkbox on the Astir tab (`_onAstirPotionToggle`) — the same manual-tracker shape equipment's `spent` tags and moves' `uses` checkboxes already use. Blue and Yellow are additionally consumable from the Roll Modifiers section of the move-roll dialog (advantage on the next Weave Magic / confidence on the next Exchange Blows or Strike Decisively); Red has no move tie-in in this module and is spent only via its own checkbox.
- **Complex Spellwork's Director-assigned -1 to -4 Power cost is pinned to a fixed `powerCost: 1`**, with the rest left as descriptive text — a catalog entry can only carry one fixed number, and a variable-cost-at-pick-time flow was explicitly descoped.
- **Resistance Charms and Transmutation Link are pure prose** — a Danger-source downgrade system and aerial/aquatic tags don't exist anywhere in this module.

### Ardents
- **An Ardent is a cheaper, more limited pilotable frame than the Astir** — no Power, no Core, no unique Move, Tier 2–4 (defaulting to 2, versus the Astir's 3–4 defaulting to 3), an Approach picked freely from the full list rather than a Core-narrowed pair, and a combined parts+weapons loadout capped at `ARDENT_MAX_LOADOUT` (2). Unlike the Astir (at most one per actor), a character may have **any number** of Ardents, and may have both an Astir and Ardents at once — but **only one frame total may be mounted at a time**, enforced by `_setMountedFrame`. They live at `system.attributes.ardents`, an array parallel to the Astir's singleton object — see `scripts/frames/ardent.js`.
- **Ardents have no catalog of their own.** `ardentParts()`/`ardentWeapons()` are pure filter *functions* evaluated fresh against the live `ASTIR_PART_CATALOG`/`ASTIR_WEAPON_CATALOG`, never a parallel list that could drift, and they return the exact same object references (not copies), so editing a part's rules text reaches Ardents automatically. A part is Ardent-eligible unless it carries `powerCost` or `weaponPowerBonus`; a weapon is eligible unless it carries a Drain tag (`DRAIN_GROUP`) — an Ardent has no Power pool for any of those to act on. That's the mechanical translation of "Ardents can't use parts/weapons with the Drain tag": a part's Power cost is encoded as `powerCost` here, not a literal tag, so the exclusion is a predicate over that field instead. **A new part or weapon is therefore Ardent-eligible by default** — it only ever needs to be *excluded* by one of those flags, never opted in. The pickers (`chooseAstirPart`/`chooseAstirWeapon`) take an optional `{ title }` override so the Ardent add flows reuse the same dialogs against the filtered catalogs rather than a second implementation.
- **`system.attributes.ardents` entries only ever carry `{ id, name, approach, tier, piloted, parts }`** — no `core`, `power`, `weaponPower`, `overheating`, `img` or `move` (see `buildArdent`). Because Alchemical Suite (`powerCost: 2`) can never be Ardent-eligible, an Ardent can never grant Potions; Standardised Parts (no `powerCost`) *is* eligible, so an Ardent can still grant a Bonus Downtime Tokens pool (see "Adding move content" below), shared across every frame it's installed on (Astir or any Ardent) the same way a part's Expended checkbox already is (see the next bullet).
- **An Ardent's weapons are ordinary `system.attributes.equipment` entries flagged `ardent: "<ardentId>"`** — the direct parallel to an Astir weapon's `astir: true`, managed only from that Ardent's own section via `configureEquipment`'s `ardentWeapon` option (hides Kind and Tier like `astirWeapon`, but never renders Drain's checkboxes). `_equipmentEntry`'s `frame` parameter (generalized from an Astir-only `astir` parameter) resolves such an entry's Tier from whichever object is passed in; both render Astir Scale, since an Ardent is Astir-scale too. Deleting an Ardent cascades to drop every weapon it owns, as `_onAstirDelete` already does for the Astir.
- **Both baseline Ardent weapon flows (`_onArdentWeaponAdd`, and Commander's `_onArdentFeatureWeaponAdd`) lock their picked entry's Kind/Tier/Range/Tags permanently** the same way `_onAstirWeaponAdd` does (`lockTags`, `catalogSource: true` — see docs/domains/equipment.md's "Equipment" notes). `.ardent-weapon-add` (`_onArdentWeaponCustomAdd`) is a catalog-free custom-creation counterpart to `_onArdentWeaponAdd` only, subject instead to the "tags sum to 0 or less" budget rule — the Commander Feature flow deliberately has no such counterpart, since it draws from a small, curated, separately-capped pool by design.
- **`_weaponFrameId(entry)` generalizes the old Astir/mundane piloted-boolean split** to a three-way (or more) frame-ownership check: `"astir"` for an `astir: true` entry, the Ardent's own id for an `ardent: "<id>"` entry, `null` for a mundane weapon. A weapon is offerable (in `_onMoveRoll`'s chooseWeapon prompt, in `_equipmentSpends`, and via its own quick-roll button) exactly when its frame id matches the mounted frame's id (`null` when nothing is mounted, which is also what a mundane weapon compares against) — this is what keeps mundane, Astir and each Ardent's weapons mutually exclusive with no special-casing per kind.
- **A part installed on both the Astir and an Ardent shares one Expended checkbox.** `moveUses` is keyed globally by part key, not per-frame. Accepted as-is: only one frame is ever mounted at a time, and it's already a manual tracker.
- **Mount Up prompts via `ardent.js#chooseFrame`** (mirroring `chooseCarrier`'s labelled-button Dialog) only when the character has more than one unmounted frame; with exactly one, `_onMountUp` mounts it directly. Dismount always clears whichever frame is currently mounted, if any.
- **The Commander playbook's Custom Ardent additionally draws from a second, Commander-exclusive catalog — `ARDENT_FEATURE_PARTS`/`ARDENT_FEATURE_WEAPONS` in `scripts/frames/ardent.js`** — deliberately *not* folded into `ASTIR_PART_CATALOG`/`ASTIR_WEAPON_CATALOG`: those feed `ardentParts()`/`ardentWeapons()` above, which every playbook's Ardent draws from, and Ardent Features must never leak into another playbook's Ardent (or into an Astir's own part/weapon picker — they're mundane military hardware, not Channeler tech). This gives a Commander's Ardent **two independent, separately-capped loadout pools** rather than one raised `ARDENT_MAX_LOADOUT`: the ordinary baseline pool (still capped at 2, exactly like any other playbook's Ardent) plus a Feature pool of its own (`ardentFeatureMax` — base 3, +2 once Requisitions is picked via that move's own `ardentFeatureBonus` flag, summed the same way `tierBonus`/`downtimeTokensMax` are above). `ardentBaselineLoadoutCount`/`ardentFeatureLoadoutCount` (`scripts/frames/ardent.js`) classify each installed item into the right pool and are what the baseline Add Part/Add Weapon handlers check instead of the old combined `ardentLoadoutCount` (kept, unchanged, for callers that never see a Feature-flagged item — the two functions agree exactly whenever nothing is Feature-flagged).
- **Classifying an installed item as baseline vs. Feature relies on two different mechanisms, because parts and weapons are stored differently.** A part is just a catalog-key reference (`ardent.parts`, never edited after being picked — see `isAceFeaturePart`, a plain catalog-membership check), so which catalog it came from is always recoverable. A weapon is not: picking one from a catalog is a snapshot, not a reference (see Equipment below) — the saved entry carries no `catalogKey`, so its source catalog can't be recovered after the fact. Commander's Feature-weapon add flow (`_onArdentFeatureWeaponAdd`) therefore stamps the saved entry with an explicit `commanderFeature: true` flag at add-time — the same "flag the entry, since origin can't be derived later" move `astir: true`/`ardent: "<id>"` already make for frame ownership — and every consumer (`ardentFeatureLoadoutCount`, `getData`'s baseline/Feature weapon split) reads that flag rather than trying to infer origin.
- **A new Ardent-part-shaped catalog has to be folded into every surface that resolves parts by key, not just the ones that render them.** `ARDENT_PART_CATALOG` (`scripts/playbook/playbook-actor-sheet.js`, `= [...ASTIR_PART_CATALOG, ...ARDENT_FEATURE_PARTS]`) is the catalog every `resolveAstirParts` call on an Ardent's own parts now defaults to — `_mountedParts()`, the per-Ardent Moves group in `getData`, and the Feature-pool split in `getData` all use it instead of the plain `ASTIR_PART_CATALOG` default. Missing any one of these doesn't error — `resolveAstirParts` just silently drops a key it can't find, so an installed Ardent Feature part would quietly vanish from whichever surface still used the narrower catalog. `ALL_MOVES` needs the same treatment for a different reason: it's not a display list, it's the flat key-lookup table `_onMoveRoll`/`_onMoveActivate`/`_onMoveDescription`/reroll/`_refreshPeriod`'s uses-clearing walk all search by key — a part catalog left out of it can still *render* (if the `ARDENT_PART_CATALOG` fix above is in place) but its Roll/Activate button, and Refresh Sortie's clearing of its `uses` checkboxes, will silently no-op.
- **Both the Astir and every Ardent additionally carry a third, uncapped loadout pool — Extra Parts/Extra Weapons** (`astir.extraParts`/`ardent.extraParts`, plus equipment entries flagged `extra: true` alongside their existing `astir: true`/`ardent: "<id>"`) — drawn from the exact same catalogs as the regular pool (`ASTIR_PART_CATALOG`/`ASTIR_WEAPON_CATALOG` for the Astir, `ardentParts()`/`ardentWeapons()` for an Ardent) and behaving identically to a regular part/weapon while installed, but scoped to a single Sortie: Refresh Sortie clears it by *removing* every entry outright, not just resetting a `uses` checkbox like the manual trackers above. Unlike the Commander-exclusive Ardent Feature pool, Extra is available on every playbook (including the Astir, which Ardent Feature never was) and has no cap of its own — `_onAstirExtraPartAdd`/`_onArdentExtraPartAdd` skip the `ARDENT_MAX_LOADOUT`/Power-cost gating their regular counterparts apply. `astir-mixin.js`'s `_astirPartKeys(astir)` and `ardent-mixin.js`'s `_ardentPartKeys(ardent)` union each frame's regular + Extra keys, and every "what's currently installed" call site (`_astirData`'s Power/Weapon Power max, `_astirParts()`, `_frames()`'s own `parts`, the per-Ardent Moves group, `_bonusDowntimeTokenKeyedSources`, the Bound/Downtime Ally Power-refund calls in `summoner-mixin.js`) reads through one of those two helpers instead of the raw `.parts` field, so Extra folds into Power cost, `requiresParts` checks, and mounted-frame effects for free — only the *display* split (regular vs. Extra as two separate template sections) resolves `.parts`/`.extraParts` separately.
- **Commander's Ace Crew roster** (`system.attributes.aceCrew`, named crew members with an adjective each) reuses `scripts/world-actors/entry-list.js`'s pure CRUD helpers directly, the same functions the World actors section above describes as "shared by every world actor list" — `PlaybookActorSheet` isn't a `WorldActorSheet`, so its three handlers (`_onAceCrewAdd`/`_onAceCrewRemove`/`_onAceCrewFieldChange`) are thin hand-wired wrappers around those same pure functions rather than a second CRUD implementation or a reason to make `PlaybookActorSheet` extend `WorldActorSheet`.
- **Gating a template section to one specific playbook computes a boolean in `getData` (`data.isCommander`), not a Handlebars equality helper** — this module registers no custom Handlebars helpers, so `{{#if}}` alone can't compare `system.playbook.slug` against a literal string. `isCommander` (gating the Ace Crew section and the Commander-only Add-Ardent-Feature controls) is the first instance of this pattern and the template for any future playbook-exclusive section.
- **The Equipment tab's own Astir Weapons/Ardent Weapons sections are additionally gated on that frame being the currently mounted one** — `_equipmentData` (`equipment-mixin.js`) filters `astirWeapons`/`ardentWeapons` down to whichever frame `mountedFrameId` names, mirroring `_weaponFrameId`'s existing gating of quick-roll buttons/spends/narrative tags above, so an unmounted frame's weapons disappear from that tab entirely rather than just having their buttons disabled. The same weapons still surface unconditionally on the Astir/Ardents tab's own per-frame list (`data.astir.weapons`/`data.ardents[].weapons`), since that's the loadout-management view — see the Astir section's "managing the loadout itself ... is not gated" bullet above. This is a distinct sense of "mounted" from that same Astir section's Drain bullet, which uses "mounted on the Astir" to mean *installed* (`astir: true`), not *piloted*.
