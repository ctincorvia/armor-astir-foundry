# Equipment

### Equipment
- Equipment can be custom-made from scratch, **or** picked as a starting point from `EQUIPMENT_CATALOG` — either way it goes through the same `configureEquipment` editor. Picking a catalog item is a **snapshot, not a reference**: `_onEquipmentCatalogAdd` opens `chooseEquipmentCatalogItem(kind)` then passes the template straight into `configureEquipment` as `initial` (same as editing an existing entry), so the player can still rename it or change tags before saving. The saved entry carries no `catalogKey` and no link back — deliberately unlike `playbookMoves`. Equipment already had to stay freely editable for the custom-made path, and a second "linked but also editable" schema would only exist to answer a question ("has this diverged from its source?") nothing in this module asks.
- **A custom-made weapon or gear item's tags must sum to 0 or less** — `configureEquipment`'s pre-existing `maxTagValue` mechanism (below), simply passed as `maxTagValue: 0` by every custom-creation call site (`_onEquipmentAdd`, `_onAstirWeaponCustomAdd`, `_onArdentWeaponCustomAdd`). Valuable/Treasure count at face value toward this rule — unlike starting-gear's own, separate `excludedTagKeys` exclusion (below), which is untouched. Starting-gear equipment and Carrier weapons are exempt (Carrier already had its own per-slot `maxTagValue`, unchanged). **A catalog-picked item is locked instead of budget-capped**: `configureEquipment`'s `lockTags` option renders Kind/Tier/Range/Tags visible but disabled from the moment it's picked, through every future edit — only Name and Description stay editable. Two optional booleans persisted on a saved entry drive `_onEquipmentEdit`'s per-entry choice between the two: `catalogSource: true` (set by every catalog-pick chain: the generic catalog, and the Astir/Ardent/Ardent-Feature weapon catalogs) locks it; `startingGear: true` (set by `_onStartingGearAdd`, both granted/picked pool items and the pool's own custom weapon) exempts it from both rules permanently. A pre-existing entry (from before this change) carries neither flag, so the default differs by domain: an Astir/Ardent weapon's only prior path was a catalog pick, so a missing `catalogSource` there defaults to locked (`entry.catalogSource !== false`) — a new custom Astir/Ardent weapon must therefore persist `catalogSource: false` explicitly, not just omit it, to opt out; plain equipment could always have been either catalog-picked or hand-authored, genuinely indistinguishable after the fact, so a missing `catalogSource` there defaults the other way, to unlocked-but-now-budget-capped on its next edit.
- **The Astir and Ardent tabs each have their own custom-weapon creator** (`.astir-weapon-add` → `_onAstirWeaponCustomAdd`, `.ardent-weapon-add` → `_onArdentWeaponCustomAdd`) alongside their existing catalog-only "O" picker — mirroring the Equipment tab's own "+"/"O" pairing. Both skip the catalog-pick step entirely and open `configureEquipment` directly with `maxTagValue: 0`, saving with `catalogSource: false`. The Commander-exclusive Ardent Feature weapon flow (`_onArdentFeatureWeaponAdd`) deliberately has no custom-creation counterpart — it draws from a small, curated, separately-capped pool (`ARDENT_FEATURE_WEAPONS`) by design, and opening it to free-form creation would undercut that curation.
- **Tags** (Blitz, Defensive, …) are the separate `EQUIPMENT_TAGS` catalog, and an entry stores only tag **keys**. Unlike `EQUIPMENT_CATALOG`, tag keys stay live-referenced even after a catalog-picked item is saved — only the item template itself (name/description/kind/scale/which tag keys) is snapshotted, not the tags' own rules text. `tier` is never part of that snapshot at all — see the Tier note below.
- **`exclusiveGroup`** marks a tag as belonging to a mutually-exclusive set. `DRAIN_GROUP` (Drain 1/2/3, values -1/-2/-3) makes a tag's checkbox behave like a radio button within the group — `configureEquipment`'s render wiring unchecks every other tag sharing the same `exclusiveGroup` the moment one is checked, resolved off the `tags` array already in scope rather than new template data attributes. It exists purely so an item can't carry more than one Drain tier at once; it is *not* required (an item may carry no Drain tier), and since each tier carries a real value rather than being a pure classifier, it still counts against `MAX_TAGS`.
- **`WEAPON_RANGE_GROUP`** (Melee/Ranged/Sniper, all `value: 0` — a pure classifier, not a Value modifier) renders as its own native `<input type="radio">` group in `equipment-editor.hbs`, not as checkboxes in the tag list, since — unlike Drain — a weapon must always carry exactly one. The radio group always has one option pre-checked: whichever range tag `initial` carries when editing, or Melee otherwise, mirroring `weapon-picker.hbs`'s hardcoded Unarmed default. `configureEquipment`'s Save-time check for a missing range is now a defensive fallback rather than the primary safeguard.
  - **Why it can't be validated at Save alone:** Foundry's `Dialog` always closes after a button callback runs, whatever the callback does. A player who forgot to pick got a warning toast *after* the dialog — and everything else they'd typed — was already gone, with no way to recover it. Prefer a defaulted native control over Save-time validation anywhere in a Dialog for this reason.
- **`MAX_TAGS`** (4) caps how many *regular* tags any entry — weapon or gear — can carry, enforced at `configureEquipment` Save. Melee/Ranged/Sniper never count against it (a classifier pick, not a regular tag) and, since they're never rendered as checkboxes, that's structural rather than something Save has to filter out. `DRAIN_GROUP` membership does count.
- Weapons and gear share **one array**, `system.attributes.equipment`, distinguished by a `kind: "weapon" | "gear"` field rather than two separate arrays — add/edit/remove and tag resolution are identical either way, and only the sheet's render (and the tab's separate headers) needs to tell them apart. Only weapons carry `scale` (`WEAPON_SCALES`, purely descriptive — nothing enforces who may wield which, since Astirs aren't their own documents).
- **No weapon stores its own Tier — it's derived from whoever is wielding it, computed fresh in `_equipmentEntry`** (see Recurring conventions). An Astir or Ardent weapon inherits its owning frame's `tier`, passed in as `_equipmentEntry`'s `frame` argument. A mundane weapon instead inherits `_conflictTier().base` — the character's own on-foot Tier — rather than `.effective`, since `.effective` reads as whichever frame is mounted, meaningless for a personal weapon that's already gated off entirely while mounted (see `_weaponGateTooltip`). `configureEquipment` hides its Tier `<input>` for every weapon flow (`hideTier: !carrierWeapon`) except the Carrier's, which has no Tier of its own to inherit and so remains the one flow storing a real `tier` (always `TIER_MAX`). `EQUIPMENT_CATALOG` templates and starting-gear pool items never carry a `tier` field either, for the same reason.
- **Astir/Ardent Parts likewise carry no `tier` of their own** — `getData` derives a display-only Tier badge from the owning frame, purely for that tab's Parts list. Nothing reads a part's Tier mechanically; it's reference only, mirroring `partType`'s badge.
- A tag with a `spend` field (e.g. Blitz: `{ period: "Scene", effect: "confidence" }`) is offerable from the move roll dialog. `_equipmentSpends` collects every unspent spendable tag and passes it to `configureMoveRoll`'s `equipmentSpends` option — **not filtered by move or trait beyond the weapon-scoping below**, the same non-enforcement stance `MOVE_POOLS` takes on pool restrictions. `spend.effect` only ever sets an existing `roll-effects.js` Effect state; when the roll already has a `lockedEffect` (Bite the Dust at max Perils), offered spends render disabled rather than being silently consumed for nothing.
- **A "narrative tag" (Impact, Distinct, Bulky, Cursed, Melee/Ranged/Sniper, the five Approach tags, …) is any tag with no codified mechanic — no `spend`, `forcesEffect`, `reroll`, or `guided`, and its `exclusiveGroup` is not `DRAIN_GROUP`.** `_narrativeWeaponTags(weapon)` collects these (same frame/`disabled`/scoped filtering as `_equipmentSpends` immediately above, *except* unscoped — `weapon === undefined`, every non-`usesWeapon` move — drops every weapon-kind entry outright rather than leaving them unfiltered; a weapon's narrative tag is pure flavor about that weapon, unlike a spend's actionable-on-any-roll resource, so it has nothing to say about a roll that never involves one. Gear stays unfiltered either way, same as `_equipmentSpends`) and passes them to `configureMoveRoll`'s `narrativeTags` option, rendered read-only in the roll dialog's own "Tags" section — this is the definition other docs/comments should point back to rather than restate. `WEAPON_RANGE_GROUP` (Melee/Ranged/Sniper) and the Approach tags both carry an `exclusiveGroup`/mechanical-looking shape but no actual codified effect, so they're included; Drain 1/2/3 (`exclusiveGroup: DRAIN_GROUP`) is excluded even though it also has no `spend`, since it's wired into the Astir Power calculation elsewhere — a real effect, just not a spend.
- **A spent tag's state lives nested on the equipment entry itself** (`entry.spent: ["blitz"]`), not in a parallel keyed map like `system.attributes.moveUses`. `moveUses` can key by move key because move keys are stable and global; equipment ids are per-actor and disposable, so a parallel map would orphan entries on delete and would need carrying separately through the playbook-swap preservation below.
- **A playbook move can grant a fixed piece of equipment the moment it's picked** (`grantsEquipment` — see `docs/domains/moves.md`'s "Adding move content" table, Cantrips' Classical Spellcasting is the reference example) — resolved through the same `_startingGearEntry` snapshot a starting-gear pick already gets (`startingGear: true`, so it's never tag-locked or budget-capped), just triggered from `move-tracking-mixin.js`'s `_onPlaybookMoveAdd` instead of character creation.
- **A move can add tags to weapons it doesn't own, two ways** (see `docs/domains/moves.md`'s "Adding move content" table for both): `grantsWeaponTags` folds a fixed tag set onto *every* weapon uniformly (The Attendant's Signed & Sealed); `grantsWeaponTagChoice` narrows that to *one specific granted weapon*, matched by `name`, with a per-actor chosen tag instead of a fixed set (Cantrips' Advanced Evocation, targeting Classical Spellcasting's own granted Hand-casting). Both resolve live in `equipment-mixin.js`'s `_weaponTagKeys` and are never written onto the target's own stored `tags` — since `grantsWeaponTagChoice`'s link is by `name`, not id, renaming the granted weapon breaks it, the same fragility `grantsEquipment`'s own dedupe-by-name already accepts.
- **Equipment is the one exception to `swapActorPlaybook`'s wholesale `system.attributes` replace.** Playbook moves are meant to clear on swap (matching Bite the Dust's own "you do not gain its starting equipment" text about the *new* playbook), but existing equipment is the character's, not the old playbook's, so `swapActorPlaybook` reads it off the actor first and merges it back onto the new attributes.
- **A move flagged `usesWeapon: true`** (Exchange Blows, Strike Decisively) can only ever be wielding one weapon. Unlike every other move, its roll dialog itself offers the weapon choice — `_onMoveRoll` gathers the actor's candidate weapons (filtered to the mounted frame, `!disabled`, plus any Fire Support Carrier weapons) and hands the whole array (possibly empty) to `_rollMove`, which dispatches on `Array.isArray(weapon)` to `_rollMoveWithWeaponChoice`. That method precomputes one **bundle** per candidate — `null` first for the always-offered `UNARMED` sentinel, since both moves' text covers unarmed/verbal conflict — via `_weaponRollBundle(move, weapon, ...)`: each bundle carries that weapon's own Trait block (the Familiar +CHANNEL swap, if any), a read-only weapon card, `equipmentSpends`, `rollModifiers`, and `lockedEffect`/`guided`. The bundles are passed to `configureMoveRoll` as `weaponBundles`, which renders one panel per candidate (toggled by a `<select name="weapon-select">`, no re-render — see `move-dialogs.js`) inside the single merged dialog, replacing the old separate `chooseWeapon` prompt entirely. Once the dialog resolves, `config.weaponId` (the selected panel's own weapon id, or `UNARMED`) resolves back to the real chosen weapon, and the rest of `_rollMoveWithWeaponChoice` mirrors `_rollMove`'s own single-weapon tail (spend-marking, reroll, the chat card's `weaponLabel`/`narrativeTags`) exactly, just reading that resolved weapon. `_equipmentSpends(lockedEffect, weapon)` is still the mechanism scoping the offer: passing anything other than `undefined` (including `null` for Unarmed) excludes every *other* weapon's tags, while gear's tags are never filtered — a character can plausibly have several relevant pieces of gear active, just not two weapons in hand. With no weapons at all, the dialog still offers Unarmed as the only candidate — there's simply nothing else to choose between. Every non-`usesWeapon` move leaves `weapon` `undefined`.
- **Each weapon in the Equipment tab also gets its own quick-roll button per `usesWeapon` move** (`data.equipment.weapons[].weaponMoves`, built once in `getData` via `_moveGroupMoves(WEAPON_MOVES)` and attached to every weapon entry rather than cross-referenced from a sibling path — see the `../` scoping hazard in Recurring conventions). Clicking one (`_onWeaponMoveRoll`) skips the `chooseWeapon` prompt, since the click *is* the choice. Both entry points converge on `_rollMove(move, weapon)`.
- **The chosen weapon (or "Unarmed") always reaches the chat card**, even when nothing was spent — `_rollMove` only adds a `weaponLabel` key to `rollMove`'s options when `weapon !== undefined`, so every other move's `rollMove` call is unchanged.
- **Every equipment/weapon card in the app renders through one shared partial**, `templates/shared/equipment-card.hbs` — the Equipment tab's Weapons/Astir Weapons/Ardent Weapons/Gear lists, the Astir tab's Weapons/Extra Weapons, Ardents' Weapons/Extra Weapons/Feature Weapons, and the Carrier's two weapon slots all `{{> "modules/armor-astir/templates/shared/equipment-card.hbs" ...}}` inside their own `{{#each}}` rather than repeating the markup. Three hash-param gates control the per-context controls: `controls=true` shows the Edit/Remove buttons (omitted for read-only lists like the Equipment tab's Astir/Ardent Weapons sections); `disabledToggle=true` shows the Disabled checkbox (omitted for gear, which has no Disabled concept, and for the Carrier, which doesn't offer it as a v1 scope cut); `hideTags=true` suppresses the card's own full tag list entirely — set only by the move-roll dialog (`move-roll-dialog.hbs`), which renders its own separate, narrower "Tags"/"Equipment" sections instead (see the narrative-tag bullet above). `tier`/`scaleLabel` are self-gating (`{{#if}}`) since gear entries simply lack those fields. Add a new weapon list by reusing this partial with the appropriate flags rather than copy-pasting another inline card.
