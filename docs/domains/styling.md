# Sheet Styling

## Sheet styling
This module's CSS is split across several files under `styles/`, all loaded together (see `module.json`'s `styles[]` array) and all styling the same handful of roots: the playbook actor sheet, the three world actor sheets (Carrier/Authority/Cause), every dialog (all carry the `armor-astir` class), and the chat cards (`armor-astir-move-chat` and `armor-astir-downtime-scene-chat`, never nested under `armor-astir`). The files are:

- `tokens.css` — the `--aa-*` custom properties themselves, light values and dark. **Must stay first in `module.json`'s `styles[]` array** — every other file references these tokens and has no fallback if it loads first.
- `sheet-chrome.css` — headers, portrait, name/callsign, header labels/selects, tier readout, status row, the shared bordered-panel treatment, meters, numeric readouts, pip tracks, +/- steppers, the sheet min-width floor.
- `sheet-layout.css` — the sticky Dangers/Tabs columns, Dangers list, Gravity Clocks, generic Clocks, Burdens, tab nav chrome, Astir/Ardent identity sections, tab visibility/scroll overrides.
- `sheet-tabs.css` — per-tab content (Moves, Equipment, Astir/Ardents, Social, Advancement, Downtime, Cosmetic).
- `move-chat.css` — the chat cards.
- `dialogs.css` — every `Dialog`-based picker/editor.
- `world-actor-shared.css` — rules shared by all three world actor sheets (Carrier/Authority/Cause): the entry-list family, entry-counter rows, the crew/tier/entry-list-counter stepper, flag-label checkboxes, etc.
- `authority-sheet.css` — Authority-only rules (Stability track, Division/Pillar cards, kind-select, outcome-text blocks) that don't belong in the shared file since no other world actor sheet uses them.
- `theme-dark.css` — dark-theme overrides for surfaces this module does **not** own (pbta's and core's own elements). **Must stay last.** See "Dark theme" below.

The world actor sheets (`world-actor-shared.css`/`authority-sheet.css`) deliberately duplicate a handful of small rules (steppers, remove buttons, pip tracks) that visually match rules already declared in `sheet-chrome.css`/`sheet-layout.css`, rather than reaching into those playbook-sheet stylesheets to share a selector — see e.g. `world-actor-shared.css`'s own `.crew-step`/`.entry-list-counter-step` comment. None of this is caught by any test — see Recurring conventions.

- **Style against the role tokens, never the gem names.** The palette defines `--aa-moonstone*` / `--aa-amethyst*`, but every rule uses `--aa-primary*` / `--aa-secondary*`, which alias one gem each at the top of the file. Primary = chrome the player acts on (section headers and their underline rules, tab nav, all buttons, hover states); secondary = the player's own tracked state (Spotlight/Gravity Clock pips, numeric readouts, equipment tag labels, row striping). Writing `var(--aa-moonstone)` in a rule works but breaks the abstraction — swapping which gem plays which role is meant to be a few lines' edit, and it has now been done twice: once outright, and once per-theme (the dark theme swaps primary and secondary, see below). `grep "var(--aa-moonstone\|var(--aa-amethyst)" styles/` should only ever match the role mappings in `tokens.css`.
- **`-strong` is the high-contrast member of a family, not a darker one.** These were called `-dark` until the dark theme landed, at which point the name became actively misleading: under the dark theme `--aa-primary-strong` resolves to a *lighter* colour than `--aa-primary`. Whichever direction it points, `-strong` is what a surface that *fills* with a colour must use, never the base (`--aa-moonstone` at full strength is ~2.4:1 under white, well under the 4.5:1 floor). Getting this wrong produced unreadable buttons once already.
- **Never pair a filled `-strong` surface with a literal `#fff`. Use the matching `--aa-on-*`.** This is what makes one `-strong` token work in both themes. 52 of the 85 `-strong` uses in this codebase are *text on the page*, and only 33 are fills — and the two invert in opposite directions: text on a dark page needs a lighter accent, while a fill needs a lighter accent with *darker* ink. Decoupling the ink into `--aa-on-primary`/`-secondary`/`-danger` (plus `--aa-on-status` for the `.move-condition` chips, which share one `color` rule across many different fills) is what lets a single value satisfy both.
- **A new `<button>` rule must set its own `width` (and `flex` if it can end up in a flex row), or Foundry core's global `button { width: 100%; }` (`public/css/style.css`) wins by default.** Every button rule in this codebase so far has declared background/border/padding/font-size but left `width` unset, trusting padding+content to size it — that only works while the button sits alone in a block-level wrapper. The moment such a button becomes a flex item (e.g. placed in a row next to a label so it reads inline instead of stacked), the unset `width` falls through to core's `100%`, and the button balloons to swallow the row while its flex sibling gets squeezed down to a sliver — this is exactly what happened when the equipment editor's "Override Max" button moved into `.equipment-editor-tag-total-row` next to the Total/max readout, hiding the "(max N)" text with no code change to the text itself. This has bitten the project more than once, so it's a checklist item now: any button rule under `styles/` that lives inside (or could ever be moved into) a flex container needs an explicit `width: auto` plus `flex: 0 0 auto`, not just visual sizing left to padding/font-size.
- **Layout rules on a tab must be scoped to `.tab.active`, not `.tab`.** Core Foundry hides inactive tabs with `.tab[data-tab]:not(.active) { display: none }` (in `public/css/foundry2.css`); scoping to `.active` keeps our rule mutually exclusive with core's so there's no specificity fight. Neither pbta nor the sibling Masks module defines a competing `.tab` rule.
- **`.sheet-tabs` must not carry a top margin.** `.sheet-main` lays `.dangers-column` and `.sheet-tabs-column` side by side starting at the same y, so any top margin on the nav drops the tab headers below the Dangers panel's top edge and visibly breaks the two columns' alignment. The panel padding shared by `.traits` / `.spotlight` / `.dangers-column` / `.tab.active > section` is what does the aligning.
- **Rows that pair a variable-length label with fixed controls use grid, not flex + `space-between`.** `.danger-item` and `.move` both use `grid-template-columns: minmax(0, 1fr) auto` so the controls land in the same fixed column on every row (a straight vertical line down the list) and a long label shrinks instead of pushing them out of the container. Both rules carry a comment explaining this; keep it if editing them.
- **Unbounded derived text in the sheet header goes on its own wrapped full-width line (`.header-derived-note`), never inline beside the controls.** The header's Tier and Approach readouts can both be overridden by a mounted frame, and a frame's name is unbounded — for an Astir it literally *is* the Callsign field's own value (`frames-mixin.js`'s `_frames`). Rendered inline they gave `.tier-value`/the old `.approach-effective-note` an enormous min-content width, and since `.sheet-header` is not a `.flexcol`, core's `.flex3 { flex: 3 }` (scoped `.flexcol > .flex3`) never applied to the Name/Callsign stack — leaving it at `flex: 0 1 auto` as the only shrinkable item, so it absorbed the whole overflow and collapsed both inputs to ~3 characters wide. The fix is structural, not cosmetic: `.sheet-header` wraps, the note claims `flex: 1 0 100%`, and `.flex3` carries an explicit `flex: 1 1 240px` so the inputs hold their width regardless of what sits beside them. Keep that basis if adding anything else to the header row, and put any future derived readout on the note line rather than inline.
- **Wrapping optional `{{#if}}` blocks in a flex container is safe even when every branch is false** — Handlebars leaves whitespace inside the wrapper, but whitespace-only text never becomes a flex item, so the container collapses to zero height rather than leaving a phantom gap. `.trait-meters` (Overheating + Power) relies on this; give such a wrapper no margin/padding of its own and leave the spacing on its children.
- **`.quarters-benefit-list`'s list-reset is defined exactly once, in `sheet-tabs.css`, even though two sheets use the class.** The playbook sheet's editable Quarters box renders it as an `<ol>` of checkbox `<li class="quarters-benefit-item">`s, while the Carrier sheet's read-only Quarters rollup renders it as a plain `<ul>` of classless `<li>{{this}}</li>`s — different markup, but the same list-reset styling applies to both, so the rule is shared rather than duplicated. Don't let a future CSS split copy it into `world-actor-shared.css` too — that would just set up a specificity fight between two identical rules.

## Dark theme

Foundry's colour scheme is a **client setting, applied as DOM classes in JS** (`Game#configureUI`, `client/game.mjs`). It is deliberately *not* a `prefers-color-scheme` media query — core resolves "Browser Default" itself and writes a real class. **Match the classes; never write a `prefers-color-scheme` query here**, or it will fire even when the player explicitly picked the opposite theme.

- **Two settings, two selectors, and the difference is the `themed` class.** `core.uiConfig`'s `colorScheme.applications` puts a bare `theme-dark` on `<body>` (sheets and dialogs); `colorScheme.interface` puts `themed theme-dark` on `#interface` and the sidebar tabs (chat). They can legitimately disagree, so scope sheet rules off `body.theme-dark` and chat rules off `.themed.theme-dark`. Both default to `"dark"` on v14 — this module read light-on-dark out of the box before this existed.
- **Nothing theme-scoped matches on v12**, which has no colour-scheme setting and never stamps these classes. v12 keeps the light values verbatim, which is why the floor stayed at 12.
- **Never depend on core's `--color-*` variables.** Every sheet and dialog here is ApplicationV1, and core's own constructor force-feeds those `themed theme-light` — verbatim, *"Force .theme-light for legacy ApplicationV1 instances"* (`client/appv1/api/application-v1.mjs`). So core's **light** variable block applies inside our windows even under a dark body, and no core rule pairs `theme-dark` with `window-app` at all. Anything inherited from core resolves light no matter what the player picked. State absolute values, or route them through an `--aa-*` token.
- **Dark mode is a token-value swap, not a second stylesheet.** `tokens.css`'s dark block redefines the same token names, so every rule in every other file follows for free. Adding a new rule needs no dark-mode counterpart *provided it only uses tokens* — that is the entire payoff of the token layer, and the reason a hardcoded `#fff` in a new rule is now a real bug rather than a style nit.
- **`theme-dark.css` is the exception list, and should stay short.** It holds only rules that exist to win a specificity fight against a stylesheet with no theme awareness of its own — pbta's `.window-content` / `#chat .message` / form-control fills, and core's ProseMirror editors. Each rule records the specificity it has to beat. If you find yourself adding a rule there for an element this module *does* own, the fix belongs in a token instead. Note core's competing rules live in `@layer compatibility`, and unlayered CSS (all of this module's) beats every layered rule regardless of specificity — only pbta's unlayered rules actually need out-specifying.
- **The window header is deliberately dark in dark mode**, rather than following `--aa-primary-strong` the way every other filled surface does. It is by far the largest area this module fills, and a light moonstone title bar on every window is exactly the high-luminance slab a dark UI should not have. It keeps its identity through a moonstone title and bottom rule instead. Every *small* primary fill (buttons, chips, tooltips) stays bright.
- **Verify contrast numerically; nothing in this repo can render a sheet.** The floor is 4.5:1 for text. Every pairing in the dark palette was checked with the WCAG sRGB formula, worst case 5.00:1 (`--aa-danger` as text on `--aa-surface-raised`). If you add or retune a colour, check it the same way rather than eyeballing it — a plausible-looking accent can easily land at 2:1.
- **`tests/theme-dark-css.test.js` is the regression guard, and it is the only CSS test in the repo.** It loads the real stylesheets (in `module.json` order, read from the manifest) into happy-dom alongside verbatim copies of the pbta and core rules they out-specify, then asserts computed colours in both themes. happy-dom resolves `var()`, `:is()`, `:has()` and `:where()` with real cascade semantics, so this genuinely tests the cascade rather than the text of a selector. Add a case here whenever you add a rule to `theme-dark.css` — that file exists *only* to win specificity fights, and a selector that quietly stops matching produces no error anywhere.
- **The reason that guard exists:** the first version of the chat-card rule required `.theme-dark` *on* `#chat`, but core themes `#interface` and only conditionally walks the sidebar tabs. The rule silently never matched, so cards kept pbta's white fill while the text rule beside it — which only needed a themed *ancestor* — correctly went light. White card, near-white text, no error. Reverting the selector in that test reproduces it exactly.
- **Use `background-color` + `background-image`, not the `background` shorthand, when either half comes from a token.** `background: var(--aa-surface) var(--aa-surface-texture)` is valid CSS, but it couples the two: the texture half is `none` in dark mode and a `url()` in light, and one malformed token value invalidates the colour along with it. The longhands are independent and unambiguous.
- **`py .claude/scripts/check_css_tokens.py` catches the one class of error that is otherwise completely silent**: a misspelled `var(--aa-*)`. CSS custom properties fail *invalid at computed-value time* — the declaration doesn't error and isn't even struck through in devtools, it just computes to the property's initial value, so a typo'd background renders transparent and a typo'd colour renders black. Run it after any token work.
