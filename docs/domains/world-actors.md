# World Actors

### World actors
- Beyond player-controlled Playbook actors, this module also has three non-playbook actor kinds representing things in the world: the **Carrier** (the players' moving base), the **Authority** (the empire/oppressor), and the **Cause** (the loosely organized factions opposing it). Each is its own Foundry Actor sub-type — `armor-astir.carrier`, `armor-astir.authority`, `armor-astir.cause` — declared via `module.json`'s `documentTypes.Actor`, sheets in `scripts/world-actors/carrier-actor-sheet.js`/`authority-actor-sheet.js`/`cause-actor-sheet.js`, templates in `templates/*-actor-sheet.hbs`.
- **Why module-declared `documentTypes` rather than pbta's own `other` type + `system.customType`:** the `other`/`customType` route is what pbta's own Actor creation dialog uses, but it requires the type to be registered in `game.pbta.sheetConfig.actorTypes` — an unregistered `customType` makes `PbtaActor#applyBaseTemplate` merge against `undefined` during `_preCreate` and throw, aborting actor creation. Registering properly means taking over `sheetConfigOverride` (what the sibling `masks-newgeneration-unofficial` module does), a much bigger commitment than three simple sheets need. A module-declared sub-type sidesteps pbta's actor-type system entirely: `Actor.TYPES` is `Object.keys(game.model.Actor)`, and Foundry's own world-launch step (`updateActiveDocumentTypes`, in the installed `resources/app/dist/packages/world.mjs`) merges every active module's `documentTypes` into `game.model` *before* pbta's `_preCreate` ever runs.
- **Actor creation is entirely custom, not pbta's dialog.** `registerPlaybookActorCreation` (`scripts/actor-creation.js`) rebinds the sidebar's `.create-entry` button to `onCreateEntryClick`, which calls `chooseActorKind()` — a Dialog offering "Playbook" plus every entry in `WORLD_ACTOR_KINDS` — then either falls into the existing `choosePlaybook()`/`createPlaybookActor()` path or calls `createWorldActor(kind, options)` directly (`Actor.create({ name, type, folder, system: kind.buildSystem() })`). No `PbtaActor.createDialog`/`defaultName` codepath is ever exercised, which also sidesteps its unguarded `game.pbta.sheetConfig.actorTypes[type].label` lookup (would throw for an unregistered type) — safe only because we always supply an explicit name and never call that dialog.
- **`WORLD_ACTOR_KINDS` in `actor-creation.js`** is the single source of truth for the three kinds — `key` (chooseActorKind's dialog button key), `type` (the Foundry Actor type string), `name` (default actor name), `buildSystem()` (returns each kind's starting `system` data fresh per call, so array/object fields are never accidentally shared between actors created from the same kind).
- **`scripts/world-actors/entry-list.js`** holds pure, Foundry-API-free CRUD helpers (`addEntry`/`removeEntry`/`updateEntryField`) over id-keyed arrays — shared by every world actor list: Carrier's Crew Members, Authority's Assets/Actors/Divisions/Pillars, Cause's Factions.
- **`scripts/world-actors/world-actor-sheet.js`'s `WorldActorSheet`** is the base class all three sheets extend. It wires one generic set of handlers against `system.attributes.<list>`, all fully dataset-driven, so a new list — or a new stepped counter on an existing list — needs new template markup but no new JS:
  - `.entry-list-add`/`.entry-list-remove`/`.entry-list-field` (`data-list`/`data-entry-id`/`data-field`) cover add/remove/edit. `_entryDefaults(key)` is the one override point for a list whose entries need more than `{name, description}` — Carrier's Crew Members add `position`, Cause's Factions add `exhausted`/`seized`/`grip`. A `<select>` element's `.type` is `"select-one"`, which already falls through the same "not a checkbox, use `.value`" branch a text input does, so Division's kind picker needed no changes to this handler either.
  - `.entry-list-counter-step` (adding `data-delta`/`data-min`/`data-max`) covers a clamped +/- counter on one entry's field — Authority's Division Strength/Disfavor, Authority's Pillar GRIP, and Cause's Faction Grip all share this one handler; nothing sheet-specific reads or writes these, the bounds live entirely in the template.
- **Authority has exactly three Divisions, each with exactly three Pillars (nine total)** — none of these are add/remove lists. `createWorldActor`'s `buildSystem` for the Authority kind builds the three Divisions first, then derives the nine Pillars from them (`divisions.flatMap(...)`), so each Pillar's `divisionId` can be seeded from its owning Division's freshly-generated `id`. The sheet renders both with `WorldActorSheet`'s generic field-edit/counter-step handlers but no add/remove controls. Authority's Stability (1–9, starting at 9) is a click-to-set segmented track like Playbook's Spotlight, but with no decrement-on-reclick behavior, since Stability's floor is 1, not 0 — there's no empty state to decrement into. Each Division additionally carries Strength (0–5, seeded 5/4/4) and Disfavor (0–10, seeded 0) via the generic counter-step mechanism above.
- **Pillars are stored as a flat list (`system.attributes.pillars`) with a `divisionId` foreign key back to their owning Division, rather than nested inside each Division object.** This is deliberate: `WorldActorSheet`'s generic handlers (`_onEntryFieldChange`/`_onEntryCounterStep`) only know how to read and write one flat `system.attributes.<list>` array at a time, so nesting Pillars inside Divisions would mean either bespoke Authority-only handlers or teaching the generic ones about nested arrays. Keeping Pillars flat — the same shape Cause's Factions already use — means Pillar GRIP (0–3) and Felled (a checkbox) ride the fully generic handlers with zero new JS, exactly like Division Strength/Disfavor and Faction Grip/Exhausted/Seized do. `authority-actor-sheet.js`'s `_divisionsData()` groups the flat Pillars list onto each Division by `divisionId` (`pillars.filter((p) => p.divisionId === division.id)`) fresh on every `getData()` call, purely for rendering — the actor's own stored data never nests them.
- **Each Division carries a `kind` key** (a plain string, unset — `""` — until the GM picks one; `createWorldActor` deliberately never seeds a real value, since picking one is a rules decision the code shouldn't make) resolved against `scripts/world-actors/division-kinds.js`'s `DIVISION_KINDS` catalog in `_divisionsData()`. A kind's passive outcome (a single HTML string, always in effect) and active outcomes (a list of HTML strings, the Authority can trigger) are resolved fresh on every render and shown read-only — catalog-in-code, key-on-actor, the same convention `ASTIR_PART_CATALOG`'s `partType` field already follows. **`DIVISION_KINDS` holds the six real Division kinds** — Military, Subterfuge, Resource, Research, Curator, Executive — each with one passive outcome and a three-option "choose one" list of active outcomes triggered when that Division wins a Conflict Scene.
- **Cause's Factions carry two independent status flags** — `exhausted` and `seized` (both default off) — plus a Grip counter (0–3, default 0). The flags are plain checkboxes through `_onEntryFieldChange` (it branches on `event.currentTarget.type === "checkbox"` vs the input's `.value`); Grip goes through `_onEntryCounterStep`. Each Faction also carries a `kind` key (unset `""` until the GM picks one, same convention as Division's `kind`), resolved against `scripts/world-actors/faction-kinds.js`'s `FACTION_KINDS` catalog in `_factionsData(listKey)` — rendered with `{{}}`, not `{{{}}}`, since unlike `DIVISION_KINDS` these strings are plain text, not HTML. **`FACTION_KINDS` holds the ten real Faction kinds** — Guerrillas, Agents, Bandits, Despoilers, Scholars, Suppliers, Firebrands, Military, Strange, Adventurers — each with an "opposes with" line and a single outcome the party gets for helping that Faction.
- **Wayward Factions (`system.attributes.waywardFactions`) are a second, independent freeform list**, identical shape/defaults/kind-catalog to `factions`. Both render through the shared `templates/cause-sheet/faction-card.hbs` partial — only the `data-list` key and section heading differ between the two call sites — and `createWorldActor`'s Cause `buildSystem` seeds both lists empty.
- **The Carrier carries two named, fixed-role weapon slots** — `primary` (Tier V, up to +2 in player-picked tags, always additionally carrying the locked `set-up`/`mounted` tags) and `secondary` (Tier III, up to +1 in player-picked tags, always additionally carrying the locked `mounted` tag) — keyed in `system.attributes.weapons` as `{ primary, secondary }` (each `null` or a stored equipment entry), not an array, and not playbooks' mixed `system.attributes.equipment`, since a Carrier never has gear. `WEAPON_SLOTS` in `carrier-actor-sheet.js` is the single source of truth for each slot's `tier`/`maxTagValue`/`lockedTagKeys`. Adding/editing one calls `configureEquipment(..., { carrierWeapon: true, carrierWeaponTier: slot.tier, excludedTagKeys: slot.lockedTagKeys, maxTagValue: slot.maxTagValue })` — mirroring the existing `astirWeapon` option — which hides Kind (always "weapon"), hides Scale (always the `"astir"` `WEAPON_SCALES` entry) and disables Tier (fixed at the slot's own tier via `carrierWeaponTier`, which defaults to `TIER_MAX` for every other caller); the sheet forces `kind`/`tier` again on save regardless, so a dialog bug can't leak a non-weapon or off-tier entry into the slot. A slot's locked tags are never written into the stored entry's own `tags` — `_weaponTagKeys(slot, entry)` unions them in fresh on every read (mirrors playbook-sheet/equipment-mixin.js's move-granted `grantsWeaponTags` lock, keyed by slot instead of by picked move), which is what makes them non-removable: there's no checkbox for them in `configureEquipment`'s editor to begin with. Each weapon gets a quick-roll button per `usesWeapon` move, always rolling a fixed `{ key: "crew", label: "CREW", value: <this Carrier's crew stat> }` trait — clicking a specific weapon's button *is* the weapon choice, so unlike `PlaybookActorSheet` there's no `chooseWeapon` prompt and no Unarmed option (a Carrier "must use the carrier weapons"). Full parity with `PlaybookActorSheet`'s own weapon rolls otherwise: narrative tags, equipment spends, forced-tag-effects, reroll offers and Guided are all resolved via shared pure resolvers in `scripts/equipment/equipment-helpers.js` (`resolveEquipmentSpends`/`resolveNarrativeWeaponTags`/`resolveForcedWeaponEffect`/`resolveAvailableReroll`/`resolveAvailableRerollTag`/`weaponTagsAreGuided`) that both `CarrierActorSheet` and `playbook-sheet/equipment-mixin.js` wrap — see below on Fire Support's "borrowed" weapons for how the same resolvers cover a weapon rolled from either sheet. The Carrier's weapon cards render through the same shared `templates/shared/equipment-card.hbs` partial the Equipment/Astir/Ardents tabs use (with `controls=true`, no `disabledToggle` — the Carrier has no Disabled toggle), so its Value/Tier/Scale badges and tag panel look identical to a playbook's own weapon cards, including a "Spent" checkbox for a spend-without-effect tag (One-Use, Dangerous, Refresh, Vorpal), wired to `_onWeaponTagSpentToggle`; each slot gets its own `.section-header` (`{{label}}` as the `<h3>`, the `+` add button when empty) rather than one shared "Weapons" header for both slots. Because the partial addresses in-card buttons by `data-equipment-id`, not `data-slot`, `_onWeaponEdit`/`_onWeaponRemove`/`_onWeaponMoveRoll`/`_onWeaponTagSpentToggle` resolve the clicked id back to its slot via `_weaponSlotForId(id)` before acting; the section header's own `+` add button (outside any card) still addresses by `data-slot`, since there's no entry/id to click on yet.
- **Fire Support (The Captain) "borrows" the Carrier's weapons into a playbook actor's own weapon-choice dialog** (`move-roll-mixin.js`'s `_onMoveRoll`, gated on `_grantsCarrierWeaponAccess`/`playbook-moves.js`'s `grantsCarrierWeaponAccess`, only offered with exactly one Carrier in the world). Each Carrier weapon is shallow-copied — never mutating the Carrier's own stored array — with its slot's locked tags pre-merged into `.tags` (`carrierWeaponTagKeys`, exported from `carrier-actor-sheet.js`) and flagged `fromCarrier: true`/`carrierActorId: <id>`. `playbook-sheet/equipment-mixin.js`'s own weapon-roll methods (`_equipmentSpends`/`_narrativeWeaponTags`/`_forcedWeaponEffect`/`_availableReroll`/`_weaponIsGuided`) each start with a `weapon.fromCarrier` fast path that calls the same shared resolver `CarrierActorSheet` wraps, rather than falling through to their normal `this._equipment()`-scanning bodies (which could never resolve a weapon living in a different actor's array). Any resulting spend (a checked equipment tag, a forced tag, a reroll) is written back to the actual Carrier — via `spendEquipmentTagsOnActor(game.actors.get(weapon.carrierActorId), spends)` in `move-roll-mixin.js#_finishMoveRoll`, and via `reroll.spendActorId` (set by `resolveAvailableReroll`, defaulted in `move-roll.js`'s `rerollOffer`, read by `move-chat-listeners.js#handleReroll`) for a reroll spent later from the chat card — never onto the rolling playbook actor's own equipment array.
- **Playbooks rolling a move with a CREW `fixedTraits` entry (Lead a Sortie) resolve it from the world's Carrier actor(s)**, not a static placeholder. `carrier-actor-sheet.js` exports `findCarrierActors()` and `chooseCarrier(carriers)` (a `choosePlaybook`-style picker), imported by `playbook-actor-sheet.js`. `_moveTraits` resolves the single/zero-Carrier case synchronously for display (0 when zero or ambiguous); `_rollMove` only prompts via `chooseCarrier` when more than one Carrier exists, overriding the trait's value before the roll — cancelling aborts the whole roll, same convention `chooseWeapon`'s own cancel already has.
