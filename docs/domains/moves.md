# Moves

### Basic moves
- Basic moves are **not** Items or compendium content — they're plain JS objects in the `BASIC_MOVES` array in `scripts/moves/basic-moves.js` (re-exported, along with everything else that used to live directly in `scripts/moves/moves.js`, from that file's barrel — see claude.md's "Code organization"), rendered directly by `PlaybookActorSheet`. Every playbook gets them automatically; there's no per-move pack setup.
- A move object's fields: `key`, `name`, `traits` (array of `TRAITS` keys it can roll +, empty if the move rolls no stat), `description` (HTML rules text), `results.{success,mixed,failure}` (chat result text, `null` if the move defines none). Optional: `hold` (per-tier hold grant, e.g. Read the Room), `questions`/`questionPrompts` (hold-spend flavor), `conditions` (array of `{key,label}` checkbox modifiers each worth +1, for moves with no base stat, e.g. Help or Hinder), `intents` (array of `{key,label}`, a flavor-only choice with no mechanical effect).
- Universal roll modifiers (Advantage/Disadvantage, Confidence/Desperation) live in `scripts/moves/roll-effects.js` and apply to every move roll regardless of the move's own fields — they are not part of a move's definition.
- Trait gating: `system.stats.<key>.disabled` (e.g. `channel` is disabled by default per playbook) hides that trait from a move's rollable options via `availableMoveTraits`/`_moveTraits`, and the move's Roll button itself greys out via each move's `gated` flag in `getData` (`gated` is true only when a move's `traits` is non-empty but every one of those traits is currently disabled for the actor — a move with no `traits` by design, like Help or Hinder, is never gated).

### Playbook moves
- Playbook moves use the **exact same move-object shape** as basic moves and run through the same `_moveGroupMoves`/`rollMove`/`postMoveDescription` path — the difference is purely *who has them*, not what they are.
- Unlike basic/special moves, **no playbook starts with any**. They're organized into pools in `MOVE_POOLS` (`scripts/moves/playbook-moves.js`) and picked one at a time via the "+" button on the sheet's Playbook Moves section, so two Scouts can carry different sets.
- A pool with a `playbookName` (matching a `PLAYBOOKS` entry in `actor-creation.js`) belongs to that playbook; a pool without one is universal (Cantrips, Soldier Moves) and carries a `note` explaining when it applies.
- **Move keys are prefixed with their pool's key** (`the-scout:bullheaded`) because `PlaybookActorSheet` resolves every move — basic, special and playbook — from one flat `ALL_MOVES` list, and different playbooks will eventually name moves the same thing.
- The actor stores only the picked keys, in `system.attributes.playbookMoves`. Since `swapActorPlaybook` replaces `system.attributes` wholesale, switching playbooks clears the picked moves — which matches the rulebook.
- **Pool restrictions are deliberately not enforced.** The picker shows every pool to every actor. The rules around Soldier Moves ("under specific circumstances") and reaching into another playbook's pool ("in rare circumstances") are loose enough that policing them in code would get in the table's way; the Advancement checklist (`advancements.js`) is where that bookkeeping lives.
- **A playbook's own starting moves are the one exception, and only under "Other Playbooks".** A playbook's `grantedKeys`/`pickOneKeys` starting moves (`STARTING_MOVE_POOLS`, `starting-moves.js`) are unconditional chargen grants, not ordinary picks, so they're filtered out of every *other* playbook's listing under "Other Playbooks" — `playbookMoveSections`/`choosePlaybookMove` take an injectable `startingMoveKeys` param (a Map built by `startingMoveKeysByPlaybook()`, wired in by `move-tracking-mixin.js`'s `_onPlaybookMoveAdd`) that `pickerSection` excludes by key. A playbook's own starting moves remain visible and pickable in its own pool section, unaffected.
- `playbookMoveSections` takes an injectable `pools` argument (like `choosePlaybook(playbooks = PLAYBOOKS)`) so its ordering/nesting/emptiness tests run against fixtures rather than live content that would quietly stop covering those cases as pools change.

### Adding move content
Adding rules text is a pure data change; adding a *mechanic* is not. Classify which one you're doing before planning — the costs are very different (see "What breaks" below).

**Deriving a move's shape from its rules text.** Match on the phrasing, not the flavor:

| Rules text says | Shape |
|---|---|
| "roll +X", "roll +X or +Y" | `traits: ["x","y"]` + `results.{success,mixed,failure}` (`null` per tier the move doesn't define) |
| "+1 if …" bullets with no base stat | `conditions: [{key,label}]`, each worth +1 — e.g. Help or Hinder |
| "on a 10+ hold 3, on a 7-9 hold 1" | `hold: {success,mixed,failure}` → writes the shared `system.resources.hold` |
| "hold 3" with no roll behind it | `flatHold: 3` → its own pool at `system.attributes.moveHold.<moveKey>`, keyed like `uses` so multiple flatHold moves on one actor don't collide, renders **Activate** instead of Roll. `suppressActivateButton: true` (Embrace Chaos only) opts a `flatHold` move back out of that Activate button when the only way to gain the hold is a different, gated mechanism (there, `grantsDowngradeHold`'s own chat-card offer) rather than a free click — see below |
| "spend N hold/a use to succeed [on any move] as if you'd rolled a 10+" | `grantsAutomaticSuccess: { cost: N }` (spent from this move's own `flatHold` pool), `{ useKey, moves? }` (spent from this move's own `uses` checkbox, optionally restricted to specific move keys), `{ costsPeril: true, moves? }` (spent by adding a fresh peril Danger instead), or `{ excludeMoves? }` with none of the three (spends nothing at all — offered on any roll, or any but the listed move keys, whenever the granting move is picked). Optional `requiresTier: "<tier>"` (Embrace Chaos's own Upgrade only) additionally restricts *that one source* to a single non-success tier, on top of the shared "never on an already-successful roll" gate every source already has. Optional `buttonLabel` overrides the chat-card button's default "Automatic success from `<name>`" text with the source's own wording — see below |
| "roll a 10+, opt to instead take a 7-9, hold N" | `grantsDowngradeHold: { amount: N }` (Embrace Chaos) — the mirror image of `grantsAutomaticSuccess` immediately above: a chat-card offer on a 10+/12+ that *grants* hold instead of spending it, gated on the source's own hold pool having room left (offering a downgrade that grants nothing would cost the player a worse result for no benefit) — see below |
| "spend N hold to convert a disadvantage into an advantage" | an ordinary `grantsRollModifier` entry (Embrace Chaos) with a `requiresAdvantage` gate and a `costsHold` cost — see below |
| no roll, no tracked resource, pure fiction | `traits: []`, no `results` — description only (Subsystems, Bullheaded). **This is the common case for playbook moves.** |
| a choice that changes no math | `intents: [{key,label}]` |
| a stat with no UI in this module | `fixedTraits: [{key,label,value}]` — appended to the roll options as-is, never read from the actor (Lead a Sortie's CREW) |
| "once per Sortie"/"once per Downtime" | `uses: [{key,label}]` — one checkbox per entry, `checked` read from `system.attributes.moveUses.<moveKey>.<useKey>`. A manual tracker (see Recurring conventions); works identically for any move source, not just playbook moves. |
| "your tier... counts as one higher than whatever it would normally be" | `tierBonus: N` → summed across picked moves, added on top of both on-foot base Tier and a mounted frame's own (`_conflictTier`) — contrast `conflictTier` itself, which is *maxed* across picks, not summed |
| "you have a total of N tokens instead of M" | `downtimeTokensMax: N` → `_downtimeTokensMax()` takes the max across picked moves' own flags, same reduce shape as `conflictTier`'s own base |
| "take +1 token during Downtime to spend on [restriction]" | `bonusDowntimeTokens: { max: N, description }` — grantable by a move, an Astir/Ardent Part, or an equipment/starting-gear entry alike. A move's or Part's own pool lives at `system.attributes.bonusDowntimeTokens.<key>`, keyed like `moveHold`/`uses` so multiple granting sources on one actor don't collide; an equipment entry instead stores its value right on itself (`bonusDowntimeTokensValue`), since equipment ids are per-actor and disposable (see Equipment below). Independent of the main `downtimeTokensMax` ceiling above, reset to its own `max` on Refresh Sortie the same as the main counter |
| rules text grants a Downtime-relevant ability (an extra Scene, a reference note on how a resource behaves during Downtime, etc.) | `downtimeAbility: "<text>"` — a plain description string, purely a reference note with no mechanical effect of its own (contrast `bonusDowntimeTokens`/`downtimeTokensMax`, which back real trackers). Read by `_downtimeAbilitiesData()` (`progression-mixin.js`), which unions it across `BASIC_MOVES`/`SPECIAL_MOVES`/picked playbook moves to populate the read-only Downtime Abilities list on the Downtime tab |
| "Requires: X" | `requiresMoves: [moveKey, ...]` — enforced via `unmetMoveRequirements`/`moveRequirementTooltip` (`playbook-moves.js`). Gates the "+" picker (the option stays visible but disabled, with a hover tooltip) and, live, an already-picked move's own Roll button on the sheet if the prerequisite is later removed — same `gated`/`gatedTooltip` fields `disablesMove` already uses. The prose "Requires: X" line in `description` stays as rules text either way. |
| "on a 12+ [do something extra]" | `addsCriticalReminderToMove: { reminder, moveKeys?, requiresTrait? }` — see below |
| "on a 7-9 [do something extra]" — check whether the target move's own `results.mixed` text also counts as a success before assuming this is the only tier needed | `addsMixedReminderToMove: { reminder, moveKeys }` — see below |
| "you may [use/roll] a Basic Move of your choice with +X instead" | `addsTraitToMove: { chooseMove: true, trait, requiresUnmounted? }` — the same `addsTraitToMove` grant Facilitator/Turn Unearthly/The Old Blood use (a move offers +X as an extra option on a target it doesn't normally roll), but with the target picked per-actor via a dropdown on the granting move's own row (`moves-mixin.js`'s `addsTraitToMoveChoosable`/`addsTraitToMoveChoice`, `move-tracking-mixin.js`'s `_onAddsTraitToMoveChoiceChange`) instead of a fixed `moveKey`/`moveKeys` in the catalog — mirrors `traitBonus`'s own `chooseTrait` (see `trait-bonuses.js`). Stored at `system.attributes.addsTraitToMoveChoices.<grantingMoveKey>`, resolved generically by `move-traits-mixin.js`'s `_moveTraits`. Cantrips' Classical Spellcasting is the reference example. |
| "use the following [weapon] profile" — a fixed piece of gear the move itself hands you | `grantsEquipment: { kind, name, tags, scale? }` — an `equipment.js`-shaped template (not a full stored entry: no `id`/`spent`) snapshotted onto `system.attributes.equipment` the moment the move is newly picked, via `move-tracking-mixin.js`'s `_grantedMoveEquipmentUpdate`/`_onPlaybookMoveAdd` calling `equipment-mixin.js`'s existing `_startingGearEntry` — the same treatment a starting-gear grant already gets, just triggered by a move pick instead of character creation (`startingGear: true`, so it's never tag-locked or budget-capped). Matched by the entry's own `name` to avoid granting a duplicate if the move is removed and re-picked; never auto-removed if the move is later dropped, matching "equipment is the character's" (see Equipment docs). No `tier` field — equipment never stores its own Tier (see Equipment docs' Tier note), so a rulebook profile's own Roman-numeral suffix ("Hand-casting **II**") is dropped from the stored `name`. Cantrips' Classical Spellcasting is the reference example. |
| "choose one of the following tags; add it to [a named granted weapon]" | `grantsWeaponTagChoice: { targetEquipmentName, options: [tagKey, ...] }` — the `grantsWeaponTags` grant (Signed & Sealed, below) with two changes: scoped to the one named weapon (matched by `name`, the same link `grantsEquipment` above already relies on) instead of every weapon, and the tag itself is a per-actor *choice* instead of a fixed set — a dropdown on the granting move's own row (`moves-mixin.js`'s `weaponTagChoiceChoosable`/`weaponTagChoiceOptions`/`weaponTagChoiceChoice`, `move-tracking-mixin.js`'s `_onWeaponTagChoiceChange`), stored at `system.attributes.weaponTagChoices.<grantingMoveKey>` and resolved generically by `equipment-mixin.js`'s `_grantedWeaponTagChoiceKeys`/`_weaponTagKeys` — never persisted onto the target weapon's own stored `tags`, so it drops out the instant the granting move is removed. Cantrips' Advanced Evocation is the reference example; a Director's-discretion "or create a new tag entirely" clause on the same move stays prose-only, same call already made for Complex Spellwork's variable Power cost. |
| "any weapon you wield gains [tags]" | `grantsWeaponTags: [tagKey, ...]` — unconditional and unscoped, folded into every weapon's tag list by `equipment-mixin.js`'s `_grantedWeaponTagKeys`/`_weaponTagKeys`. The Attendant's Signed & Sealed is the reference example. |
| "you lead/roll X with advantage" | `grantsAdvantageOnMove: { moveKey, advantage }` — a fixed, always-on lock of an Advantage state onto a specific *other* move, resolved by the sheet (`_grantedAdvantageForMove`, `move-grants-mixin.js`) at roll time. Contrast `addsTraitToMove`'s player-chosen target above: this only ever narrows an existing choice on a move the actor already has, never adds a new one. The Captain's Born Leader (`the-captain.js:177`) is the reference example. |
| the move's own text describes a conditional/optional way to make a *different* move's roll (not a standing buff on the move rolling it) | `quickRollsMove: { moveKey, trait?, advantage?, reminders? }` — the move gets its own dedicated Roll button (via non-empty `traits`) that quick-rolls the target move with the given trait/advantage forced and reminders attached, rather than locking the target move's own button/dialog. Resolved by `move-roll-mixin.js`'s `_onMoveRoll`/`_lockedTraitFor` and `move-grants-mixin.js`'s `_quickRollAdvantageModifier`. Bureaucrat/The Diplomat (trait + reminders) and Don't Follow Me/The Impostor (trait + advantage) are the reference examples. |

Anything that varies per character is a flag evaluated in the sheet, not a field on the move — see Recurring conventions.

**Systems that do not exist yet.** When move text needs one of these, transcribe it as prose in `description` and leave a code comment flagging it — don't invent machinery mid-content-entry. Roll-modifier stacking (buying extra Advantage at the cost of Desperation) used to be listed here — retired by `grantsRollModifier`'s own composable chain below, which covers both cases (All In, Embrace Chaos) that needed it.

Usage limits ("once per Sortie/Downtime") are the one exception — see the `uses` row above. Cantrips' Seek Allies / Personal Familiar (`scripts/moves/playbook-moves.js`) are the reference examples.

**`grantsRollModifier`** (array field — see `docs/domains/moves.md`, this entry, for the full field list) mechanizes a deferred or fiction-conditioned self-buff into a real "Roll Modifiers" section in the move-roll dialog: an `advantage`/`effect` value, an optional `moveKeys` scope (omitted = every dialog), at most one resource gate (`requiresOverheating`, `costsSpotlight`, `costsHold: {moveKey?, amount}`, `costsPotion`, `costsUse`), an optional `requiresAdvantage: [<advantageKey>, ...]` gate on top of any resource gate (the roll's *currently-resolved* Advantage must be one of the listed keys — see below), an optional `deferred: true` (applies to the *next* qualifying roll rather than the one currently open — see `PlaybookActorSheet#_pendingRollModifierEntries`'s one-shot mechanism), and `reminderOnly: true` for a grant with nothing to actually hook (Dark Guarantees — description text only, no checkbox). Resolved by `PlaybookActorSheet#_rollModifiersForMove`/`_rollModifierAvailability`, spent by `_spendRollModifiers`.

**The `advantage`/`effect` value on a `grantsRollModifier` entry is a signed step, not a set.** `scripts/moves/roll-chain.js` centers `ADVANTAGE_DISPLAY_ORDER`/`EFFECT_DISPLAY_ORDER` (the move-roll dialog's own Dice/Effect notched-slider order) on `"none"`, so every catalog key doubles as a signed offset from it (`advantageOffset`/`effectOffset`) — `"advantage"` means "+1 Advantage" and `"desperation"` means "-1 Effect" off whatever the roll's own running state already is, not "set Advantage/Effect to this value" outright. The move-roll dialog's own `render` callback (`move-dialogs.js`'s `configureMoveRoll`) keeps two plain mutable variables, `currentAdvantage`/`currentEffect`, seeded from `"none"`/`lockedEffect` and then folded through every `forced: true` Roll Modifier entry via `resolveRollChain` (see the forced-entries paragraph below). Checking a `[name='roll-modifier']` box nudges them **once**, at the moment it's checked, via `chainEntryResult(state, entry)` (`roll-chain.js`'s single-step resolver); unchecking it steps them back the other way via `reverseChainStep(state, entry)`, the mirror-image per-axis reversal. Between a check and its own uncheck the player has full manual control of the Dice/Effect notch sliders, and can freely move them anywhere, including away from what the checked modifier granted. This is deliberate: advantage/disadvantage stack and cancel fictionally, so an advantage-granting effect might be counteracted by a fiction-driven disadvantage, leaving a valid state where a modifier is checked but the roll is flat or even at disadvantage. Because of that, `reverseChainStep` never fails outright the way a forward `chainEntryResult` step can — it steps each axis back independently and clamps to a no-op on whichever axis has nowhere left to go (the player has since manually pushed it to that axis's own extreme, or another checked entry already has), rather than rejecting the whole reversal or touching the other axis. A modifier whose gate isn't (or is no longer) satisfied is never auto-unchecked; the Roll button still spends its resource as long as it's checked, regardless of whether its nudge is still reflected in the current Dice/Effect state (see `move-dialogs.js`'s Roll button callback). Unchecked rows are still kept live: `repaintAvailability()` re-evaluates every unchecked, non-reminder, non-statically-disabled row's disabled/reason state against the *current* `currentAdvantage`/`currentEffect` on every notch pick and checkbox change (via `chainEntryResult`, reused as a pure one-step query) — enabling a row the moment the current state makes it newly reachable (e.g. All In once Advantage is picked) and disabling one the current state makes unreachable — but a **checked** row is never touched by this loop, so it stays clickable to uncheck no matter what. `[name='equipment-tag']` (Equipment section) checkboxes do **not** join any of this; a checked equipment spend's own `effect` still sets the roll's Effect directly, layered on top of whatever `currentEffect` resolved to, the same "checking the tag IS the choice" precedence it always had.

**Several standing effects and target-matchup signals that used to hard-lock the Advantage/Effect notch sliders now surface as `forced: true` Roll Modifier entries instead** — pre-checked, impossible to uncheck (the template renders `checked disabled`), but otherwise composing through the exact same `resolveRollChain`/`chainEntryResult`/`reverseChainStep` machinery as an ordinary checked entry. The migrated sources: `_targetTierAdvantage` (Tier vs. a targeted NPC), `_targetMatchupEffect` (Approach vs. a targeted NPC), the shared `_grantedAdvantageForMove` resolver (Born Leader/The Captain, Legacy/an Astir Move — both set the same `grantsAdvantageOnMove` flag), `_coldCompanyAdvantage` (Cold Company/The Wither, a standing actor-wide lock), `_forcedWeaponEffect`/the Unreliable equipment tag, and every pending deferred `grantsRollModifier` grant (Snakes In The Grass/The Adrift, Bullheaded/The Impostor, Bonded In Blood/The Summoner, Ravenous Spectre/The Revenant). Each is resolved by its own dedicated `move-grants-mixin.js` resolver (`_grantedAdvantageRollModifier`, `_coldCompanyRollModifier`, `_targetTierRollModifier`, `_targetMatchupRollModifier`, `_forcedWeaponRollModifier`) and pushed into `_rollModifiersForMove`'s returned array independently, alongside `_pendingRollModifierEntries` (every currently-*pending* deferred grant, not just the first — see below).

**The Advantage and Effect axes land differently here, deliberately, not by oversight:**
- **Advantage axis: `lockedAdvantage` no longer exists at all.** `_lockedAdvantageFor` was deleted outright, along with `configureMoveRoll`'s `lockedAdvantage` parameter, its template "Locked: Advantage" note, and `buildNotchedSlider`'s advantage-disabling call — the Advantage slider is simply never disabled. Every source that used to feed `lockedAdvantage` (the shared grant, Cold Company, Tier, a pending deferred grant's own advantage) is now a `forced` Roll Modifier, and **none of them mask each other** — they compose unconditionally, the same "designed to stack" treatment All In/Embrace Chaos already get. A dispelled Cold Company (+1) and a Tier advantage (+1) against the same target genuinely stack to Advantage x2; opposite signs cancel to `none`, the same as any other chain fold.
- **Effect axis keeps `lockedEffect`, trimmed to two true hard locks plus one standing grant.** `forcesDesperationAtMaxPerils` (bite-the-dust) and `forcesDesperationOnShakenTenet` (weave-magic) — the two "emergency" locks that react to a crisis state rather than a standing grant or a passive target read — plus Field Scout's standing `grantsEffectOnMove`, still disable the Effect slider outright exactly as before. Everything else that used to feed `lockedEffect` — the Approach target-matchup and the Unreliable tag's forced effect — is now a `forced` Roll Modifier that composes freely *with the other two Effect-axis sources* (an Unreliable weapon rolled against a favorably-matched Approach target now cancels to a flat roll, rather than Unreliable silently winning outright and Approach being discarded, which is how it behaved before this migration) but stays masked *as a group* whenever the trimmed `lockedEffect` is set — each of `_targetMatchupRollModifier`/`_forcedWeaponRollModifier` individually returns nothing while `lockedEffect` is non-null.
- **Why the asymmetry:** the Roll button's submit-time callback in `move-dialogs.js` has a real `activeLockedEffect ??` override for Effect — not present for Advantage — specifically so the two remaining emergency locks can never be diverged from. Letting a migrated Effect source compose past that override would let a favorable signal silently cancel out an emergency lock, a rules question this migration deliberately left alone. The Advantage axis has no equivalent override to protect, so nothing masks it.

**`_pendingRollModifierEntries` replaced `_pendingRollModifierGrant`, and `_clearPendingRollModifiers` replaced `_clearPendingRollModifier`, to fix a real bug.** The old singular resolver `return`d on the *first* pending, qualifying deferred grant it found — if a player somehow had two grants pending at once for the same upcoming move (e.g. Bullheaded's unscoped grant and Blue Potion both checked on an earlier roll, then Weave Magic rolled next), the second would silently stay pending, unconsumed, rather than ever applying. `_pendingRollModifierEntries` collects *every* currently-pending, qualifying entry as an array of ordinary `forced: true` Roll Modifier rows instead, and `_clearPendingRollModifiers` clears all of them in one batched `actor.update()` (mirroring `_spendRollModifiers`'s own updates-object pattern) rather than one Foundry document update per grant.

**A `forced` entry is pre-checked and pre-folded into the dialog's initial `currentAdvantage`/`currentEffect` seed at open**, mirroring what checking it "would" do — via `roll-chain.js`'s existing `resolveRollChain` helper, the same left-to-right fold ordinary checked entries already compose through, so any number of forced entries on either axis just works. Because a forced entry's checkbox renders `checked disabled`, the browser can't fire an uncheck event on it — the player retains full manual control of the Dice/Effect steppers from that seeded starting point onward, including checking an ordinary Roll Modifier afterward (e.g. All In, once a forced Tier advantage has already satisfied its `requiresAdvantage` gate) or moving a stepper away from what a forced entry granted.

**One thing stays deliberately out of scope, untouched by this migration:** `CarrierActorSheet`'s own independent `_forcedWeaponEffect`/`lockedEffect` handling for the Carrier's own weapon rolls (`scripts/world-actors/carrier-actor-sheet.js`) — it never passes `rollModifiers` to `configureMoveRoll` at all, so there's no Roll Modifiers infrastructure there to migrate Unreliable into; its handling of Unreliable stays a plain `lockedEffect`, disabling the Effect slider outright. (Don't Follow Me's own Trait lock, once a second untouched example here, no longer exists as a lock at all — it now follows the `quickRollsMove`/Bureaucrat pattern instead: its own dedicated Roll button quick-rolls Lead a Sortie with DEFY and advantage forced, leaving Lead a Sortie's own button/dialog untouched — see the `quickRollsMove` shape-table row above.)

All In (`cantrips:all-in`) and Embrace Chaos (`the-witch:embrace-chaos`) — formerly two bespoke "Category D" mechanisms (`grantsRollStack`/`grantsDisadvantageConversion`, each with their own shape and their own live-reactive `render`-callback wiring) — are now both ordinary `grantsRollModifier` entries under this model, and each nudges `currentAdvantage`/`currentEffect` the same one-time way as any other modifier: All In is `{ advantage: "advantage", effect: "desperation", requiresAdvantage: ["advantage"] }` (+1 Advantage/-1 Effect, only while the roll's currently-resolved Advantage is exactly `"advantage"` — the rulebook's own "when you have advantage" condition, re-checked against `currentAdvantage` at the moment All In itself is checked), and Embrace Chaos is `{ advantage: "advantage2", requiresAdvantage: ["disadvantage", "disadvantage2"], costsHold: { amount: 1 } }` (+2 Advantage, only while currently at a Disadvantage state — `disadvantage(-1)+2=advantage(+1)` and `disadvantage2(-2)+2=none(0)`, both of the rulebook's own outcomes falling out of the same uniform +2 step). Checking Embrace Chaos before All In in the same roll (fiction: "Embrace Chaos converts Disadvantage to Advantage, then All In converts that Advantage to Advantage x2") composes exactly as designed — Embrace Chaos nudges `currentAdvantage` to `"advantage"`, which then satisfies All In's own `requiresAdvantage` gate when All In is checked next.

**`grantsAutomaticSuccess`** (Hot-blooded, Once the War's Over, The Arity Method, Dark Rebirth, Ancient Recall, Ain't No Grave, Embrace Chaos's own Upgrade) is a chat-card button, not a sheet control. `_availableAutomaticSuccess` scans every move for the flag ahead of each roll and passes any whose hold pool (`cost`), `uses` checkbox (`useKey`), Danger state (`costsPeril` — Dark Rebirth spends a fresh peril Danger instead of hold/uses, gated on holding zero peril-type Dangers and not already at `DANGER_MAX`), or — the costless case, where none of `cost`/`useKey`/`costsPeril` is set (Ain't No Grave) — simply being picked at all, is currently spendable through `rollMove` as an offer attached to that roll's chat message — only when the result isn't already a 10+. Clicking one (`handleAutomaticSuccess`) spends the source (a costless source spends nothing — no `actor.update` at all for the spend step), then re-renders the card's `flavor` in place (tier flipped to Success, `results.success` substituted, failure reminders cleared, a badge appended) without re-rolling or touching `content`, since `Roll.toMessage` keeps those in separate fields. It does **not** retroactively re-grant hold the original tier would have written — it reframes the outcome and skips the consequences, it doesn't re-resolve the roll. `moves` (The Arity Method, Dark Rebirth) restricts which move keys can trigger the offer, same field/meaning as `EQUIPMENT_TAGS`' own `reroll.moves`; omitted means any move qualifies. `excludeMoves` (Ain't No Grave) is the inverse — drops one specific move key from an otherwise-unrestricted offer, so Ain't No Grave can upgrade any other move's roll but never its own source move (Never Quite Free)'s. `requiresTier` (Embrace Chaos's own Upgrade only) restricts *that one source* to a single non-success tier, additive on top of the shared `tier !== "success"` gate — needed because three of this flag's other five sources (Dark Rebirth, Ancient Recall, Ain't No Grave) deliberately fire on a failure, so this couldn't be a change to the shared gate itself without silently breaking them. `buttonLabel` (Embrace Chaos again) overrides the chat card's default "Automatic success from `<name>`" button text; every other source omits it and gets the default. Not wired up for `postGuidedResult`, which posts straight into `content` rather than a separate `flavor` field and would need its own update path.

**`grantsDowngradeHold`** (Embrace Chaos only — `{ amount, moves?, excludeMoves? }`) is the mirror image of `grantsAutomaticSuccess` immediately above: a chat-card offer, this time on a 10+/12+ (`tier === "success"`, the one tier `grantsAutomaticSuccess`'s own gate excludes), that *grants* hold to the source's own `flatHold` pool instead of spending it — "you may opt to instead take a partial success as if you had rolled a 7-9, hold 1." `_availableDowngrade` (`move-grants-mixin.js`) mirrors `_availableAutomaticSuccess`'s scan/scoping (`moves`/`excludeMoves`, picked-source gate) plus one extra gate of its own: the source's own hold must be below `HOLD_MAX`, since offering a downgrade that grants nothing would cost the player a worse result for no benefit. Clicking the offer (`handleDowngrade`, `move-chat-listeners.js`) grants the hold (clamped to `HOLD_MAX`) and re-renders the card's flavor down to the Mixed tier, the same in-place edit `handleAutomaticSuccess` does up to Success.

**`grantsExternalRollBonus`/`upgradesExternalRollBonusDie`** (The Icon's Bardic Inspiration/Showstopper — `{ dieFaces }` / `{ moveKey, dieFaces }`) is this module's first cross-actor chat mechanic: every other flag/offer in this section reads or writes only the *rolling* actor's own state, but this one lets a *different* actor spend their own hold against someone else's already-posted roll. That difference shows up in two ways. First, eligibility (`eligibleExternalRollBonusActors`, `move-chat-listeners.js`) is computed live from `game.actors` at chat-render time, not baked into the flavor HTML the way every other offer's flags are — an Icon's hold, or even which moves they've picked, can change between when a card posts and when someone actually clicks its button, so the button itself is appended live in `onRenderMoveChat` rather than pre-rendered in `move-chat.hbs`. Second, clicking it (`handleExternalRollBonus`) never edits the original message: `ChatMessage#canUpdate` only lets the message's own author or a GM call `.update()` on it, and a non-GM spending actor is usually neither, so instead it spends the source's hold 1-for-1, rolls the bonus die (`grantsExternalRollBonus.dieFaces`, or `upgradesExternalRollBonusDie.dieFaces` when the spending actor has also picked a move whose `moveKey` matches the source), and posts the result as its own separate chat announcement, mirroring the original roll's `whisper`/`blind` visibility. Actually adding the rolled die to the original total stays a manual, narrated step, per this module's "manual trackers, not enforcement" convention.

**A 12+ result hooks in without `moveResultTier` gaining a fourth tier.** `moveResultTier` stays exactly three-valued (success / mixed / failure) — a 12+ total still resolves to tier `"success"`, so every existing `tier === "success"` check in the codebase (the desperation/confidence branches in `buildReminders`, `_availableAutomaticSuccess`'s own `tier !== "success"` gate, Cold Company's dispel flip in `_onMoveResolved`) needed no changes. `isCriticalResult(total)` (`scripts/moves/move-results.js`, `total >= 12`) is a second, orthogonal boolean computed alongside `tier` in `rollMove` and `move-chat-listeners.js#handleAdvantage` (a retroactive Advantage add can push a roll across 12+ just as easily as 10+), and it drives exactly two things: the chat card's badge (`critical`/`tierLabel` in `flavorArgs`, `.move-tier-critical` in `styles/playbook-actor-sheet.css`) and `resolveTierValue(source, tier, critical)` — the override mechanism for a move's own tier-keyed data. A move's `results`/`hold`/`questionPrompts` may optionally define a `critical` key alongside its usual `success`/`mixed`/`failure` ones; `resolveTierValue` returns it when `critical` is true and the key is present, and falls back to the plain `success` entry otherwise — so a move with no `critical` key (every catalog move today) behaves identically on a 12+ as on a 10+, which is what "identical to 10+ by default" means in practice. `addsCriticalReminderToMove: { reminder, moveKeys?, requiresTrait? }` is the additive mechanism a *different* move can grant, the 12+ mirror of `addsSuccessReminderToMove`/`addsFailureReminderToMove` above, resolved by `_grantedCriticalReminderForMove` (`moves-mixin.js`). Omitted `moveKeys` means universal — Soldier's Indomitable ("whenever you make a move, on a 12+...") is the one grant that needs this, the same unrestricted convention `grantsAutomaticSuccess.moves` already uses. `requiresTrait` (The Diplomat's Sharp Tongue only) further restricts the grant to whichever trait was actually rolled, since Exchange Blows offers a CLASH/TALK choice and Sharp Tongue's own text only fires "when you exchange blows with +TALK". Cantrips' Truth-making (Read the Room) and The Advocate's A Greener World (Weave Magic) are the two plain `moveKeys`-scoped examples. See `scripts/moves/playbook-moves.js` for all four. `buildReminders` skips `extraCriticalReminder` when its text is already present among the reminders `tier`/`effect` produced (in practice only ever a collision with `extraSuccessReminder`, since `critical` can only be true while `tier` is already `"success"`) rather than posting it a second time — The Witch's Bearer Of Curses is the motivating case: its trigger has no tier qualifier at all, so it grants the *same* text via `addsSuccessReminderToMove`/`addsMixedReminderToMove`/`addsFailureReminderToMove`/`addsCriticalReminderToMove` alike, and a 12+ roll would otherwise post that text twice. This mirrors `_ridersForMove`'s own "All Rolls:" collapse (see the Riders paragraph below) for the pre-roll preview of the same situation.

**`addsMixedReminderToMove: { reminder, moveKeys }`** is the 7-9 mirror of `addsSuccessReminderToMove`/`addsFailureReminderToMove`, resolved by `_grantedMixedReminderForMove` (`move-grants-mixin.js`) and threaded through `buildReminders`/`rollMove`/`handleAdvantage` alongside its three siblings. `moveKeys` is required, same as `addsSuccessReminderToMove`/`addsFailureReminderToMove` (not `addsCriticalReminderToMove`'s optional-any convention) — nothing needs a universal mixed-tier grant yet. The move worth remembering here: **a move whose own `results.mixed` text reads as a genuine success ("you succeed as above, but choose 1...") needs `addsMixedReminderToMove` on top of `addsSuccessReminderToMove`, not instead of it** — Mana Devourer, Fisher of Men, and In Blood & Terror all learned this the hard way (shipped 10+-only, then had to add the 7-9 half once someone actually checked their move's own mixed-tier wording). Check a target move's own `results.mixed` before assuming a reminder is 10+-exclusive. The Scout's Patch Job (Cool Off) is the reference example.

**Riders** (the move-roll dialog's read-only preview section, `templates/move-roll-dialog.hbs`) invents no new data model — `PlaybookActorSheet#_ridersForMove` (`move-roll-mixin.js`) calls the four `_grantingMoveForXReminder` finders (`_grantingMoveForFailureReminder`/`_grantingMoveForMixedReminder`/`_grantingMoveForSuccessReminder`/`_grantingMoveForCriticalReminder`, `move-grants-mixin.js`) — the "find the granting move" half that the post-roll `_grantedXReminderForMove` resolvers `_finishMoveRoll` calls are themselves now thin wrappers over — before the dialog opens instead of after the roll resolves, and renders whichever of the four come back non-null as plain `{label, text}` rows with no checkbox. Each row's label is prefixed with its granting move's own name (`` `${source.name} - On 7-9` ``, etc.) so a rider is traceable to what granted it — a distinct concern from the Roll Modifiers section immediately above it in the same dialog, which already defaults its own label to the granting source's name and needed no change here. Computed once per dialog open — via `_rollMove`'s single-weapon path and once at the top level of `_rollMoveWithWeaponChoice`'s array path — never per weapon, since none of the four finders take a weapon as an argument. Known limitation: `_grantingMoveForCriticalReminder` is called with `traitKey` omitted for this preview, since the trait isn't chosen until inside the dialog the preview appears in — a `requiresTrait`-gated critical reminder (The Diplomat's Sharp Tongue is the only one today) therefore never shows up pre-roll, even though it still fires correctly on the post-roll chat card, which calls the same resolver with the actually-chosen trait. Two tier combinations collapse into a single row when their reminder *text* matches: mixed+success into one "On Any Success" row (Mana Devourer), labeled from the mixed tier's own source name, and all four tiers into one "All Rolls:" row (The Witch's Bearer Of Curses), labeled from the failure tier's own source name — in the current catalog a merge only ever collapses reminders that came from the same single source anyway, so either choice names the same move. Every other combination — including a failure+success match, or a mixed+success match with different text — renders as separate rows exactly as before; nothing in the catalog needs a broader merging scheme yet.

### Move changes: what breaks
- **Adding a basic or special move breaks a test; adding a playbook move doesn't.** `tests/playbook-actor-sheet-moves.test.js` asserts the whole `data.moveGroups` array in a single `toEqual` that enumerates every basic and special move, so a new entry has to be added there too. The Playbook Moves group is empty in that test, so pool content never touches it.
- Tests index move groups **positionally** (`moveGroups[0]` = Basic, `[1]` = Playbook, then Astir if present, then Special last) — reordering `data.moveGroups` breaks many assertions at once.
- Both move test files pin specific keys as module constants (`EXCHANGE_BLOWS`, `B_PLOT`, `BULLHEADED`, …), so renaming or deleting one of those moves breaks them at import.
- **Coverage is a hard gate at 100%**, not just a report (thresholds in `vitest.config.js`). New move *data* costs nothing since it adds no branches — but any new *flag* read in `_moveGroupMoves` does, and needs its own test or the build fails.
- **A template's own `{{else}}`/fallback branch can silently assume a narrower shape-space than the data actually supports, and only a new data shape exposes it.** `starting-gear-picker.hbs` had one `{{else}}` on `{{#if groups.length}}` rendering "There is no starting equipment list for this playbook yet." — dead code for every playbook before Commander, since every prior `STARTING_GEAR_POOLS` entry with any content at all also had non-empty `groups`. Commander's pool is `grantedItems`-only with `groups: []`, which the sheet's own gating (`getData`'s `startingGear.available`, `_onStartingGearAdd`) correctly recognized as "something to show" — but the template's stale `{{else}}` fired anyway, since it keyed only off `groups.length`. Same blind spot as the rest of this section: a template's own conditional coverage has to be checked by hand against every *real* shape a pool can now take, not just the shapes that existed when the fallback was written.
