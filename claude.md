# Foundry Module Development Notes

## Concurrent work
- There might be other agents or humans working at the same time as you. Do not panic if you see diffs with changes you did not make in unrelated files. If you and another actor made changes to the same file, then you can investigate.

## Subagent Model Selection

When spawning subagents via the `Agent` tool, set the `model` parameter explicitly rather than relying on inheritance — under `opusplan` or `opus`, a subagent spawned during plan mode inherits Opus, which is overkill and expensive for most exploration.

- **Rote / well-scoped exploration** (known files or symbols, a single targeted lookup, mechanical grep/read work): use `model: "haiku"`.
- **High-complexity exploration** (ambiguous scope, cross-file inference, or output that will directly drive a plan): use `model: "sonnet"`.

Judge each exploration's complexity. When genuinely unsure, prefer `sonnet`.

In practice, a brief that's purely rote (haiku-eligible) is usually also small enough to fall under the "≤3 queries → use Grep/Read directly" guidance and not need a subagent at all — so haiku-tier Explore agents will legitimately be rare. Don't force a haiku call just to exercise the tier; most real briefs mix a verbatim-lookup part with an interpretive part, and bundling both under `sonnet` in one call is correct rather than a sign the dial isn't being used.

## Implementing Plans from Plan Mode

After a plan is approved, prefer delegating the implementation to a subagent with a distilled, self-contained brief rather than continuing inline in the planning session.

- **How**: write the brief to contain only the finalized approach — don't say "implement the plan we discussed," which leans on the polluted history to fill gaps.
- **Exception**: for work that needs tight, iterative back-and-forth or repeated judgment calls, staying inline in the session can be simpler than round-tripping through a subagent.

## Before declaring a task done
- Stage the changes (`git add`) and run the pre-commit checks (`npx lint-staged` and `npm run test:coverage`, as defined in `.husky/pre-commit`) before declaring any task done.

## Code organization
Prefer reasonable groupings of classes and functions over large "god files" — each file readable in one sitting and scoped to one clear concern. This is a judgment call, not a line count: split when a file's *responsibilities* multiply. A cohesive file that's long because its subject matter is long (e.g. a catalog of content) is fine.

- `scripts/playbook/playbook-sheet/` is the reference pattern: one file per domain (`astir-mixin.js`, `ardent-mixin.js`, `equipment-mixin.js`, `moves-mixin.js`, `frames-mixin.js`, `progression-mixin.js`, `tracking-mixin.js`), each exporting a plain object of methods merged onto `PlaybookActorSheet.prototype` via `Object.assign` in the orchestrator (`scripts/playbook/playbook-actor-sheet.js`) — not a class-inheritance chain, since the domains never need `super` or to override each other. Every method stays reachable at exactly the `sheet._methodName(...)` path callers and tests already expect.
- A mixin object merged that way is safe for a primitive-default instance field like `_dangerAddOpen = false` (reads fall through the prototype, writes shadow it per-instance) but **not** for an array/object default, which would be shared by reference across every sheet instance. Keep any non-primitive-default field as a real class-field declaration on the orchestrator class itself.
- When consolidating a derived, cross-cutting constant during a split, watch which direction the dependency points — don't drop it into the lowest-level module it happens to reuse pieces of if that would make that module depend upward on higher-level ones. This is why `ALL_MOVES`/`WEAPON_MOVES` got their own `scripts/moves/all-moves.js` rather than living in `moves.js`, which stays free of any dependency on `playbook-moves.js`/`astir.js`/`ardent.js`.
- The same principle applies to test files, not just source. `tests/playbook-actor-sheet.test.js` used to be the largest file in the repo by a wide margin; it's now been split along the same domain lines as the `playbook-sheet/` mixins, plus one file per cross-cutting concern: `tests/playbook-actor-sheet-astir.test.js`, `-ardent.test.js`, `-equipment.test.js`, `-frames.test.js`, `-progression.test.js`, `-tracking.test.js`, `-moves.test.js` (getData shaping, gating, hold, picking), `-move-rolls.test.js` (`_onMoveRoll`/`_onWeaponMoveRoll` and spend variants), `-roll-results.test.js` (every `_rollMove` variant), and `tests/move-chat-listeners.test.js` for `scripts/moves/move-chat-listeners.js`'s own exports. `tests/playbook-actor-sheet.test.js` itself now only covers the orchestrator: class basics, `getData`'s cross-cutting fields, `activateListeners`, `_seedCosmeticDefaults`, `_onPlaybookChange`. `tests/playbook-actor-sheet-commander.test.js` was the original precedent for peeling off one domain's tests into their own file.
- The same domain-per-folder principle applies one level up: `scripts/core/` (cross-cutting catalogs referenced by every domain below — Traits, Approaches), `scripts/moves/`, `scripts/equipment/`, `scripts/frames/` (Astir/Ardent), `scripts/playbook/` (the playbook actor sheet plus its own `playbook-sheet/` mixins), and `scripts/world-actors/` (Carrier/Authority/Cause). `main.js` and `actor-creation.js` stay at `scripts/` root since both are cross-domain bootstrapping code, not owned by one folder.

## Reference environment
- The baseline PBTA Foundry system (`pbta`) and two Masks: New Generation modules are checked out in sibling directories as this module's reference environment. `masks-newgeneration-sheets` is the practical example for implementing and registering custom character/NPC sheets (`ActorSheet` subclasses in `module/masks-character-sheet.mjs` / `module/masks-npc-sheet.mjs`, Handlebars in `templates/`, styling in `styles/`); it has never been updated past core v11, so it is pattern reference only, not something to version-match — and since it imports pbta's own `PbtaActorSheet` rather than hardcoding a Foundry-version-specific base class, it creates no mismatch risk.
- **The sibling `pbta` and `masks-newgeneration-unofficial` repos are pinned (detached HEAD) to the exact versions actually installed** — `pbta` at tag `1.1.15.2`, `masks-newgeneration-unofficial` at tag `1.7.6` — both matching the installed Foundry v12.331.0. This makes their code a reliable reference for what's actually running.
- **If either sibling repo is ever checked out to `main` (or a different tag) again, treat it as running ahead of what's installed** until re-pinned to match. `main` on both tracks newer, unreleased core-version support (e.g. `pbta`'s `main` currently targets core v14 / pbta 1.2.0), and a base-class or namespace reference copied from ahead-of-release source can throw at module-evaluation time — which aborts this module's entire `esmodules` import chain, not just the feature being added (this has happened once already). If in doubt, confirm a reference also appears in the *installed* system bundle (`Data/systems/pbta/module/pbta.js` in the Foundry user data directory) or in Foundry's own unpacked client source (`resources/app/client/...` under the Foundry install directory) — grep both if unsure.
- Foundry does not hot-reload `esmodules` — after editing a script file the client needs a full reload. It *does* hot-reload `css`, `hbs`/`html` and `json` (verified in the installed client's `#handleHotReload`: CSS by cache-busting the `<link>` href, Handlebars by recompiling the partial and re-rendering every open window), so a styling or template tweak can land without one. That reload is pushed by a server-side file watcher, though, and whether it fires through the dev-checkout junctions is unverified — treat a full reload as the reliable fallback whenever an edit doesn't appear. See [docs/windows-dev-setup.md](docs/windows-dev-setup.md) for the junction layout itself.

## Recurring conventions
These hold across every domain below. The domain sections note only genuine exceptions.

- **Manual trackers, not enforcement.** Nothing in this module knows when a Sortie, Downtime or Scene begins, so no tracked resource ever resets itself — the player clears it. This covers moves' `uses` checkboxes, Astir Parts' Expended, equipment's `spent` tags, Potions, Cause Factions' flags, and the Advancement checklist (which grants nothing). It's cheap bookkeeping that saves eyeballing a text block during play, not a rules engine.
- **Catalog in code, keys on the actor.** `MOVE_POOLS`, `EQUIPMENT_TAGS`, `ASTIR_PART_CATALOG`/`ASTIR_MOVE_CATALOG`/`ASTIR_WEAPON_CATALOG` hold the definitions; the actor stores only the keys it picked, so edited rules text reaches existing characters, and a `resolve*` helper drops keys that no longer resolve (`resolvePlaybookMoves`, `resolveEquipmentTags`). `EQUIPMENT_CATALOG` is the one deliberate exception — snapshotted on pick, not referenced (see Equipment).
- **Derive fresh every render, never persist.** `_conflictTier`, `equipmentValue`, a weapon's or Part's Tier, and `advancements.topCount` are all computed in `getData` so they can't drift out of sync with what they derive from.
- **Behaviour that depends on actor state goes in the sheet, not the data.** A move / part / tag definition is static data. When behaviour varies per character, put a declarative flag on the object and evaluate it generically in `PlaybookActorSheet` — `usesWeapon`, `requiresChannelDisabled`, `forcesDesperationAtMaxPerils`, `grantsGuided`, `grantsChannelOnAnyMove`, `regainPowerOnDoubles` and every other Astir Part flag work exactly this way.
- **Templates and CSS are invisible to the test suite.** `renderTemplate` is stubbed globally in `tests/setup.js`, and `lint-staged` only runs ESLint on `.js`. Handlebars syntax errors, wrong `../` scope inside a nested `{{#each}}`, and every styling regression sail past a fully green `npm run test:coverage`. Anything touching `.hbs` or `.css` has to be eyeballed in a real Foundry client.

## Domain conventions
- "Playbooks" are always player-controlled Actors (type `character`), never Items. This differs from the baseline PBTA system, where a playbook is normally an Item of type `playbook` that gets applied to a blank character actor. In this module, dragging a playbook out of a compendium should produce a ready-to-play character actor directly — see `src/packs/basic-playbook-scout/` for the pattern (an Actor document with `system.details.callsign` added so players can also record a callsign alongside the actor's native name/image).

### World actors
- Beyond player-controlled Playbook actors, this module also has three non-playbook actor kinds representing things in the world: the **Carrier** (the players' moving base), the **Authority** (the empire/oppressor), and the **Cause** (the loosely organized factions opposing it). Each is its own Foundry Actor sub-type — `armor-astir.carrier`, `armor-astir.authority`, `armor-astir.cause` — declared via `module.json`'s `documentTypes.Actor`, sheets in `scripts/world-actors/carrier-actor-sheet.js`/`authority-actor-sheet.js`/`cause-actor-sheet.js`, templates in `templates/*-actor-sheet.hbs`.
- **Why module-declared `documentTypes` rather than pbta's own `other` type + `system.customType`:** the `other`/`customType` route is what pbta's own Actor creation dialog uses, but it requires the type to be registered in `game.pbta.sheetConfig.actorTypes` — an unregistered `customType` makes `PbtaActor#applyBaseTemplate` merge against `undefined` during `_preCreate` and throw, aborting actor creation. Registering properly means taking over `sheetConfigOverride` (what the sibling `masks-newgeneration-unofficial` module does), a much bigger commitment than three simple sheets need. A module-declared sub-type sidesteps pbta's actor-type system entirely: `Actor.TYPES` is `Object.keys(game.model.Actor)`, and Foundry's own world-launch step (`updateActiveDocumentTypes`, in the installed `resources/app/dist/packages/world.mjs`) merges every active module's `documentTypes` into `game.model` *before* pbta's `_preCreate` ever runs.
- **Actor creation is entirely custom, not pbta's dialog.** `registerPlaybookActorCreation` (`scripts/actor-creation.js`) rebinds the sidebar's `.create-entry` button to `onCreateEntryClick`, which calls `chooseActorKind()` — a Dialog offering "Playbook" plus every entry in `WORLD_ACTOR_KINDS` — then either falls into the existing `choosePlaybook()`/`createPlaybookActor()` path or calls `createWorldActor(kind, options)` directly (`Actor.create({ name, type, folder, system: kind.buildSystem() })`). No `PbtaActor.createDialog`/`defaultName` codepath is ever exercised, which also sidesteps its unguarded `game.pbta.sheetConfig.actorTypes[type].label` lookup (would throw for an unregistered type) — safe only because we always supply an explicit name and never call that dialog.
- **`WORLD_ACTOR_KINDS` in `actor-creation.js`** is the single source of truth for the three kinds — `key` (chooseActorKind's dialog button key), `type` (the Foundry Actor type string), `name` (default actor name), `buildSystem()` (returns each kind's starting `system` data fresh per call, so array/object fields are never accidentally shared between actors created from the same kind).
- **`scripts/world-actors/entry-list.js`** holds pure, Foundry-API-free CRUD helpers (`addEntry`/`removeEntry`/`updateEntryField`) over id-keyed arrays — shared by every world actor list: Carrier's Crew Members, Authority's Assets/Actors/Pillars/Divisions, Cause's Factions.
- **`scripts/world-actors/world-actor-sheet.js`'s `WorldActorSheet`** is the base class all three sheets extend. It wires one generic set of handlers against `system.attributes.<list>`, all fully dataset-driven, so a new list — or a new stepped counter on an existing list — needs new template markup but no new JS:
  - `.entry-list-add`/`.entry-list-remove`/`.entry-list-field` (`data-list`/`data-entry-id`/`data-field`) cover add/remove/edit. `_entryDefaults(key)` is the one override point for a list whose entries need more than `{name, description}` — Carrier's Crew Members add `position`, Cause's Factions add `exhausted`/`seized`/`grip`.
  - `.entry-list-counter-step` (adding `data-delta`/`data-min`/`data-max`) covers a clamped +/- counter on one entry's field — Authority's Division Strength/Disfavor and Cause's Faction Grip all share this one handler; nothing sheet-specific reads or writes these, the bounds live entirely in the template.
- **Authority's Pillars and Divisions are fixed at exactly three slots each**, not add/remove lists — `createWorldActor`'s `buildSystem` for the Authority kind seeds three blank entries into each at creation, and the sheet renders them with `WorldActorSheet`'s field-edit handler but no add/remove controls. Authority's Stability (1–10, starting at 10) is a click-to-set segmented track like Playbook's Spotlight, but with no decrement-on-reclick behavior, since Stability's floor is 1, not 0 — there's no empty state to decrement into. Each Division additionally carries Strength (0–5, seeded 5/4/4) and Disfavor (0–10, seeded 0) via the generic counter-step mechanism above.
- **Cause's Factions carry two independent status flags** — `exhausted` and `seized` (both default off) — plus a Grip counter (0–3, default 0). The flags are plain checkboxes through `_onEntryFieldChange` (it branches on `event.currentTarget.type === "checkbox"` vs the input's `.value`); Grip goes through `_onEntryCounterStep`.
- **The Carrier can carry up to two weapons**, always custom-made and always Tier 5, in their own `system.attributes.weapons` array (not playbooks' mixed `system.attributes.equipment`, since a Carrier never has gear). Adding/editing one calls `configureEquipment(..., { carrierWeapon: true })` — mirroring the existing `astirWeapon` option — which hides Kind (always "weapon"), hides Scale (always the `"astir"` `WEAPON_SCALES` entry) and disables Tier (always `TIER_MAX`); the sheet forces `kind`/`tier` again on save regardless, so a dialog bug can't leak a non-weapon or off-tier entry into the array. Each weapon gets a quick-roll button per `usesWeapon` move, always rolling a fixed `{ key: "crew", label: "CREW", value: <this Carrier's crew stat> }` trait — clicking a specific weapon's button *is* the weapon choice, so unlike `PlaybookActorSheet` there's no `chooseWeapon` prompt and no Unarmed option (a Carrier "must use the carrier weapons"). Deliberately skips equipment spends, forced-tag-effects, reroll and Guided as a v1 scope cut.
- **Playbooks rolling a move with a CREW `fixedTraits` entry (Lead a Sortie) resolve it from the world's Carrier actor(s)**, not a static placeholder. `carrier-actor-sheet.js` exports `findCarrierActors()` and `chooseCarrier(carriers)` (a `choosePlaybook`-style picker), imported by `playbook-actor-sheet.js`. `_moveTraits` resolves the single/zero-Carrier case synchronously for display (0 when zero or ambiguous); `_rollMove` only prompts via `chooseCarrier` when more than one Carrier exists, overriding the trait's value before the roll — cancelling aborts the whole roll, same convention `chooseWeapon`'s own cancel already has.

### Basic moves
- Basic moves are **not** Items or compendium content — they're plain JS objects in the `BASIC_MOVES` array in `scripts/moves/moves.js`, rendered directly by `PlaybookActorSheet`. Every playbook gets them automatically; there's no per-move pack setup.
- A move object's fields: `key`, `name`, `traits` (array of `TRAITS` keys it can roll +, empty if the move rolls no stat), `description` (HTML rules text), `results.{success,mixed,failure}` (chat result text, `null` if the move defines none). Optional: `hold` (per-tier hold grant, e.g. Read the Room), `questions`/`questionPrompts` (hold-spend flavor), `conditions` (array of `{key,label}` checkbox modifiers each worth +1, for moves with no base stat, e.g. Help or Hinder), `intents` (array of `{key,label}`, a flavor-only choice with no mechanical effect).
- Universal roll modifiers (Advantage/Disadvantage, Confidence/Desperation) live in `scripts/moves/roll-effects.js` and apply to every move roll regardless of the move's own fields — they are not part of a move's definition.
- Trait gating: `system.stats.<key>.disabled` (e.g. `channel` is disabled by default per playbook) hides that trait from a move's rollable options via `availableMoveTraits`/`_moveTraits`, and the move's Roll button itself greys out via each move's `gated` flag in `getData` (`gated` is true only when a move's `traits` is non-empty but every one of those traits is currently disabled for the actor — a move with no `traits` by design, like Help or Hinder, is never gated).

### Playbook moves
- Playbook moves use the **exact same move-object shape** as basic moves and run through the same `_moveGroupMoves`/`rollMove`/`postMoveDescription` path — the difference is purely *who has them*, not what they are.
- Unlike basic/special moves, **no playbook starts with any**. They're organized into pools in `MOVE_POOLS` (`scripts/moves/playbook-moves.js`) and picked one at a time via the "+" button on the sheet's Playbook Moves section, so two Scouts can carry different sets.
- A pool with a `playbookName` (matching a `PLAYBOOKS` entry in `actor-creation.js`) belongs to that playbook; a pool without one is universal (Cantrips, Soldier Moves) and carries a `note` explaining when it applies.
- **Move keys are prefixed with their pool's key** (`the-scout:bullheaded`) because `PlaybookActorSheet` resolves every move — basic, special and playbook — from one flat `ALL_MOVES` list, and different playbooks will eventually name moves the same thing.
- The actor stores only the picked keys, in `system.attributes.playbookMoves`. Since `swapActorPlaybook` replaces `system.attributes` wholesale, switching playbooks clears the picked moves — which matches the rulebook.
- **Pool restrictions are deliberately not enforced.** The picker shows every pool to every actor. The rules around Soldier Moves ("under specific circumstances") and reaching into another playbook's pool ("in rare circumstances") are loose enough that policing them in code would get in the table's way; the Advancement checklist (`advancements.js`) is where that bookkeeping lives.
- `playbookMoveSections` takes an injectable `pools` argument (like `choosePlaybook(playbooks = PLAYBOOKS)`) so its ordering/nesting/emptiness tests run against fixtures rather than live content that would quietly stop covering those cases as pools change.

### Adding move content
Adding rules text is a pure data change; adding a *mechanic* is not. Classify which one you're doing before planning — the costs are very different (see "What breaks" below).

**Deriving a move's shape from its rules text.** Match on the phrasing, not the flavor:

| Rules text says | Shape |
|---|---|
| "roll +X", "roll +X or +Y" | `traits: ["x","y"]` + `results.{success,mixed,failure}` (`null` per tier the move doesn't define) |
| "+1 if …" bullets with no base stat | `conditions: [{key,label}]`, each worth +1 — e.g. Help or Hinder |
| "on a 10+ hold 3, on a 7-9 hold 1" | `hold: {success,mixed,failure}` → writes the shared `system.resources.hold` |
| "hold 3" with no roll behind it | `flatHold: 3` → its own pool at `system.attributes.moveHold.<moveKey>`, keyed like `uses` so multiple flatHold moves on one actor don't collide, renders **Activate** instead of Roll |
| "spend N hold/a use to succeed [on any move] as if you'd rolled a 10+" | `grantsAutomaticSuccess: { cost: N }` (spent from this move's own `flatHold` pool), `{ useKey, moves? }` (spent from this move's own `uses` checkbox, optionally restricted to specific move keys), `{ costsPeril: true, moves? }` (spent by adding a fresh peril Danger instead), or `{ excludeMoves? }` with none of the three (spends nothing at all — offered on any roll, or any but the listed move keys, whenever the granting move is picked) — see below |
| no roll, no tracked resource, pure fiction | `traits: []`, no `results` — description only (Subsystems, Bullheaded). **This is the common case for playbook moves.** |
| a choice that changes no math | `intents: [{key,label}]` |
| a stat with no UI in this module | `fixedTraits: [{key,label,value}]` — appended to the roll options as-is, never read from the actor (Lead a Sortie's CREW) |
| "once per Sortie"/"once per Downtime" | `uses: [{key,label}]` — one checkbox per entry, `checked` read from `system.attributes.moveUses.<moveKey>.<useKey>`. A manual tracker (see Recurring conventions); works identically for any move source, not just playbook moves. |
| "your tier... counts as one higher than whatever it would normally be" | `tierBonus: N` → summed across picked moves, added on top of both on-foot base Tier and a mounted frame's own (`_conflictTier`) — contrast `conflictTier` itself, which is *maxed* across picks, not summed |
| "you have a total of N tokens instead of M" | `downtimeTokensMax: N` → `_downtimeTokensMax()` takes the max across picked moves' own flags, same reduce shape as `conflictTier`'s own base |
| "take +1 token during Downtime to spend on [restriction]" | `bonusDowntimeTokens: { max: N, description }` — grantable by a move, an Astir/Ardent Part, or an equipment/starting-gear entry alike. A move's or Part's own pool lives at `system.attributes.bonusDowntimeTokens.<key>`, keyed like `moveHold`/`uses` so multiple granting sources on one actor don't collide; an equipment entry instead stores its value right on itself (`bonusDowntimeTokensValue`), since equipment ids are per-actor and disposable (see Equipment below). Independent of the main `downtimeTokensMax` ceiling above, reset to its own `max` on Refresh Sortie the same as the main counter |
| "Requires: X" | `requiresMoves: [moveKey, ...]` — enforced via `unmetMoveRequirements`/`moveRequirementTooltip` (`playbook-moves.js`). Gates the "+" picker (the option stays visible but disabled, with a hover tooltip) and, live, an already-picked move's own Roll button on the sheet if the prerequisite is later removed — same `gated`/`gatedTooltip` fields `disablesMove` already uses. The prose "Requires: X" line in `description` stays as rules text either way. |
| "on a 12+ [do something extra]" | `addsCriticalReminderToMove: { reminder, moveKeys?, requiresTrait? }` — see below |

Anything that varies per character is a flag evaluated in the sheet, not a field on the move — see Recurring conventions.

**Systems that do not exist yet.** When move text needs one of these, transcribe it as prose in `description` and leave a code comment flagging it — don't invent machinery mid-content-entry:
- **weapon tags / profiles** — e.g. a Cantrip granting "Hand-casting II (ranged/area)" or choosing a tag (defensive, decisive, …) to attach to it.
- **roll-modifier stacking** — e.g. buying extra Advantage at the cost of Desperation. Would touch `roll-effects.js`'s state machine.

Usage limits ("once per Sortie/Downtime") are the one exception — see the `uses` row above. Cantrips' Seek Allies / Personal Familiar (`scripts/moves/playbook-moves.js`) are the reference examples.

**`grantsAutomaticSuccess`** (Hot-blooded, Once the War's Over, The Arity Method, Dark Rebirth, Ancient Recall, Ain't No Grave) is a chat-card button, not a sheet control. `_availableAutomaticSuccess` scans every move for the flag ahead of each roll and passes any whose hold pool (`cost`), `uses` checkbox (`useKey`), Danger state (`costsPeril` — Dark Rebirth spends a fresh peril Danger instead of hold/uses, gated on holding zero peril-type Dangers and not already at `DANGER_MAX`), or — the costless case, where none of `cost`/`useKey`/`costsPeril` is set (Ain't No Grave) — simply being picked at all, is currently spendable through `rollMove` as an offer attached to that roll's chat message — only when the result isn't already a 10+. Clicking one (`handleAutomaticSuccess`) spends the source (a costless source spends nothing — no `actor.update` at all for the spend step), then re-renders the card's `flavor` in place (tier flipped to Success, `results.success` substituted, failure reminders cleared, a badge appended) without re-rolling or touching `content`, since `Roll.toMessage` keeps those in separate fields. It does **not** retroactively re-grant hold the original tier would have written — it reframes the outcome and skips the consequences, it doesn't re-resolve the roll. `moves` (The Arity Method, Dark Rebirth) restricts which move keys can trigger the offer, same field/meaning as `EQUIPMENT_TAGS`' own `reroll.moves`; omitted means any move qualifies. `excludeMoves` (Ain't No Grave) is the inverse — drops one specific move key from an otherwise-unrestricted offer, so Ain't No Grave can upgrade any other move's roll but never its own source move (Never Quite Free)'s. Not wired up for `postGuidedResult`, which posts straight into `content` rather than a separate `flavor` field and would need its own update path.

**A 12+ result hooks in without `moveResultTier` gaining a fourth tier.** `moveResultTier` stays exactly three-valued (success / mixed / failure) — a 12+ total still resolves to tier `"success"`, so every existing `tier === "success"` check in the codebase (the desperation/confidence branches in `buildReminders`, `_availableAutomaticSuccess`'s own `tier !== "success"` gate, Cold Company's dispel flip in `_onMoveResolved`) needed no changes. `isCriticalResult(total)` (`moves.js`, `total >= 12`) is a second, orthogonal boolean computed alongside `tier` in `rollMove` and `move-chat-listeners.js#handleAdvantage` (a retroactive Advantage add can push a roll across 12+ just as easily as 10+), and it drives exactly two things: the chat card's badge (`critical`/`tierLabel` in `flavorArgs`, `.move-tier-critical` in `styles/playbook-actor-sheet.css`) and `resolveTierValue(source, tier, critical)` — the override mechanism for a move's own tier-keyed data. A move's `results`/`hold`/`questionPrompts` may optionally define a `critical` key alongside its usual `success`/`mixed`/`failure` ones; `resolveTierValue` returns it when `critical` is true and the key is present, and falls back to the plain `success` entry otherwise — so a move with no `critical` key (every catalog move today) behaves identically on a 12+ as on a 10+, which is what "identical to 10+ by default" means in practice. `addsCriticalReminderToMove: { reminder, moveKeys?, requiresTrait? }` is the additive mechanism a *different* move can grant, the 12+ mirror of `addsSuccessReminderToMove`/`addsFailureReminderToMove` above, resolved by `_grantedCriticalReminderForMove` (`moves-mixin.js`). Omitted `moveKeys` means universal — Soldier's Indomitable ("whenever you make a move, on a 12+...") is the one grant that needs this, the same unrestricted convention `grantsAutomaticSuccess.moves` already uses. `requiresTrait` (The Diplomat's Sharp Tongue only) further restricts the grant to whichever trait was actually rolled, since Exchange Blows offers a CLASH/TALK choice and Sharp Tongue's own text only fires "when you exchange blows with +TALK". Cantrips' Truth-making (Read the Room) and The Advocate's A Greener World (Weave Magic) are the two plain `moveKeys`-scoped examples. See `scripts/moves/playbook-moves.js` for all four.

### Move changes: what breaks
- **Adding a basic or special move breaks a test; adding a playbook move doesn't.** `tests/playbook-actor-sheet-moves.test.js` asserts the whole `data.moveGroups` array in a single `toEqual` that enumerates every basic and special move, so a new entry has to be added there too. The Playbook Moves group is empty in that test, so pool content never touches it.
- Tests index move groups **positionally** (`moveGroups[0]` = Basic, `[1]` = Playbook, then Astir if present, then Special last) — reordering `data.moveGroups` breaks many assertions at once.
- Both move test files pin specific keys as module constants (`EXCHANGE_BLOWS`, `B_PLOT`, `BULLHEADED`, …), so renaming or deleting one of those moves breaks them at import.
- **Coverage is a hard gate at 100%**, not just a report (thresholds in `vitest.config.js`). New move *data* costs nothing since it adds no branches — but any new *flag* read in `_moveGroupMoves` does, and needs its own test or the build fails.
- **A template's own `{{else}}`/fallback branch can silently assume a narrower shape-space than the data actually supports, and only a new data shape exposes it.** `starting-gear-picker.hbs` had one `{{else}}` on `{{#if groups.length}}` rendering "There is no starting equipment list for this playbook yet." — dead code for every playbook before Commander, since every prior `STARTING_GEAR_POOLS` entry with any content at all also had non-empty `groups`. Commander's pool is `grantedItems`-only with `groups: []`, which the sheet's own gating (`getData`'s `startingGear.available`, `_onStartingGearAdd`) correctly recognized as "something to show" — but the template's stale `{{else}}` fired anyway, since it keyed only off `groups.length`. Same blind spot as the rest of this section: a template's own conditional coverage has to be checked by hand against every *real* shape a pool can now take, not just the shapes that existed when the fallback was written.

### Astir
- An Astir lives at `system.attributes.astir` on the playbook actor itself (nullable — `null`/absent means "no Astir"), not as its own document. `scripts/frames/astir.js` holds every catalog. Astir Parts read as moves (same `traits`/`description`/`uses` shape as `BASIC_MOVES`) and fold into the Moves tab's "Astir Moves" group alongside the Astir's one unique Move.
- **A part's or Astir weapon's benefits only apply while the Astir specifically is the mounted frame.** Since Ardents exist, `piloted` is not a single Astir-only boolean: `_mountedFrame()` returns whichever one frame (the Astir, keyed `"astir"`, or one Ardent, keyed by its stored id) currently has `piloted: true`, an invariant enforced by the single write path `_setMountedFrame`. A player isn't always in a frame, so every frame's Piloted checkbox starts unchecked, and every part-derived effect reads `_mountedParts()` (the mounted frame's own installed parts, `[]` when nothing is mounted) rather than checking "is it the Astir" directly. The whole Astir Moves group gets `gated: true` unless the Astir is mounted, as do Astir weapons' quick-roll buttons (a separate `astirWeaponMoves` mapping in `getData`, so ordinary weapons are unaffected). Managing the loadout itself — Parts, the Astir Move, Astir weapons, and the base Tier/Core/Approach/Power/Overheating fields — is **not** gated.
- Every part-specific mechanic is a declarative flag evaluated generically in the sheet (see Recurring conventions). Flags are read off the actor's *installed* parts (`_astirParts()`) for display, but the mounted frame's own (`_mountedParts()`) for any actual effect — the Parts list still needs to show installed-but-inactive parts when nothing is mounted.
- **Every Active part gets a manual `uses: [{ key: "expended", label: "Expended" }]` checkbox** — Subsystems' own rules text ("spend 1 Power to re-activate an expended Astir part") already assumes any Active part can become expended, so this reuses the generic `uses` mechanism with no new rendering code. A part with an Activate button (`showsReadTheRoomQuestions`) or a roll-dialog spend auto-checks it when used; every other Active part is toggled by the player. `partType: "Active" | "Passive"` is display-only, a badge in the Parts list — it drives no behavior.
- **An Astir Part can offer a roll-dialog spend like an equipment tag, but only when its `spend` actually sets `effect` or `advantage`** — `_astirPartSpends` requires one of the two, the same gate `_equipmentSpends` applies to tags. Artifact is the only qualifying part today: its `spend` is passed to `configureMoveRoll`'s `astirPartSpends` option and rendered in its own "Astir Parts" section of `move-roll-dialog.hbs`, structurally identical to the Equipment section. Checking it marks it Expended via `_spendAstirParts` — the *same* field the Astir Moves group's manual checkbox toggles, so both entry points land on one shared state. `spend.effect` slots into the same precedence as an equipment tag's (Confidence/Desperation axis); `spend.advantage` overrides the Advantage/Disadvantage axis, which nothing did before Artifact, winning over the dialog's Dice select the way a spent effect already wins over the Effect select. `spend.description` exists separately from the part's own rich-text `description` because the latter is multi-paragraph HTML, unusable in a compact dialog row.
  - **A part whose rules text is a manual adjustment must not carry a `spend` at all.** Warding has an Expended checkbox like any other Active part but no `spend`: giving it one with no `effect`/`advantage` made it render in every move's roll dialog as a checkbox that did nothing. Its Expended checkbox is deliberately not gated on the Astir being piloted, so it stays usable any time.
- **An Astir Move or Astir Weapon catalog entry can require an installed Astir Part via `requiresParts: [partKey, ...]`**, enforced by `unmetPartRequirements`/`partRequirementTooltip` (`astir.js`) — the exact `requiresMoves` mechanism above, mirrored for Astir Parts instead of moves. `astirMoveSections`/`chooseAstirMove` and `chooseAstirWeapon` all take an `installedPartKeys` param and gate their picker options the same way (visible but disabled, with a tooltip) rather than filtering them out. The four Familiar Astir weapons (`requiresParts: ["astir-part:familiar-matrix"]`) are the first real content; `ASTIR_MOVE_CATALOG`'s one placeholder entry carries none yet, so the mechanism there is ready but unexercised until real Astir Moves are transcribed.
- **`rollMove` returns `{ message, dice }`, not just the `ChatMessage`** — `_rollMove` needs the dice breakdown to check Flourish Component's regain-Power-on-doubles (`roll-effects.js#rolledDoubles`, true when the two *kept* dice match) without `moves.js` needing to import `astir.js`. A spent Part's label is likewise passed in pre-resolved (`options.spentPartLabels`) rather than as a raw key, for the same import-direction reason.
- **Weapon Conduit's "+2 Power towards weapons only" is a second, entirely separate Power pool** (`astir.weaponPower`, max via `astirMaxWeaponPower`), not a restriction on the main one — nothing spends Power on weapons yet, so it's tracked exactly like the main Power meter (manually stepped, clamped to its derived max on every Part/Astir-weapon change, hidden by the template whenever its max is 0).
- **A Drain tag (`drain-1`/`drain-2`/`drain-3`) on a weapon actually mounted on the Astir (`kind: "weapon"`, `astir: true`) lowers Power for real** — `astirWeaponDrainTotal` sums it, and both `astirMaxPower`/`astirMaxWeaponPower` take the actor's equipment array (not just its Parts) to fold it in. Drain is paid out of the Weapon Power pool's capacity first (that pool's whole purpose); only the remainder reduces main Power (see the shared private `splitWeaponDrain`). A mundane (Foot-scale) weapon's or gear's Drain is inert — an `astir: true` entry is only ever managed from the Astir tab, so its presence in the equipment array already *is* "mounted," with no separate equipped/carried state. Unlike Part cost, this reduction is **not** floored at `ASTIR_POWER_MIN`: a heavily-Drained loadout can legitimately push max (and current) Power negative.
- **An Astir with negative Power can't be piloted.** `_astirPowerUpdates` (shared by the Part and Astir-weapon handlers) re-clamps `power`/`weaponPower` to their recomputed max after any change and forces `piloted` off with a `ui.notifications.warn` the moment that clamp goes negative while piloted; `_onAstirPilotedToggle` mirrors the check to block manually re-checking the box. `getData`'s `power.negative` flag drives a persistent on-sheet indicator as the non-toast counterpart.
- **Alchemical Suite's Potions** (`astir.potions.{red,blue,yellow}`) are granted, uncapped, whenever *this actor* rolls Lead a Sortie while piloted — the rules text reads party-wide ("someone leads a Sortie"), but an actor sheet only sees its own rolls, so this is deliberately scoped to this Astir's pilot. Spent via a decrement-only "Use" button.
- **Complex Spellwork's Director-assigned -1 to -4 Power cost is pinned to a fixed `powerCost: 1`**, with the rest left as descriptive text — a catalog entry can only carry one fixed number, and a variable-cost-at-pick-time flow was explicitly descoped.
- **Resistance Charms and Transmutation Link are pure prose** — a Danger-source downgrade system and aerial/aquatic tags don't exist anywhere in this module.

### Ardents
- **An Ardent is a cheaper, more limited pilotable frame than the Astir** — no Power, no Core, no unique Move, Tier 2–4 (defaulting to 2, versus the Astir's 3–4 defaulting to 3), an Approach picked freely from the full list rather than a Core-narrowed pair, and a combined parts+weapons loadout capped at `ARDENT_MAX_LOADOUT` (2). Unlike the Astir (at most one per actor), a character may have **any number** of Ardents, and may have both an Astir and Ardents at once — but **only one frame total may be mounted at a time**, enforced by `_setMountedFrame`. They live at `system.attributes.ardents`, an array parallel to the Astir's singleton object — see `scripts/frames/ardent.js`.
- **Ardents have no catalog of their own.** `ardentParts()`/`ardentWeapons()` are pure filter *functions* evaluated fresh against the live `ASTIR_PART_CATALOG`/`ASTIR_WEAPON_CATALOG`, never a parallel list that could drift, and they return the exact same object references (not copies), so editing a part's rules text reaches Ardents automatically. A part is Ardent-eligible unless it carries `powerCost` or `weaponPowerBonus`; a weapon is eligible unless it carries a Drain tag (`DRAIN_GROUP`) — an Ardent has no Power pool for any of those to act on. That's the mechanical translation of "Ardents can't use parts/weapons with the Drain tag": a part's Power cost is encoded as `powerCost` here, not a literal tag, so the exclusion is a predicate over that field instead. **A new part or weapon is therefore Ardent-eligible by default** — it only ever needs to be *excluded* by one of those flags, never opted in. The pickers (`chooseAstirPart`/`chooseAstirWeapon`) take an optional `{ title }` override so the Ardent add flows reuse the same dialogs against the filtered catalogs rather than a second implementation.
- **`system.attributes.ardents` entries only ever carry `{ id, name, approach, tier, piloted, parts }`** — no `core`, `power`, `weaponPower`, `overheating`, `img` or `move` (see `buildArdent`). Because Alchemical Suite (`powerCost: 2`) can never be Ardent-eligible, an Ardent can never grant Potions; Standardised Parts (no `powerCost`) *is* eligible, so an Ardent can still grant a Bonus Downtime Tokens pool (see "Adding move content" below), shared across every frame it's installed on (Astir or any Ardent) the same way a part's Expended checkbox already is (see the next bullet).
- **An Ardent's weapons are ordinary `system.attributes.equipment` entries flagged `ardent: "<ardentId>"`** — the direct parallel to an Astir weapon's `astir: true`, managed only from that Ardent's own section via `configureEquipment`'s `ardentWeapon` option (hides Kind and Tier like `astirWeapon`, but never renders Drain's checkboxes). `_equipmentEntry`'s `frame` parameter (generalized from an Astir-only `astir` parameter) resolves such an entry's Tier from whichever object is passed in; both render Astir Scale, since an Ardent is Astir-scale too. Deleting an Ardent cascades to drop every weapon it owns, as `_onAstirDelete` already does for the Astir.
- **`_weaponFrameId(entry)` generalizes the old Astir/mundane piloted-boolean split** to a three-way (or more) frame-ownership check: `"astir"` for an `astir: true` entry, the Ardent's own id for an `ardent: "<id>"` entry, `null` for a mundane weapon. A weapon is offerable (in `_onMoveRoll`'s chooseWeapon prompt, in `_equipmentSpends`, and via its own quick-roll button) exactly when its frame id matches the mounted frame's id (`null` when nothing is mounted, which is also what a mundane weapon compares against) — this is what keeps mundane, Astir and each Ardent's weapons mutually exclusive with no special-casing per kind.
- **A part installed on both the Astir and an Ardent shares one Expended checkbox.** `moveUses` is keyed globally by part key, not per-frame. Accepted as-is: only one frame is ever mounted at a time, and it's already a manual tracker.
- **Mount Up prompts via `ardent.js#chooseFrame`** (mirroring `chooseCarrier`'s labelled-button Dialog) only when the character has more than one unmounted frame; with exactly one, `_onMountUp` mounts it directly. Dismount always clears whichever frame is currently mounted, if any.
- **The Commander playbook's Custom Ardent additionally draws from a second, Commander-exclusive catalog — `ARDENT_FEATURE_PARTS`/`ARDENT_FEATURE_WEAPONS` in `scripts/frames/ardent.js`** — deliberately *not* folded into `ASTIR_PART_CATALOG`/`ASTIR_WEAPON_CATALOG`: those feed `ardentParts()`/`ardentWeapons()` above, which every playbook's Ardent draws from, and Ardent Features must never leak into another playbook's Ardent (or into an Astir's own part/weapon picker — they're mundane military hardware, not Channeler tech). This gives a Commander's Ardent **two independent, separately-capped loadout pools** rather than one raised `ARDENT_MAX_LOADOUT`: the ordinary baseline pool (still capped at 2, exactly like any other playbook's Ardent) plus a Feature pool of its own (`ardentFeatureMax` — base 3, +2 once Requisitions is picked via that move's own `ardentFeatureBonus` flag, summed the same way `tierBonus`/`downtimeTokensMax` are above). `ardentBaselineLoadoutCount`/`ardentFeatureLoadoutCount` (`scripts/frames/ardent.js`) classify each installed item into the right pool and are what the baseline Add Part/Add Weapon handlers check instead of the old combined `ardentLoadoutCount` (kept, unchanged, for callers that never see a Feature-flagged item — the two functions agree exactly whenever nothing is Feature-flagged).
- **Classifying an installed item as baseline vs. Feature relies on two different mechanisms, because parts and weapons are stored differently.** A part is just a catalog-key reference (`ardent.parts`, never edited after being picked — see `isAceFeaturePart`, a plain catalog-membership check), so which catalog it came from is always recoverable. A weapon is not: picking one from a catalog is a snapshot, not a reference (see Equipment below) — the saved entry carries no `catalogKey`, so its source catalog can't be recovered after the fact. Commander's Feature-weapon add flow (`_onArdentFeatureWeaponAdd`) therefore stamps the saved entry with an explicit `commanderFeature: true` flag at add-time — the same "flag the entry, since origin can't be derived later" move `astir: true`/`ardent: "<id>"` already make for frame ownership — and every consumer (`ardentFeatureLoadoutCount`, `getData`'s baseline/Feature weapon split) reads that flag rather than trying to infer origin.
- **A new Ardent-part-shaped catalog has to be folded into every surface that resolves parts by key, not just the ones that render them.** `ARDENT_PART_CATALOG` (`scripts/playbook/playbook-actor-sheet.js`, `= [...ASTIR_PART_CATALOG, ...ARDENT_FEATURE_PARTS]`) is the catalog every `resolveAstirParts` call on an Ardent's own parts now defaults to — `_mountedParts()`, the per-Ardent Moves group in `getData`, and the Feature-pool split in `getData` all use it instead of the plain `ASTIR_PART_CATALOG` default. Missing any one of these doesn't error — `resolveAstirParts` just silently drops a key it can't find, so an installed Ardent Feature part would quietly vanish from whichever surface still used the narrower catalog. `ALL_MOVES` needs the same treatment for a different reason: it's not a display list, it's the flat key-lookup table `_onMoveRoll`/`_onMoveActivate`/`_onMoveDescription`/reroll/`_refreshPeriod`'s uses-clearing walk all search by key — a part catalog left out of it can still *render* (if the `ARDENT_PART_CATALOG` fix above is in place) but its Roll/Activate button, and Refresh Sortie's clearing of its `uses` checkboxes, will silently no-op.
- **Commander's Ace Crew roster** (`system.attributes.aceCrew`, named crew members with an adjective each) reuses `scripts/world-actors/entry-list.js`'s pure CRUD helpers directly, the same functions the World actors section above describes as "shared by every world actor list" — `PlaybookActorSheet` isn't a `WorldActorSheet`, so its three handlers (`_onAceCrewAdd`/`_onAceCrewRemove`/`_onAceCrewFieldChange`) are thin hand-wired wrappers around those same pure functions rather than a second CRUD implementation or a reason to make `PlaybookActorSheet` extend `WorldActorSheet`.
- **Gating a template section to one specific playbook computes a boolean in `getData` (`data.isCommander`), not a Handlebars equality helper** — this module registers no custom Handlebars helpers, so `{{#if}}` alone can't compare `system.playbook.slug` against a literal string. `isCommander` (gating the Ace Crew section and the Commander-only Add-Ardent-Feature controls) is the first instance of this pattern and the template for any future playbook-exclusive section.

### Clocks
- **A generic, reusable narrative clock mechanic lives in `scripts/playbook/clocks.js`, deliberately separate from Gravity Clocks** (`PlaybookActorSheet`'s own `gravityClocks` handling) rather than a generalization of them. Gravity Clocks are a fixed-6-step array tied specifically to the Social tab's Gravity Trigger section, with an extra secondary 1-3 `value` field that has no equivalent in the generic mechanic; retrofitting that shape to be variable-length would have touched already-tested code for no functional gain, so Clocks got its own array (`system.attributes.clocks`, `{id, label, progress, steps}`) and its own pure CRUD module (`addClock`/`removeClock`/`updateClockLabel`/`updateClockSteps`/`setClockProgress`) instead.
- **Clocks are universal, not gated to any playbook or trigger** — every playbook's sheet renders the same always-visible Clocks section on the Social tab, unlike Gravity Clocks (gated on that playbook having a `GRAVITY_TRIGGERS` entry) or Commander-only sections (gated on `isCommander`, above). A clock's own `steps` (`CLOCK_STEPS_MIN`/`MAX`, 2-12, default 6) is player-editable per clock rather than one shared constant the way Gravity Clocks' 6-step track is — this is what let Commander's Withdraw ("start or advance a 4-step clock titled 'court-martialled'") reuse the mechanic instead of inventing its own array; the move's own text stays prose, and creating the actual clock is a manual player action via the section's own Add button, the same "nothing auto-creates an entry from a roll result" convention Gravity Clocks already follow.
- **Progress uses the same click-to-set / click-the-filled-top-to-decrement interaction as Gravity Clocks and Spotlight** (`setClockProgress`, mirroring `_onGravityClockStep`'s inline logic) — clamped to the clock's *own* `steps`, not a shared constant.

### Equipment
- Equipment can be custom-made from scratch, **or** picked as a starting point from `EQUIPMENT_CATALOG` — either way it goes through the same `configureEquipment` editor. Picking a catalog item is a **snapshot, not a reference**: `_onEquipmentCatalogAdd` opens `chooseEquipmentCatalogItem(kind)` then passes the template straight into `configureEquipment` as `initial` (same as editing an existing entry), so the player can still rename it or change tags before saving. The saved entry carries no `catalogKey` and no link back — deliberately unlike `playbookMoves`. Equipment already had to stay freely editable for the custom-made path, and a second "linked but also editable" schema would only exist to answer a question ("has this diverged from its source?") nothing in this module asks.
- **Tags** (Blitz, Defensive, …) are the separate `EQUIPMENT_TAGS` catalog, and an entry stores only tag **keys**. Unlike `EQUIPMENT_CATALOG`, tag keys stay live-referenced even after a catalog-picked item is saved — only the item template itself (name/description/kind/scale/which tag keys) is snapshotted, not the tags' own rules text. `tier` is never part of that snapshot at all — see the Tier note below.
- **`exclusiveGroup`** marks a tag as belonging to a mutually-exclusive set. `DRAIN_GROUP` (Drain 1/2/3, values -1/-2/-3) makes a tag's checkbox behave like a radio button within the group — `configureEquipment`'s render wiring unchecks every other tag sharing the same `exclusiveGroup` the moment one is checked, resolved off the `tags` array already in scope rather than new template data attributes. It exists purely so an item can't carry more than one Drain tier at once; it is *not* required (an item may carry no Drain tier), and since each tier carries a real value rather than being a pure classifier, it still counts against `MAX_TAGS`.
- **`WEAPON_RANGE_GROUP`** (Melee/Ranged/Sniper, all `value: 0` — a pure classifier, not a Value modifier) renders as its own native `<input type="radio">` group in `equipment-editor.hbs`, not as checkboxes in the tag list, since — unlike Drain — a weapon must always carry exactly one. The radio group always has one option pre-checked: whichever range tag `initial` carries when editing, or Melee otherwise, mirroring `weapon-picker.hbs`'s hardcoded Unarmed default. `configureEquipment`'s Save-time check for a missing range is now a defensive fallback rather than the primary safeguard.
  - **Why it can't be validated at Save alone:** Foundry's `Dialog` always closes after a button callback runs, whatever the callback does. A player who forgot to pick got a warning toast *after* the dialog — and everything else they'd typed — was already gone, with no way to recover it. Prefer a defaulted native control over Save-time validation anywhere in a Dialog for this reason.
- **`MAX_TAGS`** (4) caps how many *regular* tags any entry — weapon or gear — can carry, enforced at `configureEquipment` Save. Melee/Ranged/Sniper never count against it (a classifier pick, not a regular tag) and, since they're never rendered as checkboxes, that's structural rather than something Save has to filter out. `DRAIN_GROUP` membership does count.
- Weapons and gear share **one array**, `system.attributes.equipment`, distinguished by a `kind: "weapon" | "gear"` field rather than two separate arrays — add/edit/remove and tag resolution are identical either way, and only the sheet's render (and the tab's separate headers) needs to tell them apart. Only weapons carry `scale` (`WEAPON_SCALES`, purely descriptive — nothing enforces who may wield which, since Astirs aren't their own documents).
- **No weapon stores its own Tier — it's derived from whoever is wielding it, computed fresh in `_equipmentEntry`** (see Recurring conventions). An Astir or Ardent weapon inherits its owning frame's `tier`, passed in as `_equipmentEntry`'s `frame` argument. A mundane weapon instead inherits `_conflictTier().base` — the character's own on-foot Tier — rather than `.effective`, since `.effective` reads as whichever frame is mounted, meaningless for a personal weapon that's already gated off entirely while mounted (see `_weaponGateTooltip`). `configureEquipment` hides its Tier `<input>` for every weapon flow (`hideTier: !carrierWeapon`) except the Carrier's, which has no Tier of its own to inherit and so remains the one flow storing a real `tier` (always `TIER_MAX`). `EQUIPMENT_CATALOG` templates and starting-gear pool items never carry a `tier` field either, for the same reason.
- **Astir/Ardent Parts likewise carry no `tier` of their own** — `getData` derives a display-only Tier badge from the owning frame, purely for that tab's Parts list. Nothing reads a part's Tier mechanically; it's reference only, mirroring `partType`'s badge.
- A tag with a `spend` field (e.g. Blitz: `{ period: "Scene", effect: "confidence" }`) is offerable from the move roll dialog. `_equipmentSpends` collects every unspent spendable tag and passes it to `configureMoveRoll`'s `equipmentSpends` option — **not filtered by move or trait beyond the weapon-scoping below**, the same non-enforcement stance `MOVE_POOLS` takes on pool restrictions. `spend.effect` only ever sets an existing `roll-effects.js` Effect state; when the roll already has a `lockedEffect` (Bite the Dust at max Perils), offered spends render disabled rather than being silently consumed for nothing.
- **A spent tag's state lives nested on the equipment entry itself** (`entry.spent: ["blitz"]`), not in a parallel keyed map like `system.attributes.moveUses`. `moveUses` can key by move key because move keys are stable and global; equipment ids are per-actor and disposable, so a parallel map would orphan entries on delete and would need carrying separately through the playbook-swap preservation below.
- **Equipment is the one exception to `swapActorPlaybook`'s wholesale `system.attributes` replace.** Playbook moves are meant to clear on swap (matching Bite the Dust's own "you do not gain its starting equipment" text about the *new* playbook), but existing equipment is the character's, not the old playbook's, so `swapActorPlaybook` reads it off the actor first and merges it back onto the new attributes.
- **A move flagged `usesWeapon: true`** (Exchange Blows, Strike Decisively) can only ever be wielding one weapon, so `_onMoveRoll` prompts `chooseWeapon` — or the always-offered `UNARMED` sentinel, since both moves' text covers unarmed/verbal conflict — before rolling. The chosen weapon is passed to `_equipmentSpends(lockedEffect, weapon)`: passing anything other than `undefined` (including `null` for Unarmed) excludes every *other* weapon's tags, while gear's tags are never filtered — a character can plausibly have several relevant pieces of gear active, just not two weapons in hand. `chooseWeapon` is skipped entirely when the actor has no weapons. Every non-`usesWeapon` move leaves `weapon` `undefined`.
- **Each weapon in the Equipment tab also gets its own quick-roll button per `usesWeapon` move** (`data.equipment.weapons[].weaponMoves`, built once in `getData` via `_moveGroupMoves(WEAPON_MOVES)` and attached to every weapon entry rather than cross-referenced from a sibling path — see the `../` scoping hazard in Recurring conventions). Clicking one (`_onWeaponMoveRoll`) skips the `chooseWeapon` prompt, since the click *is* the choice. Both entry points converge on `_rollMove(move, weapon)`.
- **The chosen weapon (or "Unarmed") always reaches the chat card**, even when nothing was spent — `_rollMove` only adds a `weaponLabel` key to `rollMove`'s options when `weapon !== undefined`, so every other move's `rollMove` call is unchanged.

### Cosmetic tab
- Look, Consider, Backstory and Notes are four rich-text fields stored at `system.details.look.value`, `system.details.consider.value`, `system.details.biography.value` and `system.details.notes.value`. Backstory/Notes are pure template additions — no `getData` fields, no listeners, no data model — because pbta's own `ActorDataTemplate` defines `details` as an unrestricted `MappingField` of `{label, value}` entries with no `initialKeys` lock, the same mechanism `system.details.callsign` relies on. Any new key just works.
- **Backstory deliberately reuses pbta's own `biography` key** rather than a new one — pbta already auto-migrates legacy plain-string biographies into this `{label, value}` shape (`ActorDataTemplate.migrateData`), so it's the more standard field name rather than a module-invented duplicate.
- **Look and Consider get a starting value, and that takes two parts working together — a `getData` fallback is not enough on its own.** `getData` sets `data.lookText`/`data.considerText` to the actor's stored value when present, falling back to `defaultLookText`/`defaultConsiderText` (`playbook-flavor.js`, built from that playbook's `PLAYBOOK_FLAVOR` entry) when it isn't, and the template's `{{editor}}` call reads `lookText`/`considerText` rather than the `system.details` path. **But that only affects the read-only preview shown before the player clicks to edit** — Foundry's `FormApplication#_activateEditor` re-reads `system.details.look/consider.value` straight off the real document the moment editing starts, bypassing `getData` entirely. So `_seedCosmeticDefaults`, called from `activateListeners`, does the real work: the first time an owned actor's sheet renders with either value still `undefined`, it writes the default text for real via `actor.update()`; after that the editor's own save takes over and it never fires again for that field. Checked against `undefined` rather than falsy, so a player who deliberately clears a field to `""` doesn't get the prompt text resurrected; gated on `actor.isOwner` so a GM or observer opening someone else's sheet never attempts a write it lacks permission for. A playbook with no `PLAYBOOK_FLAVOR` entry just gets an empty starting editor and `_seedCosmeticDefaults` writes nothing for it.
- Unlike `callsign` (a plain `<input>`), these four use Foundry's `{{editor}}` helper, matching both pbta's own `actor-description.hbs` and the sibling Masks module's description tab. Content is passed **unenriched** (no `TextEditor.enrichHTML`) — this module has no other enrichment usage, and adding it here would turn `getData` async for freeform notes that don't need @UUID/roll links.
- Persistence rides entirely on Foundry's default `DocumentSheet`/`FormApplication` editor-save handling, like every other bound `name="system...."` input — `PlaybookActorSheet` doesn't override `_updateObject`.

## Sheet styling
All of this module's CSS lives in one file, `styles/playbook-actor-sheet.css`, covering the actor sheet, every dialog (all carry the `armor-astir` class) and the chat card (its own `armor-astir-move-chat` root, never nested under `armor-astir`). Tokens are declared on both roots so nothing leaks into pbta's chrome or other modules' sheets. None of this is caught by any test — see Recurring conventions.

- **Style against the role tokens, never the gem names.** The palette defines `--aa-moonstone*` / `--aa-amethyst*`, but every rule uses `--aa-primary*` / `--aa-secondary*`, which alias one gem each at the top of the file. Primary = chrome the player acts on (section headers and their underline rules, tab nav, all buttons, hover states); secondary = the player's own tracked state (Spotlight/Gravity Clock pips, numeric readouts, equipment tag labels, row striping). Writing `var(--aa-moonstone)` in a rule works but breaks the abstraction — swapping which gem plays which role is meant to be a two-line edit, and it has already been done once. `grep "var(--aa-moonstone\|var(--aa-amethyst)" styles/` should only ever match the six role mappings.
- **The `-dark` variants are a contrast requirement, not just darker shades.** Moonstone at full strength (`#7fa8b8`) is only ~2.6:1 against white — well under the 4.5:1 floor — so any surface that *fills* with a color and carries white text must use a `-dark` variant (`--aa-moonstone-dark` is ~5.5:1, amethyst is ~8.7:1 even at base). This is why the chat card's Confidence/Desperation chips and the move/weapon picker's trait pills use `--aa-secondary-dark`. Getting this wrong produced unreadable buttons once already.
- **Layout rules on a tab must be scoped to `.tab.active`, not `.tab`.** Core Foundry hides inactive tabs with `.tab[data-tab]:not(.active) { display: none }` (in `public/css/foundry2.css`); scoping to `.active` keeps our rule mutually exclusive with core's so there's no specificity fight. Neither pbta nor the sibling Masks module defines a competing `.tab` rule.
- **`.sheet-tabs` must not carry a top margin.** `.sheet-main` lays `.dangers-column` and `.sheet-tabs-column` side by side starting at the same y, so any top margin on the nav drops the tab headers below the Dangers panel's top edge and visibly breaks the two columns' alignment. The panel padding shared by `.traits` / `.spotlight` / `.dangers-column` / `.tab.active > section` is what does the aligning.
- **Rows that pair a variable-length label with fixed controls use grid, not flex + `space-between`.** `.danger-item` and `.move` both use `grid-template-columns: minmax(0, 1fr) auto` so the controls land in the same fixed column on every row (a straight vertical line down the list) and a long label shrinks instead of pushing them out of the container. Both rules carry a comment explaining this; keep it if editing them.
- **Wrapping optional `{{#if}}` blocks in a flex container is safe even when every branch is false** — Handlebars leaves whitespace inside the wrapper, but whitespace-only text never becomes a flex item, so the container collapses to zero height rather than leaving a phantom gap. `.trait-meters` (Overheating + Power) relies on this; give such a wrapper no margin/padding of its own and leave the spacing on its children.

## Compendium packs (compiled, not committed)
Foundry compendium packs are LevelDB directories at runtime, not loose JSON — you can't point `module.json`'s `packs[].path` at a folder of raw JSON files and expect it to load. The convention (matching the sibling Masks module) is:
- Keep human-readable source under `src/packs/<pack-name>/*.json` (one file per document), committed to git.
- Compile it with `@foundryvtt/foundryvtt-cli` into a real LevelDB pack under `packs/<pack-name>/` via `npm run pullJSONtoLDB` (uses `compilePack`). This output is gitignored — it's a build artifact, regenerate it, don't hand-edit it.
- `npm run pushLDBtoJSON` does the reverse (`extractPack`), for pulling edits made in the Foundry UI back into source JSON.
- Only after compiling does `module.json`'s `packs` array entry actually resolve to something Foundry can load.
