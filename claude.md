# Foundry Module Development Notes

## Concurrent work
- There might be other agents or humans working at the same time as you. Do not panic if you see diffs with changes you did not make in unrelated files. If you and another actor made changes to the same file, then you can investigate.

## Subagent Model Selection

When spawning subagents via the `Agent` tool, set the `model` parameter explicitly rather than relying on inheritance — under `opusplan` or `opus`, a subagent spawned during plan mode inherits Opus, which is overkill and expensive for most exploration.

- **Rote / well-scoped exploration** (known files or symbols, a single targeted lookup, mechanical grep/read work): use `model: "haiku"`.
- **High-complexity exploration** (ambiguous scope, cross-file inference, or output that will directly drive a plan): use `model: "sonnet"`.

Judge each exploration's complexity. When genuinely unsure, prefer `sonnet`.

In practice, a brief that's purely rote (haiku-eligible) is usually also small enough to fall under the "≤3 queries → use Grep/Read directly" guidance and not need a subagent at all — so haiku-tier Explore agents will legitimately be rare. Don't force a haiku call just to exercise the tier; most real briefs mix a verbatim-lookup part with an interpretive part, and bundling both under `sonnet` in one call is correct rather than a sign the dial isn't being used.

## Implementing Plans from Plan Mode

After a plan is approved, prefer delegating the implementation to a subagent with a distilled, self-contained brief rather than continuing inline in the planning session.

- **How**: write the brief to contain only the finalized approach — don't say "implement the plan we discussed," which leans on the polluted history to fill gaps.
- **Exception**: for work that needs tight, iterative back-and-forth or repeated judgment calls, staying inline in the session can be simpler than round-tripping through a subagent.

## Before declaring a task done
- Stage the changes (`git add`) and run the pre-commit checks (`npx lint-staged` and `npm run test:coverage`, as defined in `.husky/pre-commit`) before declaring any task done.

## What a module is
- A Foundry module is a package folder placed in the user data modules directory.
- The module folder name must match the manifest `id` exactly.
- A module can add content, UI changes, new functionality, or translations.
- The baseline PBTA Foundry system source is available in a sibling directory and should be used as the reference environment for this module.
- A similar module for Masks: New Generation is also available in a sibling directory and can be used as a practical example for structure and patterns.
- A sibling directory, `masks-newgeneration-sheets`, contains that game's character/NPC sheet module (`ActorSheet` subclasses in `module/masks-character-sheet.mjs` / `module/masks-npc-sheet.mjs`, Handlebars templates in `templates/`, styling in `styles/`) and can be referenced for how to implement and register custom character sheets. This one has never been updated for core v12+ (tagged releases and `main` all cap at v11) — it's pattern reference only, not something to version-match, and it doesn't create a mismatch risk since it imports pbta's own `PbtaActorSheet` class rather than hardcoding a Foundry-version-specific base class.
- **The sibling `pbta` and `masks-newgeneration-unofficial` repos are pinned (detached HEAD) to the exact versions actually installed** — `pbta` at tag `1.1.15.2`, `masks-newgeneration-unofficial` at tag `1.7.6` — both matching the installed Foundry v12.331.0. This makes their code a reliable reference for what's actually running.
- **If either sibling repo is ever checked out to `main` (or a different tag) again, treat it as running ahead of what's installed** until re-pinned to match. `main` on both tracks newer, unreleased core-version support (e.g. `pbta`'s `main` currently targets core v14 / pbta 1.2.0), and a base-class or namespace reference copied from ahead-of-release source can throw at module-evaluation time — which aborts this module's entire `esmodules` import chain, not just the feature being added (this has happened once already). If in doubt, confirm a reference also appears in the *installed* system bundle (`Data/systems/pbta/module/pbta.js` in the Foundry user data directory) or in Foundry's own unpacked client source (`resources/app/client/...` under the Foundry install directory) — grep both if unsure.
- Foundry does not hot-reload `esmodules` — after editing script files, the Foundry client needs a full reload (not just saving the file) to pick up the change. It *does* hot-reload `css`, `hbs`/`html` and `json` (verified in the installed client's `#handleHotReload`: CSS by cache-busting the `<link>` href, Handlebars by recompiling the partial and re-rendering every open window). So a styling or template tweak can land without a reload, while a script change always needs one — but the reload is driven by a server-side file watcher pushing a socket event, and whether that watcher fires through the `Data/modules/armor-astir` junctions is unverified, so treat a full reload as the reliable fallback whenever an edit doesn't appear.

## Domain conventions
- "Playbooks" are always player-controlled Actors (type `character`), never Items. This differs from the baseline PBTA system, where a playbook is normally an Item of type `playbook` that gets applied to a blank character actor. In this module, dragging a playbook out of a compendium should produce a ready-to-play character actor directly — see `src/packs/basic-playbook-scout/` for the pattern (an Actor document with `system.details.callsign` added so players can also record a callsign alongside the actor's native name/image).

### World actors
- Beyond player-controlled Playbook actors, this module also has three non-playbook actor kinds representing things in the world: the **Carrier** (the players' moving base), the **Authority** (the empire/oppressor), and the **Cause** (the loosely organized factions opposing it). Each is its own Foundry Actor sub-type — `armor-astir.carrier`, `armor-astir.authority`, `armor-astir.cause` — declared via `module.json`'s `documentTypes.Actor`, sheets in `scripts/carrier-actor-sheet.js`/`authority-actor-sheet.js`/`cause-actor-sheet.js`, templates in `templates/*-actor-sheet.hbs`.
- **Why module-declared `documentTypes` rather than pbta's own `other` type + `system.customType`:** the `other`/`customType` route is what pbta's own Actor creation dialog uses, but it requires the type to be registered in `game.pbta.sheetConfig.actorTypes` (pbta's "Configure Sheet" system) — an unregistered `customType` makes `PbtaActor#applyBaseTemplate` merge against `undefined` during `_preCreate` and throw, aborting actor creation. Registering properly means taking over `sheetConfigOverride` (the approach the sibling `masks-newgeneration-unofficial` module takes), which is a much bigger commitment than three simple sheets need. A module-declared sub-type sidesteps pbta's actor-type system entirely: `Actor.TYPES` is `Object.keys(game.model.Actor)` (core Foundry, `common/abstract/document.mjs`), and Foundry's own world-launch step (`updateActiveDocumentTypes`, confirmed in the installed `resources/app/dist/packages/world.mjs`) merges every active module's `documentTypes` into `game.model` *before* pbta's `PbtaActor.createDialog` or `_preCreate` ever run — and since this module bypasses `PbtaActor.createDialog` entirely (see below), pbta's own actor-type list (which doesn't know about `armor-astir.*` types) never gets consulted.
- **Actor creation is entirely custom, not pbta's dialog.** `registerPlaybookActorCreation` (`scripts/actor-creation.js`) rebinds the sidebar's `.create-entry` button to `onCreateEntryClick`, which first calls `chooseActorKind()` — a Dialog offering "Playbook" plus every entry in `WORLD_ACTOR_KINDS` — then either falls into the existing `choosePlaybook()`/`createPlaybookActor()` path or calls `createWorldActor(kind, options)` directly with a plain object (`Actor.create({ name, type, folder, system: kind.buildSystem() })`). No `PbtaActor.createDialog`/`defaultName` codepath is ever exercised, which also sidesteps its unguarded `game.pbta.sheetConfig.actorTypes[type].label` lookup (would throw for an unregistered type) — safe here only because we always supply an explicit name and never call that dialog.
- **`WORLD_ACTOR_KINDS` in `actor-creation.js`** is the single source of truth for the three kinds — `key` (chooseActorKind's dialog button key), `type` (the Foundry Actor type string), `name` (default actor name), `buildSystem()` (returns each kind's starting `system` data fresh per call, so array/object fields are never accidentally shared between actors created from the same kind).
- **`scripts/entry-list.js`** holds pure, Foundry-API-free CRUD helpers (`addEntry`/`removeEntry`/`updateEntryField`) over id-keyed arrays — shared by every world actor list: Carrier's Crew Members, Authority's Assets/Actors/Pillars/Divisions, Cause's Factions.
- **`scripts/world-actor-sheet.js`'s `WorldActorSheet`** is the base class all three sheets extend. It wires one generic set of handlers against `system.attributes.<list>`, all fully dataset-driven, so a new list — or a new stepped counter on an existing list — needs new template markup but no new JS:
  - `.entry-list-add`/`.entry-list-remove`/`.entry-list-field` (`data-list`/`data-entry-id`/`data-field`) cover add/remove/edit. `_entryDefaults(key)` is the one override point for a list whose entries need more than `{name, description}` — Carrier's Crew Members add `position`, Cause's Factions add `exhausted`/`seized`/`grip`.
  - `.entry-list-counter-step` (adding `data-delta`/`data-min`/`data-max`) covers a clamped +/- counter on one entry's field — Authority's Division Strength/Disfavor and Cause's Faction Grip all share this one handler; nothing sheet-specific reads or writes these, the bounds live entirely in the template.
- **Authority's Pillars and Divisions are fixed at exactly three slots each**, not add/remove lists — `createWorldActor`'s `buildSystem` for the Authority kind seeds three blank entries into each at creation, and the sheet renders them with `WorldActorSheet`'s field-edit handler but no add/remove controls. Authority's Stability (1–10, starting at 10) is a click-to-set segmented track like Playbook's Spotlight, but with no decrement-on-reclick behavior, since Stability's floor is 1, not 0 — there's no empty state to decrement into. Each Division additionally carries Strength (0–5, seeded 5/4/4) and Disfavor (0–10, seeded 0) via the generic counter-step mechanism above.
- **Cause's Factions carry two independent status flags** — `exhausted` and `seized` (both default off) — plus a Grip counter (0–3, default 0). The flags are plain checkboxes through `_onEntryFieldChange` (it branches on `event.currentTarget.type === "checkbox"` vs the input's `.value`); Grip goes through `_onEntryCounterStep`. Same manual-tracking model as Playbook moves' `uses` checkboxes and Equipment's `spent` tags: nothing auto-refreshes any of these, the player does.
- **The Carrier can carry up to two weapons**, always custom-made and always Tier 5 — `scripts/carrier-actor-sheet.js` stores them in their own `system.attributes.weapons` array (not playbooks' mixed `system.attributes.equipment`, since a Carrier never has gear). Adding/editing one calls `configureEquipment(..., { carrierWeapon: true })` — a new option on `scripts/equipment.js`'s shared editor, mirroring the existing `astirWeapon` option — that hides the Kind select (always "weapon"), hides the Scale select (always the `"astir"` `WEAPON_SCALES` entry — Carrier weapons are never Foot scale), and disables the Tier input (always `TIER_MAX`); the sheet forces `kind`/`tier` again on save regardless, so a bug in the dialog can't leak a non-weapon or off-tier entry into the array. Each weapon gets a quick-roll button per `usesWeapon` move (Exchange Blows, Strike Decisively — filtered from `BASIC_MOVES`), which always rolls a fixed `{ key: "crew", label: "CREW", value: <this Carrier's own crew stat> }` trait rather than offering CLASH/TALK — clicking a specific weapon's button is the weapon choice, so unlike `PlaybookActorSheet` there's no `chooseWeapon` prompt and no Unarmed option (a Carrier "must use the carrier weapons"). Deliberately skips equipment spends, forced-tag-effects, reroll, and Guided — all of which `PlaybookActorSheet`'s own weapon rolls support — as a v1 scope cut.
- **Playbooks rolling a move with a CREW `fixedTraits` entry (Lead a Sortie) resolve it from the world's Carrier actor(s)**, not a static placeholder. `carrier-actor-sheet.js` exports `findCarrierActors()` (filters `game.actors` by type) and `chooseCarrier(carriers)` (a `choosePlaybook`-style picker), imported by `playbook-actor-sheet.js`. `_moveTraits` resolves the single/zero-Carrier case synchronously for display (0 when zero or ambiguous); `_rollMove` only prompts via `chooseCarrier` when more than one Carrier exists, overriding the trait's value before the roll — cancelling aborts the whole roll, same convention `chooseWeapon`'s own cancel already has.

### Basic moves
- Basic moves are **not** Items or compendium content — they're plain JS objects in the `BASIC_MOVES` array in `scripts/moves.js`, rendered directly by `PlaybookActorSheet` (`scripts/playbook-actor-sheet.js`). Every playbook gets them automatically; there's no per-move pack setup.
- A move object's fields: `key`, `name`, `traits` (array of `TRAITS` keys it can roll +, empty if the move rolls no stat), `description` (HTML rules text), `results.{success,mixed,failure}` (chat result text, `null` if the move defines none). Optional: `hold` (per-tier hold grant, e.g. Read the Room), `questions`/`questionPrompts` (hold-spend flavor), `conditions` (array of `{key,label}` checkbox modifiers each worth +1, for moves with no base stat, e.g. Help or Hinder), `intents` (array of `{key,label}`, a flavor-only choice with no mechanical effect).
- Universal roll modifiers (Advantage/Disadvantage, Confidence/Desperation) live in `scripts/roll-effects.js` and apply to every move roll regardless of the move's own fields — they are not part of a move's definition.
- Trait gating: `system.stats.<key>.disabled` (e.g. `channel` is disabled by default per playbook) hides that trait from a move's rollable options via `availableMoveTraits`/`_moveTraits`, and the move's Roll button itself greys out via each move's `gated` flag in `getData` (`gated` is true only when a move's `traits` is non-empty but every one of those traits is currently disabled for the actor — a move with no `traits` by design, like Help or Hinder, is never gated).

### Playbook moves
- Playbook moves use the **exact same move-object shape** as basic moves and run through the same `_moveGroupMoves`/`rollMove`/`postMoveDescription` path — the difference is purely *who has them*, not what they are.
- Unlike basic/special moves, **no playbook starts with any**. They're organized into pools in `MOVE_POOLS` (`scripts/playbook-moves.js`) and picked one at a time via the "+" button on the sheet's Playbook Moves section, so two Scouts can carry different sets.
- A pool with a `playbookName` (matching a `PLAYBOOKS` entry in `actor-creation.js`) belongs to that playbook; a pool without one is universal (Cantrips, Soldier Moves) and carries a `note` explaining when it applies.
- **Move keys are prefixed with their pool's key** (`the-scout:bullheaded`) because `PlaybookActorSheet` resolves every move — basic, special and playbook — from one flat `ALL_MOVES` list, and different playbooks will eventually name moves the same thing.
- The actor stores **only the picked keys**, in `system.attributes.playbookMoves`; definitions stay in code, so edited rules text reaches existing characters. `resolvePlaybookMoves` drops keys that no longer resolve. Since `swapActorPlaybook` replaces `system.attributes` wholesale, switching playbooks clears the picked moves — which matches the rulebook.
- **Pool restrictions are deliberately not enforced.** The picker shows every pool to every actor. The rules around Soldier Moves ("under specific circumstances") and reaching into another playbook's pool ("in rare circumstances") are loose enough that policing them in code would get in the table's way; the Advancement checklist (`advancements.js`) is where that bookkeeping lives, and it remains a pure tracker that grants nothing.
- `playbookMoveSections` takes an injectable `pools` argument (like `choosePlaybook(playbooks = PLAYBOOKS)`) so its ordering/nesting/emptiness tests use fixtures — otherwise those assertions would quietly stop covering their cases as real move content fills the currently-sparse pools in.
- Cantrips (`MOVE_POOLS`'s `cantrips` entry) are the first pool with real, full content — see "Adding move content" below for the shape each Cantrip maps to, including the `uses` checkbox mechanism it introduced.

### Adding move content
Adding rules text is a pure data change; adding a *mechanic* is not. Classify which one you're doing before planning — the costs are very different (see "What breaks" below).

**Deriving a move's shape from its rules text.** Match on the phrasing, not the flavor:

| Rules text says | Shape |
|---|---|
| "roll +X", "roll +X or +Y" | `traits: ["x","y"]` + `results.{success,mixed,failure}` (`null` per tier the move doesn't define) |
| "+1 if …" bullets with no base stat | `conditions: [{key,label}]`, each worth +1 — e.g. Help or Hinder |
| "on a 10+ hold 3, on a 7-9 hold 1" | `hold: {success,mixed,failure}` → writes the shared `system.resources.hold` |
| "hold 3" with no roll behind it | `flatHold: 3` → its own pool at `system.attributes.moveHold.<moveKey>`, keyed like `uses` so multiple flatHold moves on one actor don't collide, renders **Activate** instead of Roll |
| "spend N hold/a use to succeed [on any move] as if you'd rolled a 10+" | `grantsAutomaticSuccess: { cost: N }` (spent from this move's own `flatHold` pool) or `{ useKey, moves? }` (spent from this move's own `uses` checkbox, optionally restricted to specific move keys) — see below |
| no roll, no tracked resource, pure fiction | `traits: []`, no `results` — description only (Subsystems, Bullheaded). **This is the common case for playbook moves.** |
| a choice that changes no math | `intents: [{key,label}]` |
| a stat with no UI in this module | `fixedTraits: [{key,label,value}]` — appended to the roll options as-is, never read from the actor (Lead a Sortie's CREW) |
| "once per Sortie"/"once per Downtime" | `uses: [{key,label}]` — one checkbox per entry, `checked` read from `system.attributes.moveUses.<moveKey>.<useKey>`. A **manual** tracker only: nothing in this module knows when a Sortie or Downtime starts, so nothing ever unchecks it automatically — the player does, same as the Advancement checklist. Not scoped to playbook moves; works identically for any move source. |
| "your tier... counts as one higher than whatever it would normally be" | `tierBonus: N` → summed across picked moves, added on top of both on-foot base Tier and a mounted frame's own (`_conflictTier`) — contrast `conflictTier` itself, which is *maxed* across picks, not summed |
| "you have a total of N tokens instead of M" | `downtimeTokensMax: N` → `_downtimeTokensMax()` takes the max across picked moves' own flags, same reduce shape as `conflictTier`'s own base |

**Anything that depends on actor state goes in the sheet, not the move.** A move definition is static data. When behavior varies per character, put a boolean on the move and evaluate it in `PlaybookActorSheet` — that's exactly what `requiresChannelDisabled` (b-plot) and `forcesDesperationAtMaxPerils` (bite-the-dust) do.

**Systems that do not exist yet.** When move text needs one of these, transcribe it as prose in `description` and leave a code comment flagging it — don't invent machinery mid-content-entry:
- **weapon tags / profiles** — e.g. a Cantrip granting "Hand-casting II (ranged/area)" or choosing a tag (defensive, decisive, …) to attach to it.
- **roll-modifier stacking** — e.g. buying extra Advantage at the cost of Desperation. Would touch `roll-effects.js`'s state machine.
- **move-level prerequisites** — "Requires: \<other move\>". Consistent with pool membership not being enforced, these stay descriptive — the picker never checks whether the prerequisite is picked.
- **result tiers above 10+** — `moveResultTier` has exactly three tiers (success / mixed / failure); "on a 12+" text has no tier to hook into and stays descriptive.

Usage limits ("once per Sortie/Downtime") are the one exception — see the `uses` row in the shape table above. It's a manual checkbox, not real enforcement (nothing stops a second use, nothing auto-resets it), but it's cheap and removes the need to eyeball a text block during play. Cantrips' Seek Allies / Personal Familiar (`scripts/playbook-moves.js`) are the reference examples.

**`grantsAutomaticSuccess`** (Hot-blooded, Once the War's Over, The Arity Method — `scripts/playbook-moves.js`) is a chat-card button, not a sheet control: `PlaybookActorSheet#_availableAutomaticSuccess` scans every move for this flag ahead of each roll and, for any whose hold pool (`cost`) or `uses` checkbox (`useKey`) is currently spendable, passes it through `moves.js#rollMove` as an offer attached to that roll's chat message (only when the result isn't already a 10+ — nothing to upgrade). The card renders one "Automatic success from \<move\>" button per qualifying source; clicking it (`PlaybookActorSheet#handleAutomaticSuccess`) spends the source, then re-renders the card's `flavor` in place — tier flipped to Success, that move's `results.success` text substituted in, failure reminders cleared, an "Automatic Success (\<source\>)" badge appended — without re-rolling or touching the message's `content` (the dice display), since `Roll.toMessage` keeps those in separate fields. It does **not** retroactively re-grant whatever hold-on-success the original roll's own tier would have written (e.g. a Mixed Read the Room's hold stays at its Mixed value) — the button reframes the fictional outcome and skips the failure/mixed consequences, it doesn't re-resolve the whole roll. `moves` (The Arity Method only) restricts which move keys can trigger the offer at all, the same field/meaning as `EQUIPMENT_TAGS`' own `reroll.moves` in `scripts/equipment.js`; omitted (Hot-blooded, Once the War's Over) means any move qualifies. Not wired up for `postGuidedResult` (Guided's "Take 7-9" skip-the-dice path) — that path posts its card straight into `content` rather than a separate `flavor` field, so it would need its own update path; scoped out for now.

### Move changes: what breaks
- **Adding a basic or special move breaks a test; adding a playbook move doesn't.** `tests/playbook-actor-sheet.test.js` asserts the whole `data.moveGroups` array in a single `toEqual` that enumerates every basic and special move, so a new entry has to be added there too. The Playbook Moves group is empty in that test, so pool content never touches it.
- Tests index move groups **positionally** (`moveGroups[0]` = Basic, `[1]` = Playbook, then Astir if present, then Special last) — reordering `data.moveGroups` breaks many assertions at once.
- Both move test files pin specific keys as module constants (`EXCHANGE_BLOWS`, `B_PLOT`, `BULLHEADED`, …), so renaming or deleting one of those moves breaks them at import.
- **Coverage is a hard gate at 100%**, not just a report (thresholds in `vitest.config.js`). New move *data* costs nothing since it adds no branches — but any new *flag* read in `_moveGroupMoves` does, and needs its own test or the build fails.
- **`.hbs` templates are never rendered by the test suite** — `renderTemplate` is stubbed globally in `tests/setup.js`. Handlebars syntax errors, and wrong `../` scope inside a nested `{{#each}}`, sail past a fully green suite. Template changes have to be eyeballed in a real Foundry client.
- **A template's own `{{else}}`/fallback branch can silently assume a narrower shape-space than the data actually supports, and only a new data shape exposes it.** `starting-gear-picker.hbs` had one `{{else}}` on `{{#if groups.length}}` rendering "There is no starting equipment list for this playbook yet." — dead code for every playbook before Commander, since every prior `STARTING_GEAR_POOLS` entry with any content at all also had non-empty `groups`. Commander's pool is `grantedItems`-only with `groups: []`, which the sheet's own gating (`getData`'s `startingGear.available`, `_onStartingGearAdd`) correctly recognized as "something to show" — but the template's stale `{{else}}` fired anyway, since it keyed only off `groups.length`. Same blind spot as the rest of this section: a template's own conditional coverage has to be checked by hand against every *real* shape a pool can now take, not just the shapes that existed when the fallback was written.

### Astir
- An Astir lives at `system.attributes.astir` on the playbook actor itself (nullable — `null`/absent means "no Astir"), not as its own document. `scripts/astir.js` holds every catalog (`ASTIR_PART_CATALOG`, `ASTIR_MOVE_CATALOG`, `ASTIR_WEAPON_CATALOG`) and the same catalog-in-code/keys-on-actor split `MOVE_POOLS`/`EQUIPMENT_TAGS` already use elsewhere. Astir Parts read as moves (same `traits`/`description`/`uses` shape as `BASIC_MOVES`) and fold into the Moves tab's "Astir Moves" group alongside the Astir's one unique Move — see `PlaybookActorSheet#getData`.
- **A part's/Astir weapon's benefits only apply while the Astir specifically is the mounted frame.** Since Ardents (below) exist, `piloted` is no longer a single Astir-only boolean in practice — `PlaybookActorSheet#_mountedFrame()` returns whichever one frame (the Astir, keyed internally as `"astir"`, or one Ardent, keyed by its own stored id) currently has `piloted: true`, enforced as an invariant by the single write path `_setMountedFrame` (Astir tab's own Piloted checkbox, each Ardent's own, and Mount Up/Dismount all funnel through it — see Ardents below). A player isn't always in a frame, so every frame's Piloted checkbox starts unchecked, and every part-derived effect reads `PlaybookActorSheet#_mountedParts()` (the mounted frame's own installed parts, resolved — `[]` when nothing is mounted) rather than checking "is it the Astir" directly: the whole Astir Moves group (parts *and* the unique Move) gets `gated: true` unless the Astir specifically is mounted, same as Astir weapons' own quick-roll buttons (a separate `astirWeaponMoves` mapping in `getData`, so ordinary weapons are unaffected); every part-granted hook into *other* moves' rolls (Input Channel's +CHANNEL, Spell Routines' Guided, Flourish Component's doubles-regen, Alchemical Suite's Potion grant, Artifact's roll-dialog spend) reads `_mountedParts()` directly. Managing the loadout itself — adding/removing/editing Parts, the Astir Move, Astir weapons, and the base Tier/Core/Approach/Power/Overheating fields — is **not** gated.
- **Every part-specific mechanic is a declarative flag on the catalog entry, evaluated generically in `PlaybookActorSheet`** — the same "boolean on the object, evaluated in the sheet" convention `usesWeapon`/`forcesDesperationAtMaxPerils`/`requiresChannelDisabled` already establish for moves (see "Adding move content" above). `grantsGuided`, `grantsChannelOnAnyMove`, `regainPowerOnDoubles`, `grantsPotionsOnLeadASortie`, `grantsRepairTokens`, `showsReadTheRoomQuestions`, `weaponPowerBonus`, and a part's own `spend` (below) are all read off the actor's *installed* parts (`PlaybookActorSheet#_astirParts()`) for display, or the mounted frame's own (`_mountedParts()`) for any actual effect — the Parts list on the Astir tab still needs to show installed-but-inactive parts even when nothing is mounted.
- **Every Active part gets a manual `uses: [{ key: "expended", label: "Expended" }]` checkbox** — Subsystems' own rules text ("spend 1 Power to re-activate an expended [Active] Astir part") already assumes every Active part can become expended, so this reuses the existing generic `uses` mechanism (`_moveGroupMoves`/`_onMoveUseToggle`) with no new rendering code. A part with an Activate button (`showsReadTheRoomQuestions`) or a roll-dialog spend (below) auto-checks this box when used; every other Active part is toggled by the player manually, same as any other `uses` checkbox in this module. `partType: "Active" | "Passive"` is display-only, rendered as a badge next to a part's name in the Astir tab's Parts list — it doesn't drive any behavior itself.
- **An Astir Part can offer a roll-dialog spend the same way an equipment tag does, but only when its `spend` actually sets `effect` or `advantage`** — `PlaybookActorSheet#_astirPartSpends` requires one of the two (`if (!part.spend?.effect && !part.spend?.advantage) continue;`), the same effect-only gate `_equipmentSpends` applies to equipment tags (Ward, Vorpal, Refresh, ...). Artifact is the one part that qualifies today: its `spend: { effect?, advantage?, description? }` is collected by `_astirPartSpends`, passed to `configureMoveRoll`'s `astirPartSpends` option, and rendered in its own "Astir Parts" section of the roll dialog (`move-roll-dialog.hbs`), structurally identical to the Equipment section. Checking it marks it Expended via `_spendAstirParts` — the *same* field the Astir Moves group's own manual checkbox toggles, so either entry point lands on one shared state. `spend.effect` slots into the same precedence as an equipment tag's spend (Confidence/Desperation axis); `spend.advantage` is a **new** override (nothing overrode the Advantage/Disadvantage axis before Artifact) that wins over the roll dialog's Dice select the same way a spent effect already wins over the Effect select. A part's own rich-text `description` is unsuitable for the compact roll-dialog row (it's multi-paragraph HTML), hence the separate short plain-text `spend.description`. Warding has a `uses: EXPENDED_USE` checkbox like any other Active part, but no `spend` at all — its rules text ("you may use this once per Sortie to reduce an incoming source of harm...") is a manual, non-mechanical adjustment the player tracks themselves, not something that should ever appear as if it modifies the roll in progress; giving it a `spend` object (as it used to have, with no `effect`/`advantage`) let it leak into every move's roll dialog as a checkbox that did nothing when checked. Its Expended checkbox is not gated on the Astir being piloted (see the invariant above), so it stays usable any time, independent of what's being rolled or which weapon/scale is in play.
- **`rollMove` (`scripts/moves.js`) returns `{ message, dice }`, not just the `ChatMessage`** — `PlaybookActorSheet#_rollMove` needs the dice breakdown to check Flourish Component's "regain Power on doubles" (`roll-effects.js#rolledDoubles`, true when the two *kept* dice match) without `moves.js` needing to import `astir.js`. A spent Astir Part's label is likewise passed in pre-resolved (`options.spentPartLabels`) rather than as a raw key, for the same import-direction reason.
- **Weapon Conduit's "+2 Power towards weapons only" is a second, entirely separate Power pool** (`astir.weaponPower`, max via `astirMaxWeaponPower`), not a restriction on the main one — nothing in this module spends Power on weapons yet, so it's tracked exactly like the main Power meter (manually stepped, clamped to its derived max on every Part/Astir-weapon add/edit/remove, hidden by the template whenever its max is 0).
- **A Drain tag (`drain-1`/`drain-2`/`drain-3`, `EQUIPMENT_TAGS`) on a weapon actually mounted on the Astir (`kind: "weapon"`, `astir: true`) lowers Power for real** — `astir.js#astirWeaponDrainTotal` sums it, and `astirMaxPower`/`astirMaxWeaponPower` both take the actor's equipment array (not just its Parts) to fold that in. Drain is paid out of the Weapon Power pool's own capacity first (Weapon Conduit's whole purpose is funding weapon-related power draw) — only once that's exhausted does the remainder reduce main Power (see the private `splitWeaponDrain` helper both Max functions share). A mundane (Foot-scale) weapon's or gear's Drain is inert, same as before — an `astir: true` entry is only ever added/edited/removed from the Astir tab, so its presence in the equipment array already *is* "mounted," with no separate equipped/carried state to track. Unlike Part cost, this reduction is **not** floored at `ASTIR_POWER_MIN`: a heavily-Drained loadout can legitimately push max (and current) Power negative.
- **An Astir with negative Power can't be piloted.** `PlaybookActorSheet#_astirPowerUpdates` (shared by the Part add/remove and Astir-weapon add/edit/remove handlers) re-clamps `power`/`weaponPower` to their recomputed max after any change, and forces `piloted` off with a `ui.notifications.warn` the moment that clamp goes negative while piloted; `_onAstirPilotedToggle` mirrors the same check to block manually re-checking the box while Power is still negative. `getData`'s `power.negative` flag drives a persistent on-sheet indicator (red value + a note under Piloted in the template) as the non-toast counterpart to that warning.
- **Alchemical Suite's Potions** (`astir.potions.{red,blue,yellow}`) are granted, uncapped, whenever *this actor* rolls Lead a Sortie while piloted — the rules text reads as party-wide ("someone leads a Sortie"), but an actor sheet only ever sees its own rolls, so this is deliberately scoped to this Astir's own pilot. Spent via a plain decrement-only "Use" button, the same manual-consumption model as every other tracked resource here.
- **Standardised Parts' Repair Tokens** (`astir.repairTokens`) are a plain number input with no custom JS handler at all (same as the Cosmetic tab's plain-bound fields) — Downtime isn't a tracked phase anywhere in this module, so, like every other "once per Sortie/Downtime" tracker, the player edits the count themselves rather than it being auto-granted.
- **Complex Spellwork's Director-assigned -1 to -4 Power cost is pinned to a fixed `powerCost: 1`** in the catalog, with the rest left as descriptive text — a single catalog entry can only carry one fixed number, and building a variable-cost-at-pick-time flow was explicitly descoped when this was authored.
- **Resistance Charms and Transmutation Link are pure prose** — a Danger-source downgrade system and aerial/aquatic tags don't exist anywhere in this module, matching "Adding move content"'s stance on rules text that needs a system this module hasn't built yet.

### Ardents
- **An Ardent is a cheaper, more limited pilotable frame than the Astir** — no Power, no Core, no unique Move, Tier 2–4 (defaulting to 2, versus the Astir's 3–4 defaulting to 3), an Approach picked freely from the full list rather than a Core-narrowed pair, and a combined parts+weapons loadout capped at `ARDENT_MAX_LOADOUT` (2). Unlike the Astir (at most one per actor), a character may have **any number** of Ardents, and may have both an Astir and Ardents at once — but **only one frame total may be mounted ("piloted") at a time**, enforced by `PlaybookActorSheet#_setMountedFrame`, the single write path every frame's own Piloted checkbox and the Controls section's Mount Up/Dismount buttons all funnel through. They live at `system.attributes.ardents`, an array parallel to the Astir's singleton object — see `scripts/ardent.js`.
- **Ardents have no catalog of their own.** `ardent.js`'s `ardentParts()`/`ardentWeapons()` are pure filter *functions* evaluated fresh on every call against the live `ASTIR_PART_CATALOG`/`ASTIR_WEAPON_CATALOG` (astir.js) — never a parallel list that could drift. A part is Ardent-eligible unless it carries `powerCost` or `weaponPowerBonus` (an Ardent has no Power pool for either to act on); a weapon is Ardent-eligible unless it carries a Drain tag (`DRAIN_GROUP` — an Ardent has no Power for Drain to reduce). This is the mechanical translation of "Ardents can't use parts/weapons with the Drain tag": in this module a part's Power cost is encoded as `powerCost`, not a literal tag, so the exclusion is expressed as a predicate over that field instead. A new Astir part or weapon is therefore Ardent-eligible by default the moment it's added — it only needs to be *excluded* by giving it one of those flags, never opted in. Entries returned by both functions are the exact same object references as in the Astir's own catalogs (not copies), so editing a part's rules text reaches Ardents automatically. The two pickers (`chooseAstirPart`/`chooseAstirWeapon` — astir.js) both take an optional `{ title }` override so the Ardent add flows (`PlaybookActorSheet#_onArdentPartAdd`/`_onArdentWeaponAdd`) reuse the exact same dialogs against the filtered catalogs, rather than a second implementation.
- **`system.attributes.ardents` entries only ever carry `{ id, name, approach, tier, piloted, parts, repairTokens }`** — no `core`, `power`, `weaponPower`, `overheating`, `img`, or `move` (see `ardent.js#buildArdent`). Because Alchemical Suite (`powerCost: 2`) can never be Ardent-eligible, an Ardent can never grant Potions; Standardised Parts (no `powerCost`) *is* Ardent-eligible, so an Ardent can still have Repair Tokens, gated in `getData` the same "object once a granting part is installed, else `null`" way the Astir's own is — but unlike the Astir's, it's written through a manual `_onArdentRepairTokensChange` handler rather than a plain `name`-bound input, since Ardents live in an array (same reasoning Dangers/Gravity Clocks/Burdens already establish for per-entry fields in a list).
- **An Ardent's weapons are ordinary `system.attributes.equipment` entries flagged `ardent: "<ardentId>"`** — the direct parallel to an Astir weapon's `astir: true`, added/edited/removed only from that Ardent's own section on the Astir & Ardents tab via `configureEquipment`'s new `ardentWeapon` option (hides Kind and Tier, same as `astirWeapon`, but never renders Drain's checkboxes — an Ardent weapon can never carry Drain). `PlaybookActorSheet#_equipmentEntry`'s `frame` parameter (generalized from an Astir-only `astir` parameter) resolves such an entry's Tier from whichever object — the Astir's or the owning Ardent's — is passed in; both render Astir Scale, since an Ardent is Astir-scale too. Deleting an Ardent cascades to drop every weapon it owns, the same cascade `_onAstirDelete` already gives the Astir.
- **`PlaybookActorSheet#_weaponFrameId(entry)` generalizes the old Astir/mundane piloted-boolean split** to a three-way (or more) frame-ownership check: `"astir"` for an `astir: true` entry, the Ardent's own id for an `ardent: "<id>"` entry, `null` for a mundane weapon. A weapon is offerable (in `_onMoveRoll`'s chooseWeapon prompt, in `_equipmentSpends`, and via its own quick-roll button) exactly when its frame id matches the currently mounted frame's id (`null` when nothing is mounted, which is also what a mundane weapon's id compares against) — this is what lets a mundane weapon, the Astir's weapons, and each individual Ardent's weapons all stay mutually exclusive with no special-casing per kind.
- **A part installed on both the Astir and an Ardent shares one Expended checkbox.** `moveUses` is keyed globally by move/part key (`system.attributes.moveUses.<partKey>.expended`), not per-frame — installing e.g. Chromatic Focus on both the Astir and an Ardent means marking it Expended from either frame's roll dialog checks it for both. Accepted as-is: only one frame is ever mounted at a time, and this is already a manual tracker the player is expected to reset themselves (same as every other `uses` checkbox in this module).
- **Mount Up prompts via `ardent.js#chooseFrame`** (mirroring `carrier-actor-sheet.js#chooseCarrier`'s labelled-button Dialog exactly) only when the character has more than one unmounted frame; with exactly one, `_onMountUp` mounts it directly with no prompt. Dismount always clears whichever frame is currently mounted, if any.
- **The Commander playbook's Custom Ardent additionally draws from a second, Commander-exclusive catalog — `ARDENT_FEATURE_PARTS`/`ARDENT_FEATURE_WEAPONS` in `ardent.js`** — deliberately *not* folded into `ASTIR_PART_CATALOG`/`ASTIR_WEAPON_CATALOG`: those feed `ardentParts()`/`ardentWeapons()` above, which every playbook's Ardent draws from, and Ardent Features must never leak into another playbook's Ardent (or into an Astir's own part/weapon picker — they're mundane military hardware, not Channeler tech). This gives a Commander's Ardent **two independent, separately-capped loadout pools** rather than one raised `ARDENT_MAX_LOADOUT`: the ordinary baseline pool (still capped at 2, exactly like any other playbook's Ardent) plus a Feature pool of its own (`ardentFeatureMax` — base 3, +2 once Requisitions is picked via that move's own `ardentFeatureBonus` flag, summed the same way `tierBonus`/`downtimeTokensMax` are below). `ardentBaselineLoadoutCount`/`ardentFeatureLoadoutCount` (ardent.js) classify each installed item into the right pool and are what the baseline Add Part/Add Weapon handlers check instead of the old combined `ardentLoadoutCount` (kept, unchanged, for callers that never see a Feature-flagged item — the two functions agree exactly whenever nothing is Feature-flagged).
- **Classifying an installed item as baseline vs. Feature relies on two different mechanisms, because parts and weapons are stored differently.** A part is just a catalog-key reference (`ardent.parts`, never edited after being picked — see `isAceFeaturePart`, a plain catalog-membership check), so which catalog it came from is always recoverable. A weapon is not: picking one from a catalog is a snapshot, not a reference (see Equipment below) — the saved entry carries no `catalogKey`, so its source catalog can't be recovered after the fact. Commander's Feature-weapon add flow (`_onArdentFeatureWeaponAdd`) therefore stamps the saved entry with an explicit `commanderFeature: true` flag at add-time — the same "flag the entry, since origin can't be derived later" move `astir: true`/`ardent: "<id>"` already make for frame ownership — and every consumer (`ardentFeatureLoadoutCount`, `getData`'s baseline/Feature weapon split) reads that flag rather than trying to infer origin.
- **A new Ardent-part-shaped catalog has to be folded into every surface that resolves parts by key, not just the ones that render them.** `ARDENT_PART_CATALOG` (`playbook-actor-sheet.js`, `= [...ASTIR_PART_CATALOG, ...ARDENT_FEATURE_PARTS]`) is the catalog every `resolveAstirParts` call on an Ardent's own parts now defaults to — `_mountedParts()`, the per-Ardent Moves group in `getData`, and the Feature-pool split in `getData` all use it instead of the plain `ASTIR_PART_CATALOG` default. Missing any one of these doesn't error — `resolveAstirParts` just silently drops a key it can't find, so an installed Ardent Feature part would quietly vanish from whichever surface still used the narrower catalog. `ALL_MOVES` needs the same treatment for a different reason: it's not a display list, it's the flat key-lookup table `_onMoveRoll`/`_onMoveActivate`/`_onMoveDescription`/reroll/`_refreshPeriod`'s uses-clearing walk all search by key — a part catalog left out of it can still *render* (if the `ARDENT_PART_CATALOG` fix above is in place) but its Roll/Activate button, and Refresh Sortie's clearing of its `uses` checkboxes, will silently no-op.
- **Commander's Ace Crew roster** (`system.attributes.aceCrew`, named crew members with an adjective each) reuses `scripts/entry-list.js`'s pure CRUD helpers directly, the same functions the World actors section above describes as "shared by every world actor list" — `PlaybookActorSheet` isn't a `WorldActorSheet`, so its three handlers (`_onAceCrewAdd`/`_onAceCrewRemove`/`_onAceCrewFieldChange`) are thin hand-wired wrappers around those same pure functions rather than a second CRUD implementation or a reason to make `PlaybookActorSheet` extend `WorldActorSheet`.
- **Gating a template section to one specific playbook computes a boolean in `getData` (`data.isCommander`), not a Handlebars equality helper** — this module registers no custom Handlebars helpers, so `{{#if}}` alone can't compare `system.playbook.slug` against a literal string. `isCommander` (gating the Ace Crew section and the Commander-only Add-Ardent-Feature controls) is the first instance of this pattern and the template for any future playbook-exclusive section.

### Clocks
- **A generic, reusable narrative clock mechanic lives in `scripts/clocks.js`, deliberately separate from Gravity Clocks** (`PlaybookActorSheet`'s own `gravityClocks` handling) rather than a generalization of them. Gravity Clocks are a fixed-6-step array tied specifically to the Social tab's Gravity Trigger section, with an extra secondary 1-3 `value` field that has no equivalent in the generic mechanic; retrofitting that shape to be variable-length would have touched already-tested code for no functional gain, so Clocks got its own array (`system.attributes.clocks`, `{id, label, progress, steps}`) and its own pure CRUD module (`addClock`/`removeClock`/`updateClockLabel`/`updateClockSteps`/`setClockProgress`) instead.
- **Clocks are universal, not gated to any playbook or trigger** — every playbook's sheet renders the same always-visible Clocks section on the Social tab, unlike Gravity Clocks (gated on that playbook having a `GRAVITY_TRIGGERS` entry) or Commander-only sections (gated on `isCommander`, above). A clock's own `steps` (`CLOCK_STEPS_MIN`/`MAX`, 2-12, default 6) is player-editable per clock rather than one shared constant the way Gravity Clocks' 6-step track is — this is what let Commander's Withdraw ("start or advance a 4-step clock titled 'court-martialled'") reuse the mechanic instead of inventing its own array; the move's own text stays prose, and creating the actual clock is a manual player action via the section's own Add button, the same "nothing auto-creates an entry from a roll result" convention Gravity Clocks already follow.
- **Progress uses the same click-to-set / click-the-filled-top-to-decrement interaction as Gravity Clocks and Spotlight** (`setClockProgress`, mirroring `_onGravityClockStep`'s inline logic) — clamped to the clock's *own* `steps`, not a shared constant.

### Equipment
- Equipment can be custom-made from scratch, **or** picked as a starting point from `EQUIPMENT_CATALOG` (`scripts/equipment.js`) — either way it ends up going through the same `configureEquipment` editor. Picking a catalog item is a **snapshot, not a reference**: `PlaybookActorSheet#_onEquipmentCatalogAdd` opens `chooseEquipmentCatalogItem(kind)` to pick a template, then passes it straight into `configureEquipment` as `initial` (same as editing an existing entry) so the player can still rename it or add/drop tags before saving. The saved entry carries no `catalogKey` and no link back — this is deliberately unlike `playbookMoves`, which stores a permanent key reference; equipment already needed to stay freely editable (the custom-made path), and a second "linked but also editable" schema would only exist to answer a question ("has this diverged from its catalog source?") nothing in this module asks.
- **Tags** (Blitz, Defensive, …) are the other, separate catalog: `EQUIPMENT_TAGS` in `scripts/equipment.js` holds the definitions, and an equipment entry stores only the tag **keys** it has, the same catalog/keys split `MOVE_POOLS`/`playbookMoves` use for moves. `resolveEquipmentTags` drops a stale key quietly, mirroring `resolvePlaybookMoves`. Unlike `EQUIPMENT_CATALOG`, tag keys stay live-referenced even after a catalog-picked item is saved — only the item template itself (name/description/kind/scale/which tag keys) is snapshotted, not the tags' own rules text. `tier` is never part of that snapshot at all — see the Tier note below.
- **`exclusiveGroup`** marks a tag as belonging to a mutually-exclusive set. `DRAIN_GROUP` (Drain 1/2/3, values -1/-2/-3) makes a tag's checkbox behave like a radio button within that group value — `configureEquipment`'s render wiring unchecks every other tag sharing the same `exclusiveGroup` the moment one is checked, resolved off the `tags` array already in scope rather than new template data attributes. It exists purely so an item can't carry more than one Drain tier at once (Drain used to be simulated by repeating the same `drain` key, which the editor's one-checkbox-per-key model couldn't actually produce or preserve through a re-save); it is *not* required — an item may carry no Drain tier — and, since each tier carries a real value rather than being a pure classifier, it still counts against `MAX_TAGS` below.
- **`WEAPON_RANGE_GROUP`** (Melee/Ranged/Sniper, all `value: 0` — a pure classifier, not a Value modifier) instead renders as its own native `<input type="radio">` group in `equipment-editor.hbs`, not as checkboxes in the tag list, since — unlike Drain — a weapon must always carry exactly one. It used to be a checkbox trio sharing `DRAIN_GROUP`'s exclusiveGroup mechanism, validated only at `configureEquipment`'s Save (`ui.notifications.warn` when Kind is Weapon and none of the three was checked) — but Foundry's `Dialog` always closes after a button callback runs regardless of what the callback does, so a player who forgot to check one got a warning toast after the dialog (and everything else they'd typed) was already gone, with no way to recover it. The radio group instead always has one option pre-checked by default — whichever range tag `initial` already carries when editing, or Melee otherwise — mirroring `weapon-picker.hbs`'s own hardcoded Unarmed default; a native radio group with a default can't end up with nothing selected through normal use, so `configureEquipment`'s Save-time check is now a defensive fallback rather than the primary safeguard. That's still a single hardcoded weapon-only check, not a generic "required groups" system, since it's the only group that needs one.
- **`MAX_TAGS`** (4) caps how many *regular* tags any equipment entry — weapon or gear — can carry, enforced at `configureEquipment` Save the same way as the weapon-range check above. Melee/Ranged/Sniper never count against this cap — they're a classifier pick, not a regular tag — and, since they're never rendered as checkboxes at all, that's now structural rather than something Save has to filter out. `DRAIN_GROUP` membership does count, for the reason above.
- Weapons and gear share **one array**, `system.attributes.equipment`, distinguished by a `kind: "weapon" | "gear"` field rather than two separate arrays — add/edit/remove and tag resolution are identical either way, and only the sheet's render (and the tab's separate Weapons/Gear headers) needs to tell them apart. Only weapons carry `scale` (`WEAPON_SCALES`, purely descriptive — nothing enforces who may wield which, since Astirs aren't their own documents yet).
- **No weapon stores its own Tier — every weapon's Tier is derived from whoever/whatever is wielding it, computed fresh in `PlaybookActorSheet#_equipmentEntry` (never persisted, same "derive fresh every render" convention `_conflictTier`/`equipmentValue`/`advancements.topCount` already establish).** An Astir or Ardent weapon (`astir: true`/`ardent: "<id>"`) inherits its owning frame's own `tier` field, passed in as `_equipmentEntry`'s `frame` argument. A mundane (plain foot-scale) weapon instead inherits `_conflictTier().base` — the wielding character's own on-foot Tier — rather than `.effective`, since `.effective` would read as whichever frame is currently mounted, which is meaningless for a personal weapon that's already gated off entirely while mounted (see `_weaponGateTooltip`). `configureEquipment` hides its Tier `<input>` for every weapon flow (`hideTier: !carrierWeapon`) except the Carrier's — a Carrier has no Tier of its own for a weapon to inherit, so `carrierWeapon` remains the one flow that still stores a real `tier` on the entry, always fixed at `TIER_MAX` (see the Carrier note above). `EQUIPMENT_CATALOG` templates and starting-gear pool items (`scripts/starting-gear.js`) never carry a `tier` field either, for the same reason.
- **Astir/Ardent Parts likewise carry no `tier` field of their own** — `getData` derives a display-only Tier badge for each installed part from its owning frame (`astir.tier` for the Astir's own Parts list, that specific Ardent's own `tier` for its Parts list), purely for the Astir/Ardent tab's Parts list. Nothing reads a part's Tier for any mechanical purpose — it's flavor/reference only, mirroring `partType`'s own display-only badge.
- An entry's **Value is always the live sum of its current tags** (`equipmentValue`) — never stored on the entry — so it can't drift out of sync after a tag is added or removed, the same reasoning as `data.advancements.topCount` being computed in `getData` rather than persisted.
- A tag with a `spend` field (e.g. Blitz: `{ period: "Scene", effect: "confidence" }`) is offerable from the move roll dialog. `PlaybookActorSheet#_equipmentSpends` collects every unspent spendable tag across the actor's equipment and passes it to `configureMoveRoll`'s `equipmentSpends` option — **not filtered by move or trait beyond the weapon-scoping below**, the same non-enforcement stance `MOVE_POOLS` takes on pool restrictions. `spend.effect` only ever sets an existing `roll-effects.js` Effect state; when the roll already has a `lockedEffect` (Bite the Dust at max Perils), offered spends render disabled rather than being silently consumed for nothing.
- **A spent tag's state lives nested on the equipment entry itself** (`entry.spent: ["blitz"]`), not in a parallel keyed map like `system.attributes.moveUses`. `moveUses` can key by move key because move keys are stable and global; equipment ids are per-actor and disposable, so a parallel map would orphan entries on delete and would need carrying separately through the playbook-swap preservation below. Nesting `spent` inside the entry avoids both problems. Like `moveUses`, unchecking is manual — nothing in this module knows when a Scene starts, so a spent tag stays spent until the player clears it themselves (on the sheet, or by spending it again next roll).
- **Equipment is the one exception to `swapActorPlaybook`'s wholesale `system.attributes` replace.** Playbook moves are meant to clear on swap (matching Bite the Dust's own "you do not gain its starting equipment" text about the *new* playbook), but existing equipment is the character's, not the old playbook's, so `swapActorPlaybook` reads it off the actor first and merges it back onto the new attributes.
- The Equipment tab's `{{#each tags}}` nested inside `{{#each weapons}}`/`{{#each gear}}` is exactly the `../` scoping shape flagged in "Move changes: what breaks" as invisible to the test suite (`renderTemplate` is stubbed) — eyeball it in a real Foundry client after template edits here.
- **A move flagged `usesWeapon: true`** (Exchange Blows, Strike Decisively — `scripts/moves.js`) can only ever be wielding one weapon at a time, so `PlaybookActorSheet#_onMoveRoll` prompts `chooseWeapon` (`scripts/equipment.js`) for which weapon — or the always-offered `UNARMED` sentinel, since both moves' text covers unarmed/verbal conflict too — before rolling. The chosen weapon is passed through to `_equipmentSpends(lockedEffect, weapon)`: passing anything other than `undefined` (including `null` for Unarmed) excludes every *other* weapon's tags from what's offered, while gear's tags are never filtered — a character can plausibly have more than one relevant piece of gear active, just not more than one weapon in hand. `chooseWeapon` is skipped entirely when the actor has no weapons at all (nothing to choose between). Every non-`usesWeapon` move leaves `weapon` `undefined`, which both `_equipmentSpends` and the `weaponLabel` computation below treat identically to before this existed.
- **Each weapon in the Equipment tab gets its own quick-roll button per `usesWeapon` move** (`data.equipment.weapons[].weaponMoves`, built once in `getData` via `_moveGroupMoves(WEAPON_MOVES)` and attached to every weapon entry rather than cross-referenced from a sibling path — see the `../` scoping note above). Clicking one (`PlaybookActorSheet#_onWeaponMoveRoll`) skips the `chooseWeapon` prompt entirely, since the click itself is the weapon choice. Both entry points converge on `_rollMove(move, weapon)`, the single roll pipeline `_onMoveRoll` and `_onWeaponMoveRoll` share.
- **The chosen weapon (or "Unarmed") always reaches the chat card**, even when nothing was spent — `_rollMove` only adds a `weaponLabel` key to `rollMove`'s options when `weapon !== undefined` (i.e. only for a `usesWeapon` move), so every other move's `rollMove` call is byte-for-byte unchanged from before.

### Cosmetic tab
- Look, Consider, Backstory and Notes are four rich-text fields on the sheet's Cosmetic tab, stored at `system.details.look.value`, `system.details.consider.value`, `system.details.biography.value` and `system.details.notes.value`. Backstory/Notes are pure template additions — no `getData` fields, no listeners, no data model, because pbta's own `ActorDataTemplate` (`pbta/src/module/data/actor/templates/actor.js`) already defines `details` as an unrestricted `MappingField` of `{label, value}` entries with no `initialKeys` lock, the exact mechanism `system.details.callsign` already relies on. Any new key just works.
- **Backstory deliberately reuses pbta's own `biography` key** rather than a new one — pbta already auto-migrates legacy plain-string biographies into this `{label, value}` shape (`ActorDataTemplate.migrateData`), so this is the more standard field name rather than a module-invented duplicate.
- **Look and Consider are editable, unlike a plain rich-text field, they get a starting value, and that takes two parts working together — a `getData` display fallback is not enough on its own.** `PlaybookActorSheet#getData` sets `data.lookText`/`data.considerText` to the actor's own stored value when present, falling back to `defaultLookText`/`defaultConsiderText` (`playbook-flavor.js`) — HTML built from that playbook's `PLAYBOOK_FLAVOR` entry (the same chargen prompts/questions this tab used to render read-only) — when it isn't; the template's `{{editor}}` call reads from `lookText`/`considerText` directly rather than `data.system.details.look.value`. **But that alone only affects the read-only preview shown before the player clicks to edit** — Foundry's own `FormApplication#_activateEditor` (`client/apps/form.js`) re-reads `system.details.look/consider.value` straight off the real actor document the moment editing actually starts, bypassing whatever `getData` computed entirely. So `PlaybookActorSheet#_seedCosmeticDefaults`, called from `activateListeners`, does the real work: the first time an owned actor's sheet renders with `system.details.look/consider.value` still `undefined`, it writes the same default text for real via `actor.update()` — after that, the editor's own save takes over and this never fires again for that field. Checked against `undefined` rather than falsy so a player who deliberately clears a field to `""` doesn't have the prompt text resurrected on the next render; gated on `actor.isOwner` so a GM or observer opening someone else's sheet never attempts a write it doesn't have permission for. A playbook with no `PLAYBOOK_FLAVOR` entry (every playbook but The Scout, currently) just gets an empty starting editor, and `_seedCosmeticDefaults` writes nothing for it. There used to be a separate, permanently-read-only Appearance field alongside a non-editable Look list; both were collapsed into this one editable Look field, and Consider went from read-only to editable the same way.
- Unlike `callsign` (a plain `<input>`), these four use Foundry's `{{editor}}` helper for rich text, matching the pattern in both `pbta`'s own `actor-description.hbs` and the sibling Masks module's description tab. Content is passed **unenriched** (no `TextEditor.enrichHTML`) — this module has no other enrichment usage anywhere, and adding it here would turn `getData` async for a freeform-notes field that doesn't need @UUID/roll links.
- Persistence rides entirely on Foundry's default `DocumentSheet`/`FormApplication` editor-save handling, the same as every other bound `name="system...."` input on this sheet — `PlaybookActorSheet` doesn't override `_updateObject`.

## Sheet styling
All of this module's CSS lives in one file, `styles/playbook-actor-sheet.css`, covering the actor sheet, every dialog (all carry the `armor-astir` class) and the chat card (its own `armor-astir-move-chat` root, never nested under `armor-astir`). Tokens are declared on both roots so nothing leaks into pbta's chrome or other modules' sheets.

- **Style against the role tokens, never the gem names.** The palette defines `--aa-moonstone*` / `--aa-amethyst*`, but every rule uses `--aa-primary*` / `--aa-secondary*`, which alias one gem each at the top of the file. Primary = chrome the player acts on (section headers and their underline rules, tab nav, all buttons, hover states); secondary = the player's own tracked state (Spotlight/Gravity Clock pips, numeric readouts, equipment tag labels, row striping). Writing `var(--aa-moonstone)` in a rule works but breaks the abstraction — swapping which gem plays which role is meant to be a two-line edit, and it has already been done once. `grep "var(--aa-moonstone\|var(--aa-amethyst)" styles/` should only ever match the six role mappings.
- **The `-dark` variants are a contrast requirement, not just darker shades.** Moonstone at full strength (`#7fa8b8`) is only ~2.6:1 against white — well under the 4.5:1 floor — so any surface that *fills* with a color and carries white text must use a `-dark` variant (`--aa-moonstone-dark` is ~5.5:1, amethyst is ~8.7:1 even at base). This is why the chat card's Confidence/Desperation chips and the move/weapon picker's trait pills use `--aa-secondary-dark` rather than `--aa-secondary`. Getting this wrong produced unreadable buttons once already; it isn't visible in any test, only by looking at the sheet.
- **Layout rules on a tab must be scoped to `.tab.active`, not `.tab`.** Core Foundry hides inactive tabs with `.tab[data-tab]:not(.active) { display: none }` (in `public/css/foundry2.css`); scoping to `.active` keeps our rule mutually exclusive with core's so there's no specificity fight over which wins. Neither pbta nor the sibling Masks module defines a competing `.tab` rule.
- **`.sheet-tabs` must not carry a top margin.** `.sheet-main` lays `.dangers-column` and `.sheet-tabs-column` side by side starting at the same y, so any top margin on the nav drops the tab headers below the Dangers panel's top edge and visibly breaks the two columns' alignment. The panel padding shared by `.traits` / `.spotlight` / `.dangers-column` / `.tab.active > section` is what does the aligning — an earlier `padding-top` fudge on `.dangers-column` was removed in favour of it.
- **Rows that pair a variable-length label with fixed controls use grid, not flex + `space-between`.** `.danger-item` and `.move` both use `grid-template-columns: minmax(0, 1fr) auto` so the controls land in the same fixed column on every row (a straight vertical line down the list) and a long label shrinks instead of pushing them out of the container. Both rules carry a comment explaining this; keep it if editing them.
- **Wrapping optional `{{#if}}` blocks in a flex container is safe even when every branch is false** — Handlebars leaves whitespace inside the wrapper, but whitespace-only text never becomes a flex item, so the container collapses to zero height rather than leaving a phantom gap. `.trait-meters` (Overheating + Power) relies on this; give such a wrapper no margin/padding of its own and leave the spacing on its children.
- Templates are never rendered by the test suite and CSS is not linted (`lint-staged` only runs ESLint on `.js`), so **nothing here is caught by `npm run test:coverage`** — style and template changes have to be eyeballed in a real Foundry client. See "Move changes: what breaks" for the `../` scoping hazard that hides in the same blind spot.

## Compendium packs (compiled, not committed)
Foundry compendium packs are LevelDB directories at runtime, not loose JSON — you can't point `module.json`'s `packs[].path` at a folder of raw JSON files and expect it to load. The convention (matching the sibling Masks module) is:
- Keep human-readable source under `src/packs/<pack-name>/*.json` (one file per document), committed to git.
- Compile it with `@foundryvtt/foundryvtt-cli` into a real LevelDB pack under `packs/<pack-name>/` via `npm run pullJSONtoLDB` (uses `compilePack`). This output is gitignored — it's a build artifact, regenerate it, don't hand-edit it.
- `npm run pushLDBtoJSON` does the reverse (`extractPack`), for pulling edits made in the Foundry UI back into source JSON.
- Only after compiling does `module.json`'s `packs` array entry actually resolve to something Foundry can load.

## Linking a dev checkout into Foundry's Data/modules on Windows
To test a working checkout without repackaging on every change, you'd naturally symlink/junction the repo into `Data/modules/<module-id>`. **This does not work if the top-level module folder itself is the link.**

Windows/Node quirk: `fs.readdir(dir, { withFileTypes: true })` reports a junction or symlinked directory as `isSymbolicLink: true` / `isDirectory: false`, even though `fs.stat` (which follows it) correctly resolves it as a directory. Foundry's package scanner enumerates `Data/modules/*` and — like most scanners — filters on `isDirectory()` from that raw listing. A linked top-level module folder is silently skipped: no error, no warning, it just never appears in *Manage Modules*.

The fix is to invert which level gets linked:
1. Make `Data/modules/<module-id>` a **real** directory (not a reparse point).
2. Copy the small, rarely-changing manifest files into it directly: `module.json`, `LICENSE`, `README.md`. Re-copy after editing these in the repo.
3. Inside that real directory, create junctions for the frequently-changing subfolders only — e.g. `scripts/` and `packs/` — pointing at the repo's copies. Nested paths are reached via direct file access (`readFile`/`stat`), which follows reparse points fine; it's only the top-level scan that's affected.

This gives live-reloading dev iteration for code and compiled packs, while still satisfying Foundry's directory scan.
